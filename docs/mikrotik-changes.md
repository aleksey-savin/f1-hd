# Mikrotik changes proposed by AI agents — Implementation Notes

Added 2026-10-10. An AI agent that holds an MCP key with the `mikrotikChanges`
access can **propose** a configuration change for a managed Mikrotik device. HD
validates the proposal, compares it with the live router (read-only), asks the
named people to approve, takes a backup, applies the commands and records what
happened. The agent never writes to a router: it has `propose`, `get` and `list`
tools only.

This file describes behaviour, data, rules and operations. The MCP tools are
described in `docs/mcp.md` («Mikrotik change tools»); the device module in
`docs/mikrotik-management.md`; the notification categories in
`docs/notifications.md`. Design intent and the agreed scope:
`docs/superpowers/specs/2026-10-10-mikrotik-agent-changes-design.md` (Russian;
its last section lists where the implementation differs).

## Purpose and scope

In scope:

- actions `add`, `set`, `remove`, `enable`, `disable` on RouterOS menus, as
  structured commands (never console text);
- up to 30 commands per request, one device per request;
- human approval (one or two steps) through the portal or Telegram;
- a pre-change backup, safe mode held for the duration of the apply, an outcome
  decided by re-reading the router;
- WireGuard client configuration (`.conf`) generated by HD, with keys the agent
  never sees.

Out of scope (not implemented): restoring from the backup, manual rollback,
scripts, the scheduler, reboot, router users, one request for several devices,
placeholders other than the two WireGuard keys, secrets passed by the agent.

## Roles and who decides

**Requester.** The agent passes the Telegram id of the person who asked
(`requester`, digits). `mongoStore.findUserByTelegram` finds an employee whose
`telegramBot.chatId` equals it and `telegramBot.isActive` is true, who is not
an end user (`isEndUser: false`), not a service account and not banned
(`isBanned`). No match: the proposal is refused with an explanation. Two
matching employees: refused (`more than one employee has this Telegram id`).
HD takes the agent's word about *who asked*, so naming a person grants
nothing: every decision is made by a person who signed in to HD, or who tapped
a button in their own private Telegram chat.

**Responsible person.** `Mikrotik.responsibleId` (optional). Set in the record
create/update handlers (routes guarded by `mikrotik.manage`); `parseResponsible`
validates a changed value with `services/mikrotik/responsible.js`: the user must
be a current employee (not end user, not service account, not banned) holding
`mikrotik.approveChanges`; otherwise `422`. A value equal to the stored one is
not re-validated, so a responsible person who lost the right does not block
other edits of the record. A change is written to the audit log
(`responsibleFrom` / `responsibleTo`). `GET …/responsible-candidates` lists the
eligible people. `describe()` returns the name and whether the right is still
held.

**Right.** `mikrotik.approveChanges` (dictionary `auth/access.js`, staff
audience). It is required to *approve* on a single-step request and on the
responsible person's step; it is not required for the requester's confirmation
step of a two-step request. The right is evaluated from the session (portal) or
from `req.auth` of the Telegram actor (bot), never from the request body. See
«Operations» for the one-off grant.

**Decision table** (`planSteps`, evaluated when the agent proposes):

| Responsible | Requester | Steps |
|---|---|---|
| set, a different person | right not needed | 1) requester confirms «I asked for this»; 2) responsible approves |
| set, the same person | needs the right | one step (role `responsible`) |
| not set | has the right | one step (role `requester`) |
| not set | no right | refused: nobody can approve |
| set, but he or she lost the right | any | refused: ask an administrator to assign another person |

The request for the responsible person is created and notified only after the
requester's confirmation. Either person can reject at their step; a rejection
is final. The requester can cancel (`cancel`) while the request is still open
(`awaiting_*`) and not expired. `responsible` on the record is a snapshot of
the device's `responsibleId` at proposal time.

**Who can see a request** (`changeView.toView`):

- the requester, the responsible person (snapshot) and anyone with a step: full view;
- anyone holding `mikrotik.approveChanges` or `mikrotik.manageConfigs`: full view;
- anyone else who reaches the endpoint with `mikrotik.read`: reduced view
  (number, title, status, creation time, device name and company) — no
  commands, no people, no timeline;
- a staff member with none of the Mikrotik rights who is not involved gets `404`
  on every `/mikrotik-changes/:id` route — view, decision, cancel and download —
  so the status code does not reveal whether the request exists or what state
  it is in.

End users never reach any of these routes (`isNotClient`).

## Request life cycle

Status values (`STATUS` in `changeSteps.js`):

| Status | Meaning | Final |
|---|---|---|
| `awaiting_requester` | the requester has to confirm (two-step request) or approve (single step, role `requester`) | no |
| `awaiting_responsible` | waiting for the responsible person | no |
| `queued` | approved; waiting for the apply worker | no |
| `applying` | claimed by the worker | no |
| `applied` | all commands are on the router | yes |
| `rolled_back` | safe-mode executor only: a command was refused, the device stopped answering, or the release was not confirmed, and the re-read of the router found none of the commands | yes |
| `not_applied` | nothing was changed on the router | yes |
| `rejected` | a person rejected it | yes |
| `expired` | nobody decided within 24 hours | yes |
| `cancelled` | withdrawn by the requester | yes |
| `needs_attention` | HD cannot vouch for what is on the router; a person must check | yes |

`queued` and `applying` share one label (`STATUS_LABELS`).

Transitions:

- proposal accepted → `awaiting_requester` or `awaiting_responsible`
  (whichever role is the first step);
- an approval: next step's status, or `queued` after the last step
  (`changeSteps.decide`); a rejection → `rejected`;
- the requester's `cancel` → `cancelled`;
- the sweep (`changeWorker.sweep`) → `expired` for open statuses past `expiresAt`
  (24 hours from creation); `queued` requests are not expired by this rule, but
  an approval older than 30 minutes is not applied (see «Apply worker»);
- the worker claims `queued` → `applying` and ends in `applied`, `rolled_back`,
  `not_applied` or `needs_attention`; it can also put `applying` back to
  `queued` while it waits (see «Apply worker»);
- the sweep sets `needs_attention` on a request stuck in `applying` for more
  than 10 minutes (`STALE_APPLYING_MS`) that no live worker call owns.

A `needs_attention` request is **never applied again**. Re-applying could
apply a command twice. The request keeps `failure` (what the re-read saw for
the commands), the per-command `result` and `backupArtifact`; the same data
is in the `get_mikrotik_change` output.

Every decision is conditional in the database on the previous status and on
the step still having no decision (`changeDecisions.mongoStore.applyPatch`), so
two simultaneous taps (portal and Telegram, or two admins) produce one
decision; the loser gets `closed` and no notification.

## What the agent sends and how it is accepted

Input of `propose_mikrotik_change`: `device` (id, or exact name / label / host /
serial), `requester`, `title` (≤ 200), `reason` (≤ 1000), `commands[]`,
optional `wireguardClient`. Every refusal returns reasons to the agent and
creates nothing.

Order of checks in `changeProposals.propose`: shape (including all of
`validateProposal`), then device and requester lookup, then the decision plan,
then — under an in-process lock per key and per device — limits, the live read
and reconciliation, limits again, and the write.

### Menus, fields and values (`changeRules.js`)

- **Command shape.** `action` in `add|set|remove|enable|disable`. `path` is
  normalised to `/word word …`; at most 6 words, each `[a-z0-9][a-z0-9-]*`.
  `where` (1-5 string pairs) is required for everything except `add` and is
  forbidden for `add`. `params` is 1-40 pairs for `add`/`set` and must be empty
  for `remove`/`enable`/`disable`. Field names match `[a-z0-9][a-z0-9.-]*` and are at most 64 characters (`MAX_NAME`);
  values are strings, no control characters, at most 500 characters. `where`
  is exact equality on row fields only (no sub-queries, no regular expressions).
- **Denied menus** (`DENIED_PATHS`): `/user`, `/system`, `/file`, `/tool`,
  `/import`, `/export`, `/certificate`, `/ip service`, `/ip ssh`, `/ppp secret`,
  `/ip hotspot user`, `/user-manager`, `/container`, `/snmp community`,
  `/radius`, `/password`, `/console`, `/port`, `/special-login`,
  `/tr069-client`, `/ip socks`, `/ip proxy`, `/ip cloud`, `/disk`,
  `/ip ipsec key`, `/ip tftp`, `/ip smb`, `/app`, `/partitions`, `/zerotier`.
  **Abbreviations are treated as the full name**: the console
  accepts unambiguous prefixes of menu words, so `underPath` matches when every
  word of the denied path *starts with* the corresponding word of the request
  path (`/sys`, `/ip ser`, `/us` are all refused). A path shorter than the
  denied one does not match. The API executor accepts only exact names, so this
  is defence in depth for what a person sees and for the display.
- **Script fields** (`isScriptField`, `SCRIPT_FIELDS` from `configRedact.js`:
  `source`, `on-event`, `on-up`, `on-down`, any `on-…`) are refused in `where`
  and `params`, including any name that is a prefix of a script field
  (`looksLikeScript`).
- **Secrets.** A secret field (`isSecretField(path, name)`, plus the extra list
  `SECRET_NAMES` and every prefix of those names, e.g. `private-k`) accepts
  **only a placeholder**. Seven real fields that are also prefixes of a secret
  name are exempt by exact name (`NOT_SECRET`: `user`, `auth`, `authentication`,
  `group`, `encryption`, `http-proxy`, `tls`; and the `PUBLIC_FIELDS` of
  `configRedact.js`). `where` never accepts placeholders.
- **Placeholders** (`PLACEHOLDERS`): `{{wireguard.public-key}}` (only in the
  field `public-key`) and `{{wireguard.preshared-key}}` (only in
  `preshared-key`). A `{{`/`}}` anywhere else is refused. Further, in
  `changeProposals`: placeholders are allowed only when `wireguardClient` is
  present, only in an `add` on `/interface wireguard peers` whose `interface`
  equals `wireguardClient.interface`, and in **one** command per request.
  `wireguardClient` requires such a peer with the public-key placeholder.
- **`wireguardClient` shape**: `interface` (interface-name pattern), `address`
  (IPv4 or IPv4/prefix), `allowedIps` (1-10 IPv4 or IPv4/prefix), `dns` (0-3
  IPv4), optional `endpoint` (`host:port`, IPv4 or hostname, port 1-65535).
- **Text.** `title` and `reason` are required, length-capped, refused when they
  contain control, line-break, invisible or bidirectional characters
  (`hasForbiddenChars`), and pass `maskText` before storage. They are shown as
  the agent's words.
- **Display strings.** `displayCommand` builds the RouterOS-style line the
  person approves. Values are quoted unless they are plain literals; inside
  `where` only strict literals (IPv4, integers, `yes|no|true|false`) stay bare,
  everything else is quoted, so a word is never read as an expression. The
  line is for reading only: nothing in HD types it into a console.

### Limits

- At most **5 open requests per device** (`MAX_OPEN`: counted over all
  non-final statuses, which includes `queued` and `applying`).
- At most **20 proposals per key per hour** (`MAX_PER_HOUR`: all requests
  created through the key in the last hour, whatever their status). Refused
  proposals do not count towards it (nothing is created for them).
- At most **60 attempts per key per hour** (`MAX_ATTEMPTS_PER_HOUR`), refused
  ones included: an attempt that passes the shape checks costs a login on the
  router. Counted in the memory of the backend process; the 61st attempt is
  refused before the device lookup and before any router read.
- Both are checked twice (before and after the router read) under the in-process
  locks `key:<keyId>` and `device:<deviceId>`, so parallel proposals cannot
  exceed them in one backend process.

### Reconciliation with the router

For each distinct menu the service reads `<menu>/print` over the API in one
session (`liveReadMenus`). A menu the router cannot read, or a failed session,
refuses the proposal (router text is returned as a quoted fragment). Then, per
command:

- `set`, `remove`, `enable`, `disable`: `where` must match **exactly one** row
  (equality after normalising `true/false` and `yes/no`); the row is stored in
  `command.before`, redacted (`redactRow`) and without dot-fields, and its `.id`
  in `command.rowId`, which the worker compares with the live row before
  applying (see «Apply worker»). Zero or several matches refuse the proposal.
- A `set`, `enable` or `disable` that would change nothing (the row already has
  the values; `disabled` already as requested) is refused
  (`command N changes nothing`): such a command would read as «present» in the
  post-apply check and turn a clean rollback into `needs_attention`.
- Unknown field names in `where`/`params` (not present in any row of the menu
  when the menu has rows) are refused, except the optional fields `comment`,
  `disabled`, `timeout`, `place-before`, `copy-from` and placeholder values.
- `add` on a menu with a uniqueness key (`UNIQUE_KEYS`:
  `/ip firewall address-list` list+address, `/ip dns static` name+address,
  `/ip dhcp-server lease` address, `/interface wireguard peers` public-key) is
  refused when such a row already exists; two such `add`s of the same entry in
  one request, and two commands that target the same row, are refused.
- Firewall risk is recomputed from the real row (see below).

### Risk marking

Not a prohibition: a warning in the request and in the messages. A command is
«may cut off the device» (`risk: "high"`) when it touches `/ip address`,
`/ip route`, `/ip firewall nat`, `/interface bridge`, `/interface vlan`,
`/routing`, `/ip dhcp-client`, `/interface list`, `/ipv6 address`,
`/ipv6 route`, `set|remove|disable` on `/interface` itself, or
`/ip firewall filter|raw` and `/ipv6 firewall filter|raw` that involve the
`input` chain (`firewallInput`). For `add` that is `chain=input` in `params`.
For every other action it is high unless `where.chain` is a plain value other
than `input`, and once the row is read it is recomputed from the stored row's
`chain` (and from a `params.chain` of `input` or starting with `!`). The request
risk is `high` when any command is.

## How commands are executed

**Status of the safe-mode behaviour.** That safe mode held by an SSH shell also
undoes changes made through a separate API session was confirmed on a live
router on 2026-10-11 (`scripts/spikeSafeMode.js` on `F1-VLD-GW01`, RouterOS
7.23.7: `SAFE MODE: api rollback=ok keep=ok`): an entry added through the API
while the shell held safe mode disappeared when the shell was dropped, and
stayed after a normal release. It is not confirmed on RouterOS 6 (see «Known
limits»). HD does not rely on it blindly either: after any uncertain executor
outcome the worker decides the status by re-reading the router (see «Apply
worker»), so a router that does not roll back surfaces as `needs_attention`,
never as a false `rolled_back`.

`changeExecutor.js` is the only feature code that writes to a router. The
worker hands it `items[{ words }]` — API sentences built by `apiWords`:
`/menu/path/action`, `=.id=<*id>` for everything except `add`, and `=name=value`
pairs. `where` never reaches the router; HD resolves it to the row `.id`.

**Mode `safe-mode` (default).** RouterOS safe mode lives only in an interactive
console. HD opens one SSH shell (login suffix `+ct200w`, `shellLogin`; no
colours, 200 columns) whose only job is to **hold** safe mode, and sends the
writes through a *separate* API session:

1. Wait for the prompt, send Ctrl+X, expect `[Safe Mode taken]`/`<SAFE>`
   (`classifyCtrlX`). If the console asks the hijack question (`[u/r/d]`),
   another administrator holds safe mode: HD answers `d` and stops — failure
   `safe mode is held by another session`, nothing was changed. Anything else
   unrecognised: `could not confirm safe mode`.
2. Send the sentences one by one over the API session. The shell is checked
   before every write: if it died, or the buffered console output shows safe
   mode was released/taken over (`lostSafeMode`), writing stops.
3. A command failure, timeout or lost shell: the shell is **dropped without
   releasing** safe mode (by design, the router then undoes what was made
   since Ctrl+X).
4. All commands passed: a fresh API connection probes the router
   (`/system/identity/print`). No answer: the shell is dropped, again without
   releasing.
5. Answer received: Ctrl+X again; `[Safe Mode released]` confirms the release.
   An unconfirmed release or a hijack question at this point is reported as
   such and the worker re-reads the router to decide.

Only Ctrl+X (`\x18`) and the single letter `d` are ever written into the
console. HD never types anything derived from the agent's text. The reasoning:
the console accepts abbreviated menu and field names and needs quoting; the API
requires exact names and answers errors with `!trap`.

Side effect of the design: safe mode is router-wide, so while HD holds it
(seconds to a minute) a concurrent change made by another administrator is
subject to the same undo if HD's session drops.

**Mode `api`** (`MIKROTIK_CHANGE_EXECUTOR=api`): the same API writes, no safe
mode and no rollback. The first failed command stops the set; what was applied
stays. After the set a probe checks connectivity. Intended only as a fallback
if safe mode turns out not to cover changes made from an API session. The
texts that promise an automatic rollback follow the mode (see «Notifications»).

**Settings** (environment of the backend):

- `MIKROTIK_CHANGE_EXECUTOR` — `safe-mode` (default) or `api`. Read only by
  `executorMode` (`changeExecutorMode.js`; trimmed, case-insensitive; empty
  means `safe-mode`). An unknown value does not stop the worker: it runs as
  `safe-mode`. The error line («Mikrotik change worker: unknown
  MIKROTIK_CHANGE_EXECUTOR value, falling back to safe-mode …») is written
  when the worker is assembled — at the first scheduled tick after start-up
  (within about 15 seconds, provided MongoDB is connected and the Mikrotik
  module is on), once per distinct value per process. With the module off the
  worker is not assembled and the line does not appear. The portal's `rollback`
  flag and the confirmation texts call the same function without a logger, so
  they silently show `safe-mode` and cannot reveal a typo. The executor object
  itself is still built lazily at the first apply (`lazyExecutor`); the sweep
  does not need it. The mode actually used is stored in the
  request's `executor` field.
- `MIKROTIK_CHANGE_KEEPALIVE` — `1` turns on SSH keepalive on the hold
  connection (every 5 s, give up after 2 missed). **Off by default**: it is not
  verified that RouterOS answers the keepalive requests; without answers a
  healthy hold would die after about 15 s and the router would roll the change
  back. With keepalive off, the death of the hold is noticed from the stream and
  connection events only.

**Limits** (`DEFAULT_LIMITS`): 15 s per command, 120 s for the whole run, 10 s
to wait for a console reply, 5 s settle pause before the post-failure probe.
A command that times out may still be executed later; the worker's re-read
covers this.

**Failure paths** (`FAILURES`, the executor's `failure` text) and what each
means for the worker:

| Failure | Meaning | Outcome |
|---|---|---|
| `safe mode is held by another session` | hijack question on entry; nothing changed | `not_applied` |
| `could not confirm safe mode`, `timed out; could not confirm safe mode`, `safe mode was taken over by another session` (on entry) | never entered, nothing sent | `not_applied` |
| `could not open a console session…` / `could not open the API session…` | connection failed before any command | `not_applied` |
| `timed out before any command was sent`, `the safe mode session was lost before any command was sent` | nothing sent | `not_applied` |
| any other failure with every command `skipped` and no rollback (e.g. `unexpected error while applying…` before the first command) | nothing sent — a sent command is never reported `skipped` | `not_applied` («Применение не началось из-за внутренней ошибки — изменения не вносились»), no re-read |
| `The device is being upgraded` | upgrade guard | request waits, then `not_applied` after 30 min |
| `command N failed …` where the router refused the command (`!trap`, stored as `refused`) | the shell was dropped without release | re-read: no command present -> `rolled_back` (safe mode) / `not_applied` (API mode, when nothing was done); otherwise `needs_attention` |
| `command N timed out …`, a sent command that was not confirmed (`not confirmed`), a lost API session | the command may still run later | always `needs_attention` (a command that is not definitively refused is never counted as «did not run») |
| `the device stopped answering after the change` / `timed out while checking the device…` / `the safe mode session was lost` | the executor reports the commands as `rolled_back` (not `done`) and the shell was dropped without release | re-read: none present -> `rolled_back`; anything else, **including all present**, -> `needs_attention` (the executor's own report contradicts the router, so HD does not call it `applied`) |
| `safe mode was taken over by another session; applied commands may remain` / `…before release…` | another admin took safe mode: HD cannot vouch | `needs_attention` |
| `release of safe mode was not confirmed…` | all commands passed, release unconfirmed | re-read: all commands present -> `applied`; none present -> `rolled_back` (safe mode); anything else -> `needs_attention` |
| `unexpected error while applying…` | bug or unforeseen error; command states depend on the phase | the same re-read rules: `applied` only if the executor had reported every command `done`, none present -> `rolled_back` (safe mode) unless a command was not definitively refused, otherwise `needs_attention`; unreadable router -> `needs_attention` |

Result states per command: `pending`, `done`, `failed`, `rolled_back`,
`skipped`. In API mode a sentence that was sent but not confirmed is `failed`
(`not confirmed`), never `skipped`, because it may have been applied.

## The apply worker (`changeWorker.js`)

**Scheduling** (`app.js`, registered with `jobs.register`, both with
`quietSkip: true`):

- `Mikrotik change worker`: `*/15 * * * * *` (every 15 s), deadline 15 minutes,
  calls `runChangeTick` — one request per tick;
- `Mikrotik change sweep`: `1-56/5 * * * *` (minutes 1, 6, 11 … 56), deadline
  120 s, calls `runChangeSweep`.

Both do nothing while MongoDB is not connected or the Mikrotik module switch
(`mikrotikEnabled`) is off.

**Queue.** `tick` lists up to 50 `queued` requests oldest first
(`createdAt`), and for each: **ends it as `not_applied` without claiming it
when the last approving decision is more than 30 minutes old** (`GIVE_UP_MS`;
failure «Утверждение устарело…», or the wait reason when the request had been
waiting; the executor and the router are not touched, `notifier.result` is
called) — an approval is valid for 30 minutes because an `add` has no drift
protection after a long standstill; skips it if a retry was scheduled in the
future;
loads the device; defers it if the device or its transit router is upgrading,
or another request of the device is `applying`, or its lane is busy; then
**claims** it with one conditional update (`queued` → `applying`, sets
`applyingSince`). Only the claim winner proceeds. `tick` returns after the
first request it handled to a final outcome; requests that had to wait do not
block the ones behind them in the same tick.

**Serialisation and the single-process assumption.** A *lane* is the transit
router if the device has one, otherwise the device itself: two changes for one
device, or for two devices behind one transit router, never run together. The
lane set (`busyLanes`) is in process memory, together with the retry-time map.
Safety across processes comes only from the atomic claim; the lane rule holds
for **one backend process** (as deployed). Running several backend processes
needs a database-backed lane lock. The in-process proposal locks have the same
assumption.

**Apply steps** (`apply`):

1. Read all menus used by the commands (and `/interface wireguard` when a
   WireGuard client is requested). A transient error (upgrade, busy, link
   down) waits; a permanent one (credentials, forbidden address) ends in
   `not_applied`.
2. **Drift check.** Each non-`add` command's row is looked up again by `where`
   (must still be exactly one). Its `.id` must equal the stored `rowId`
   («строка заменена другой с момента запроса» otherwise: the people approved
   another row), and the row is compared with `command.before` (both redacted,
   dot-fields removed). Any difference ends in `not_applied` with the name of
   the first changed field. Rules of the comparison (`changeMatch.js`):
   runtime and statistics fields are ignored — counters, timestamps, link state,
   values handed out to clients — and the set of ignored fields is **per menu**;
   a menu without its own entry is compared almost exactly (only names that
   are unambiguous everywhere are ignored), so unusual menus refuse safely on
   any difference; for `set`, the fields the command itself changes are compared
   exactly first (even a normally ignored runtime field) and then the whole
   rest of the row as for the other actions; a `timeout` on a firewall address-list entry is
   configuration that also counts down, so the fresh value may only be
   **smaller** than the stored one (parsed RouterOS duration), and growth, a
   missing or unparsable value counts as drift. The same helpers are used when
   a proposal is accepted.
3. WireGuard server data: the server public key and `listen-port` are read from
   the router's interface row; the endpoint is `wireguardClient.endpoint` or
   `<device host>:<listen-port>`.
4. **Keys.** Generated now, not at proposal time (see «WireGuard client
   configuration»), and encrypted at once, so a broken `APP_ENC_KEY` shows up
   before the router is touched (`not_applied`).
5. Build the API sentences (`apiWords`); a failure here is `not_applied`.
   **Account policies.** Before the backup the worker reads `/user` and
   `/user group` over the API (`readRights`) and `assessChangeRights` checks
   that the group of the managed account (`credentials.user`) holds
   `REQUIRED_CHANGE_POLICIES`: `api`, `read`, `write`, `ssh` (a policy written
   `!name` counts as missing). Missing policies end in `not_applied` naming
   them, before anything is backed up or sent. If no verdict can be reached —
   the lists are not returned (RouterOS answers `/user` only to an account
   holding `policy`, so the read can wait out its timeout), the account or its
   group is not in them, or the read fails permanently — the worker logs
   `rights check skipped` (the read failed) or `rights check gave no verdict`
   (the read answered but the account or group could not be assessed) and goes
   on; the router then refuses a write itself.
   A transient read failure (upgrade, busy, link down) waits like step 1. The
   check costs one more API session per apply. The executor object is built
   (`executor.prepare`) right after this, so a broken executor setup is
   `not_applied`, not «state unknown».
6. **Backup.** `createArtifact(record, { trigger: "pre-change", userId })`
   (`userId` = the last approver). A request that goes back to the queue and
   returns reuses its backup for at most 10 minutes (`BACKUP_MAX_AGE_MS`) and
   only if no other request of the device reached `applied`, `rolled_back` or
   `needs_attention` since. No backup: `not_applied`; the executor is not called.
7. Executor call. From here the router may have changed; a crash after this
   point is `needs_attention`, before it `not_applied`.
8. **Outcome from the router, not from the executor's words.** If the console
   confirmed the release and the probe answered, the request is `applied`.
   Otherwise the worker re-reads the same menus (3 attempts, 3 s apart) and
   classifies every command as `present`, `absent` or `unknown` (`observe`):
   - all present, every command reported `done` by the executor, and safe mode was not taken
     over → `applied`;
   - all absent, no sent command left unanswered — a command that failed by
     timeout, a lost API session or «not confirmed» may still run, only a
     router refusal counts as «did not run» — and no takeover: `rolled_back` in safe-mode (`not_applied` in
     API mode when the first command was refused and nothing ran);
   - anything else — a mix, unclear rows, takeover by another administrator, an
     unconfirmed release with a partial picture, API-mode partial apply, an
     unreadable router → `needs_attention`, with what the check saw.

**Waiting and giving up.** When nothing was sent and the cause may pass
(device busy, upgrading, unreachable), the request stays `queued`, a single
timeline note per reason is added, and it is tried again no sooner than a
minute later (in-memory). `queuedSince` is the time of the last approving
decision; 30 minutes after it (`GIVE_UP_MS`) the request ends as `not_applied`
(with the wait reason, if there was one).

**Stale-apply sweep.** An `applying` request older than 10 minutes that is not
being processed by this process becomes `needs_attention` («Применение было
прервано; состояние устройства неизвестно»). It is never retried.

**Expiry and reminders** (sweep): open requests past `expiresAt` become
`expired` and the notifier is called. Open requests expiring within 2 hours
and not yet reminded (`remindedAt`) are marked reminded atomically and the
current step's person is notified.

**Key purge** (sweep): `purgeKeys` unsets `wireguard.privateKey` and
`wireguard.presharedKey` where `wireguard.keysExpireAt` has passed.

## WireGuard client configuration

- **Who generates.** HD, in the worker, after the drift check and before the
  executor: an X25519 pair (`generateKeyPair`, Node `crypto`) and, when the
  request uses `{{wireguard.preshared-key}}`, a random 32-byte preshared key.
  The agent sees neither. The public key goes into the peer command; the
  preshared key into the peer and the client file.
- **Where they live.** Private and preshared keys are stored encrypted with
  `encryptSecret` (AES-256-GCM, `services/crypto/secretBox`) in
  `wireguard.privateKey` / `wireguard.presharedKey`, both `select: false` in the
  model. They are written **only** when the request ends `applied`, together
  with `publicKey`, `serverPublicKey`, `endpoint` and `keysExpireAt`. In every
  other outcome no key is stored; for `needs_attention` and `rolled_back` the
  failure text also says that the configuration was not saved and that a peer
  left on the device has to be removed by hand. The keys exist in memory during the apply and are scrubbed
  from any text the worker writes (`scrub`, by key prefix).
- **How long.** `keysExpireAt` = time of `applied` + 24 hours. The sweep erases
  both secrets afterwards; the public data stays.
- **Who can download.** `GET /mikrotik-changes/:id/wireguard.conf` for the
  requester and for people who recorded a decision on the request (`isRecipient`),
  signed in to HD, only while the status is `applied` and the keys exist.
  Refusals: `403` not a recipient, `409` not applied, `404` request without a
  client configuration, `410` keys expired. The file is generated at request
  time from the decrypted secrets (`buildClientConfig`: `[Interface]` with
  `PrivateKey`, `Address`, `DNS`; `[Peer]` with server `PublicKey`, optional
  `PresharedKey`, `AllowedIPs`, `Endpoint`, `PersistentKeepalive = 25`), sent
  with `Cache-Control: no-store` as `attachment`. The file name derives from the
  peer's `comment` (characters `[A-Za-z0-9._-]` only) or `wg-<number>`.
- **What is logged.** Every download adds a timeline entry (`download`) with the
  person's name; showing the QR code (`?via=qr`) adds a `qr` entry, at most one
  per person per 10 minutes, while the file is still returned every time. If the
  entry cannot be written the file is not sent. The key material, the file and
  decrypted values are never logged; on an error only the message and the
  request number are.
- The agent gets only the page link (`get_mikrotik_change`), which opens
  nothing without a sign-in.

## Notifications

Category `mikrotikChange` (one key for both kinds of events, see
`docs/notifications.md`). Events and recipients (`createChangeNotifier`):

| Event | Method | Called by | Recipients |
|---|---|---|---|
| New request | `step` | the MCP tool `propose_mikrotik_change` right after the request is created (`notifier` injected in `routes/mcp.js`) | the person whose step is current |
| Requester confirmed | `step` | `changeDecisions.decide` | the responsible person |
| Rejected | `decided` | `changeDecisions.decide` | requester and everyone who decided |
| Applied, rolled back, not applied, needs attention | `result` | the worker | requester and everyone who decided |
| Expiring in 2 hours | `reminder` | the sweep | the person whose step is current (text prefixed «Запрос истекает через 2 часа») |
| Expired | `expired` | the sweep | requester and the person whose step was waiting |
| Cancelled | `cancelled` | `changeDecisions.cancel` | the person whose step was waiting (nobody if that is the requester) |

A notifier failure never undoes the thing it reports: after a proposal the tool
logs `MCP: Mikrotik change notification failed` (request number and error text)
and still answers with the created request.

Channels:

- **In-app (bell)** — always delivered: `pushInApp({ …, force: true })` skips
  the category switches (global and personal). Service accounts, banned users
  and duplicate recipients are still dropped. A bell failure does not block the
  other channels.
- **Telegram** — queued in the `Notification` collection (`instrument:
  "telegram"`) for the existing outbox. Sent only when Telegram notifications
  are active in the preferences, the category is on in
  `Preferences.notify.personal.mikrotikChange`, the user has an active linked
  chat and has not switched `notify.byTelegram.mikrotikChange` off.
  Step messages carry inline buttons; result messages carry a link button only.
  The outbox sends with `parse_mode` HTML, so the text is **HTML-escaped**
  (`escapeHtml`) when queued; the in-app text stays plain. The link button is
  added only for an `https` base URL that is not localhost (Telegram rejects
  the whole message otherwise).
- **E-mail** — queued the same way, same preference checks (`byEmail`). The
  body is **HTML**: the message text is escaped (`escapeHtml`), line breaks
  become `<br>`, and the link is a real `<a href>` built from the base URL and
  the fixed path, never from message text.

Texts built by HD contain only stored, HD-written command lines (`command.text`).
Text written by others (title, agent name, router errors, reject comments) is
collapsed to one line and capped before it is put into a message, so it cannot
forge extra lines.

**When a Telegram step message carries decision buttons** (`stepMessage` returns
`fits: true`): every command is shown whole. That requires, for each command,
a display line of at most `COMMAND_MAX` (600) characters (the stored text is
shown as is — spaces inside values are not collapsed) and, for a `set`, no
«было» field name or value longer than `WAS_MAX` (120) characters, plus a total
of at most 3500 characters after escaping (`MAX_LENGTH`). Nothing is cut under
decision buttons. Otherwise the message lists only the whole leading commands
that fit, says how many more there are, and has **no decision buttons**, only
the link button; `confirmFull` is `null`, and an approval from Telegram is
refused with `too_long` (on the backend as well). The confirmation text must
also fit the hard cap of 4000 characters (`HARD_LIMIT`). Long values can
therefore be approved only on the portal.

**Rollback wording follows the executor mode.** The confirmation text and the
high-risk note promise an automatic rollback (`ROLLBACK_NOTE`) only when
`rollbackAvailable()` (`changeExecutorMode.js`) is true, i.e. mode `safe-mode`;
in mode `api` they carry `NO_ROLLBACK_NOTE`. The portal view has a boolean
`rollback` with the same value. `ROLLED_BACK_NOTE` is used for `rolled_back`
results, which only the safe-mode executor produces.

**Result texts.** Every final status has a title and a summary
(`RESULT_TITLES`, `resultFacts`). For `needs_attention` the title is
«Запрос на изменение конфигурации требует проверки», the summary says HD cannot vouch for the state
of the device, followed by `Что известно: <failure>`, the approvers and the
backup time. In `rolled_back` and `not_applied` messages `failure` is HD's own
sentence and is printed as `Причина: <failure>`, so its beginning cannot pass
for one of the message's own lines; the
label «Роутер ответил:» is used only for a command the router refused
(`result.refused`), otherwise the command's error is labelled «Не подтверждена:».

The link points to `/devices/mikrotik/changes/<id>` on `APP_PUBLIC_URL`
(`VITE_API_ADDRESS` as a fallback in the notifier). The MCP tools build the
same link from `ADDRESS` (which `compose` sets from `APP_PUBLIC_URL`).

## Telegram decision flow

Messages and buttons come from `changeNotifications.js`; taps are handled by
`tg-service/src/bot/mikrotikChange.ts` and the backend routes in
`controllers/inventory/mikrotikChangeBot.js`.

Callback data: `mc:<action>:<24-hex id>`, enforced by `/^mc:([abyr]):([0-9a-f]{24})$/`.

| Data | Effect |
|---|---|
| `mc:a` | replaces the message with the confirmation text and the full command list (only when the commands are shown whole, see above) |
| `mc:y` | records the approval |
| `mc:b` | restores the original message |
| `mc:r` | records the rejection at once (no confirmation step, no comment) |

Backend routes (under `/api/bot`, behind the limiter, `attachTelegramActor`,
`mikrotikIsActive`, `isNotClient`): `GET /mikrotik-changes/:id/message` and
`POST /mikrotik-changes/:id/decision`. A separate per-actor rate limit applies
(30 taps per minute per `x-tg-actor`) before the shared bot limiter.

**Enforced by the backend at tap time** (portal-grade checks, repeated
atomically in `changeDecisions`): the actor is the person of the current step;
the request is not closed or expired; the person holds `approveChanges` where
the step needs it (read from the session of the Telegram actor); every command
is shown whole (`too_long` otherwise); the decision is recorded once.
Refusals are HTTP 200 with `{ ok: false, code, message }`.

**Enforced only by the bot**: the two-tap approval (the backend honours
`approve` whatever screen the person saw; `mc:y` exists only on the
confirmation keyboard), and that a decision is made only in a private chat
(`ctx.chat.type === "private"`). The backend still checks identity and
current step, so a forwarded button is useless to anyone else.

**Stale buttons.** A decision made on the portal does not edit existing
Telegram messages (the outbox cannot edit them). On the next tap the backend
answers `closed`, `expired`, `already_yours` or `not_found` and the bot
replaces the message with that reason (`replaceWithReason`), removing the
buttons. `already_yours` tells the person what they already decided and the
state now. If the answer to a decision was lost (network, 5xx), the bot says so
and keeps the buttons; pressing again is safe because the backend then answers
that the step is already decided. Someone who has no step in the request
always gets `not_yours`, whatever the request's state: the bot does not tell
an outsider whether it is closed or expired (`gate` in
`mikrotikChangeBot.js`).

## Data model

`MikrotikChange` (`models/mikrotikChange.js`, collection `mikrotikchanges`):

- `number` — unique, sequence `Counter` `_id: "mikrotikChange"`
  (`nextMikrotikChangeNumber`), shared `models/counter.js`;
- `mikrotik` (device record), `title`, `reason`, `requestedBy` (User),
  `requestedVia { keyId, keyName }`, `responsible` (User snapshot);
- `commands[]` — `path`, `action`, `where`, `params`, `text` (display line),
  `risk`, `riskReason`, `before` (redacted row), `rowId` (the row's `.id` at
  proposal time, compared at apply time), `result { state, error, at, refused }`
  (`refused: true` only when the router answered the command with a refusal);
- `risk`, `status`, `expiresAt`, `remindedAt`, `applyingSince`, `queuedSince`,
  `failure`, `executor` (`safe-mode` or `api`, what actually ran),
  `backupArtifact` (→ `MikrotikArtifact`, trigger `pre-change`);
- `steps[]` — `role` (`requester` or `responsible`), `user`, `decision`
  (`approve`/`reject`/null), `channel` (`portal`/`telegram`), `comment`,
  `decidedAt`;
- `wireguard` — `publicKey`, `privateKey` and `presharedKey` (encrypted,
  `select: false`), `client {interface, address, allowedIps, dns, endpoint}`,
  `serverPublicKey`, `endpoint`, `keysExpireAt`;
- `timeline[]` — `at`, `kind`, `user`, `text`; kinds used: `proposed`,
  `decision`, `cancelled`, `wait`, `backup`, `result`, `expired`, `reminder`,
  `download`, `qr`.

Indexes: `{ mikrotik, createdAt }`, `{ status, expiresAt }`,
`{ "steps.user", status }`, unique `number`. Writes are plugged into the pulse
(`services/pulsePlugin`, topic `mikrotikChanges`; reminder marks do not count
as changes).

Related: `Mikrotik.responsibleId`; `MikrotikArtifact.trigger` accepts
`pre-change`; `McpKey.scopes` accepts `mikrotikChanges`;
`Preferences.notify.personal.mikrotikChange` and `User.notify.{byTelegram,
byEmail, inApp}.mikrotikChange`.

The portal view (`changeView`, a whitelist) never returns `where`, `params`,
the private or preshared key, or contact details of people. For WireGuard it
returns the file name, `publicKey`, `serverPublicKey`, `endpoint`,
`keysExpireAt` and the client settings, and a boolean `rollback` (whether the
current executor mode gives an automatic rollback).

## Security model

| Threat | How it is addressed |
|---|---|
| **Prompt-injected agent** (text read from a device, a ticket or a note convinces it to propose something) | The agent can only propose. A person sees the exact structured commands (`command.text`, `before → after` for `set`) and approves; a request with any command that cannot be shown whole in a Telegram message cannot be approved there. Menus that give control of the router (users, system, files, scripts, services, certificates and others) are refused; scripts and secrets cannot be passed; the `INSTRUCTIONS` the MCP server sends tell the agent that device text is data. Everything dangerous but legitimate is flagged `high`. |
| **Spoofed requester** (the agent names someone else) | It only changes who receives the request. Nothing is applied until a person who is signed in (or is in their private Telegram chat) approves; where there is no responsible person, only someone holding `approveChanges` can approve; a named employee without a linked Telegram is refused. |
| **Lock-out of the router** | Design: safe mode held by a separate SSH session during the whole write phase and a probe over a fresh connection before release, with the hold dropped (not released) on any doubt so that the router undoes the change; this relies on the unconfirmed assumption described in «How commands are executed». Independent of it: risky menus are flagged, the outcome is decided by re-reading the router, and a backup is taken first (restoring is manual and outside HD). |
| **Secrets** | The agent cannot send a secret (placeholders only; abbreviations of secret field names are refused too). Keys are generated in the worker, encrypted at rest, stored only for an applied request, for 24 hours, erased by the sweep, downloadable only by the requester and deciders, every read logged; never put in logs, MCP answers, notifications or timeline text. Router error text goes through `scrub` and a length cap. |
| **Concurrent administrators** | Row drift between proposal and apply (a changed row, or another row under the same `where`) refuses the request; an approval older than 30 minutes is not applied; a hijacked safe mode is detected and reported as `needs_attention` (HD answers `d` to the hijack question, never takes another administrator's safe mode over). |
| **Double apply** | Decisions and the worker claim are single conditional updates. A request stuck in `applying` is moved to `needs_attention` and never retried. A request is never re-applied after the executor was called. |
| **Tampering with the display** | Agent text must be free of control, line-break, invisible and bidirectional characters; values are quoted in the display line; agent-supplied echoes in messages are single-lined. |

## Known limits and what was not verified live

- **Safe mode is verified on one router and one version only.** The probe
  `scripts/spikeSafeMode.js` ran on `F1-VLD-GW01` (RouterOS 7.23.7, direct
  connection) on 2026-10-11 with `rollback=ok keep=ok`. Not verified: RouterOS
  6, a device reached through a transit router, and a real link loss (the probe
  closes the session cleanly; on a silent loss the router rolls back only after
  its own session timeout). If a device behaves differently, the re-read
  reports `needs_attention`; `MIKROTIK_CHANGE_EXECUTOR=api` switches the whole
  installation to the mode without rollback.
- **Console texts.** Entering («Taking Safe Mode session... Success!», prompt
  `<SAFE>`), releasing («Releasing Safe Mode... Success!», then «Safe Mode
  released»), the prompt and the `+ct200w` login suffix are verified on
  RouterOS 7.23.7 and pinned as fixtures in `safeModeConsole.test.js`. The
  RouterOS 6 wording («[Safe Mode taken]») and the question asked when another
  session already holds safe mode (`HIJACK`) still come from documentation. An
  unrecognised reply is never treated as success: nothing is sent, the request
  ends `not_applied`.
- **Keepalive** on the hold connection is unverified and off by default.
- The Mongo wiring (`mongoStore` objects, `liveReadMenus`, `readRights`,
  `lazyExecutor`, `liveExecutor`, `mongoNotifier`, the bot route wiring in
  `routes/bot.js`) is covered by syntax checks and by unit tests on fakes; the
  cross-module path (propose -> approve -> apply with an in-memory store) is
  covered by `changeFlow.test.js`. The end-to-end run on the real router
  (propose -> approve -> apply -> config download, rejection, expiry, command
  failure) is still to be done.
- The account-policy check (`api`, `read`, `write`, `ssh`) is not verified
  against a live router. When `/user` or `/user group` cannot be read (the
  account lacks `policy`) there is no verdict and the apply goes on; the read
  may wait out its timeout (about 8 s) first.
- Long values (a command line over 600 characters, a «было» value over 120)
  can be approved on the portal only.
- Single backend process assumed (lanes, proposal locks, retry timers).
- A request cannot be restored from its backup in HD; a `needs_attention`
  request needs a person on the router.
- A request still `applying` when the backend process stops stays `applying`
  until the sweep, which moves it to `needs_attention` once it is 10 minutes
  old.
- A user holding `mikrotik.manage` and `mikrotik.approveChanges` can clear a
  device's responsible person and then approve alone (by design; the change of
  responsible is audit-logged).
- Only IPv4 for the WireGuard client; IPv6 is accepted in risk marking only.

## Operations

**One-off grant.** Adding `approveChanges` to the dictionary breaks «full
access» for existing administrator roles (`isFullAccess` needs every staff
action, and `isAdmin` mirrors it). Migration `2026-10-10-grantApproveChanges`
(`scripts/grantApproveChanges.js`, listed in `scripts/migrate.js` after
`2026-10-01-grantUpgradeFirmware`) adds the action to roles that lack exactly
that one action, then recomputes the mirror for holders of all full-access staff
roles. Run with the application stopped, as `deploy.sh` does for migrations.
By hand: `node scripts/grantApproveChanges.js` (shows), `… --apply` (writes);
then `./deploy.sh migrate mark 2026-10-10-grantApproveChanges`. New
installations get the right from `scripts/roles.catalogue.json`.

**Live probe.** `scripts/spikeSafeMode.js` answers one question: does a safe
mode held by an SSH shell undo changes made by a separate API session, and does
a normal release keep them. It writes only entries of the address list
`hd-probe` and types nothing into the console but Ctrl+X and `d`. Run it while
nobody else configures the router (safe mode is router-wide), from a terminal
that will not drop (tmux/screen), inside the backend container (as
`docs/deployment.md` does for scripts: `docker compose run --rm backend node
scripts/<name>.js …`). `<recordId>` is the `_id` of the `Mikrotik` record — the
id in `/mikrotik-devices/records/:recordId` and the `id` that
`list_mikrotik_devices` returns. Dry run first (opens no connection, prints the
plan and a self-check of the console patterns), then the real run:

```
docker compose run --rm backend node scripts/spikeSafeMode.js <recordId>
docker compose run --rm backend node scripts/spikeSafeMode.js <recordId> --apply
```

The script refuses to start (router untouched) if the list `hd-probe` is not
empty, cleans up its own entries and re-checks after 30 s. Read the last line,
`SAFE MODE: api rollback=<R> keep=<K>`; it is printed on every exit after
`--apply`. Exit code 0 means only that the pre-check passed and the list is
empty after clean-up. A few minutes after any run check on the router:
`/ip firewall address-list print where list=hd-probe`.

Values of `rollback` (an entry added through the API while the shell holds safe
mode, then the shell dropped without release):

| Value | Meaning |
|---|---|
| `ok` | the entry disappeared: the router undid the API-session write |
| `FAILED` | the entry stayed after the drop |
| `BUSY` | another session holds safe mode; the script answered `d` and stopped |
| `UNKNOWN` | no safe-mode confirmation, or the entry count could not be read |
| `NOADD` | the entry was not visible while safe mode was held (the add did not happen) |
| `NOT RUN` | the script stopped before this phase |

Values of `keep` (the same write, then a normal Ctrl+X release, then the shell
dropped; only run when `rollback=ok`):

| Value | Meaning |
|---|---|
| `ok` | release confirmed by the console and the entry stayed |
| `ok?` | the entry stayed, but the console text of the release was not recognised (`RELEASED` pattern needs a correction) |
| `FAILED` | release confirmed, but the entry is gone |
| `UNKNOWN` | no verdict (unreadable count, release not performed, foreign safe-mode text) |
| `BUSY` | another session holds safe mode |
| `NOADD` | the entry was not visible while safe mode was held |
| `SKIPPED` | `rollback` was not `ok`, so the phase was not run |
| `NOT RUN` | the script stopped earlier |

What to do with the result:

- `rollback=ok keep=ok` — the safe-mode design works as assumed. Keep
  `MIKROTIK_CHANGE_EXECUTOR` unset or `safe-mode`.
- `rollback=ok keep=ok?` — works; correct the console patterns (`RELEASED`,
  `TAKEN`) in `safeModeConsole.js` from the raw text the script printed, or the
  worker will report `needs_attention` for applies whose release it cannot
  confirm. Executor choice unchanged.
- `rollback=FAILED` — safe mode does not cover API-session writes. Set
  `MIKROTIK_CHANGE_EXECUTOR=api`: there is then no automatic rollback and the
  texts say so.
- `keep=FAILED` — a normal release loses the change; neither mode is usable
  until investigated.
- `UNKNOWN`, `NOADD`, `BUSY`, `NOT RUN`, `SKIPPED` (in either column) — no verdict; fix the cause
  (another administrator in safe mode, an unrecognised console text, an
  unreachable router) and run again. Do not switch modes on these.

**Settings.** `MIKROTIK_CHANGE_EXECUTOR` and `MIKROTIK_CHANGE_KEEPALIVE` go in
`.env`. A container reads `.env` only when it is created, so after editing run
`docker compose up -d --force-recreate backend` (as in `docs/deployment.md`:
changes need a recreate). To confirm the mode **right after a restart**
(the error line for a typo appears only at the worker's first tick, and not at
all while the Mikrotik module is off), read the environment of the running backend
container: `docker compose exec backend printenv MIKROTIK_CHANGE_EXECUTOR`.
No output, or an empty or blank value, means `safe-mode` and is not a typo;
any other value than `safe-mode` or `api` (ignoring case and surrounding
spaces) is a typo and behaves as `safe-mode`.
After applies have run, a request that reached the executor stores the mode
that ran in its `executor` field; the portal view's `rollback` flag is only a
consequence of the same function and does not show typos. The managed account on the router needs the
policies `api`, `read`, `write`, `ssh` (see «Apply steps»).

**Logs** (`./deploy.sh logs backend`): lines starting `Mikrotik change worker:`
(`cannot start: …`, `read failed for good`, `executor: …` with mode,
`rolledBack` and `reachable` — written when the executor reports a failure,
`rights check skipped`, `approval went stale`, `verification read n/3 failed`,
`unexpected error`, `final status … not written`, the unknown-executor error),
`Mikrotik change notification:`, `Mikrotik change:`,
`MCP: Mikrotik change notification failed`, and `MCP tool call` for the agent's
calls. Job names in the jobs registry: `Mikrotik change worker`,
`Mikrotik change sweep`.

**A request in `needs_attention`.** Data and tools, in order:

1. Read the request: `get_mikrotik_change` (MCP) or the portal view show the
   per-command `result` (`done`, `failed` with `refused` or not, `rolled_back`,
   `skipped`), the `Note from HD` / `failure` text with what the re-read saw
   («на месте команды …; нет команд …; неясно по командам …»), the steps and
   the `backupArtifact` time.
2. Compare with the router itself: read the menus of the commands (`/export`
   or `get_mikrotik_config` for the section) and decide per command whether it
   is present. Finish or undo by hand on the router; the pre-change backup
   (`MikrotikArtifact`, trigger `pre-change`, linked from `backupArtifact`) is
   the reference of the previous state; HD has no restore.
3. WireGuard request: no key was saved; remove the peer left on the device and
   propose again.
4. HD never retries it. If the change is still wanted, a new request is
   proposed (the agent is told not to do it before a person has checked).
5. A request stuck in `applying` becomes `needs_attention` on the first sweep
   after it is 10 minutes old.

**A request waiting too long.** `queued` for more than 30 minutes after the
last approval ends in `not_applied` with the reason (device busy, upgrading,
unreachable) or «Утверждение устарело…».
