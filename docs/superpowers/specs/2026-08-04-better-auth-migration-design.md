# Переезд авторизации на better-auth

## Контекст

Авторизация написана вручную и держится на JWT: `bcryptjs` cost 12, токен HS256 на 14 дней, серверных сессий нет. Отсюда три класса проблем.

**Токен нельзя отозвать.** Нет refresh, нет ротации, нет хранилища сессий, нет ручки выхода — выход это `localStorage.removeItem` на клиенте, а токен живёт свои 14 дней. Единственный рубильник — `isActive: false`, который `backend/middleware/isAuth.js` перепроверяет на каждом запросе ценой лишнего `findById`. Смена пароля, снятие прав и снятие `isAdmin` живые токены не гасят.

**Примитив идентичности дырявый.** `backend/middleware/getAuthData.js` — не middleware, а хелпер, вызываемый из контроллеров **134 раза**. Внутри `jwt.decode` вместо `jwt.verify`: подпись не проверяется, `exp` игнорируется, а `JWT_SECRET` вторым аргументом молча выбрасывается, потому что у `decode` там опции, а не ключ. Спасает только то, что `isAuth` успевает отработать раньше — но на трёх монтированиях (`backend/routes/index.js:83-99`) гейты прав стоят **до** `isAuth`, и аноним получает там 500 вместо 401.

**Права размазаны.** 28 плоских булевых флагов на пользователе, 33 функции в `backend/middleware/permissions.js` вида «а есть ли галочка», плюс инлайн-проверки в контроллерах. Ролей нет: при заведении каждого человека приходится вспоминать, кому что можно. Список ключей прав существует в трёх копиях (`models/user.js`, `types/user.ts`, `frontend/.../permissions-catalog.js`) и уже разошёлся: в типе есть три несуществующих права и нет двух реально работающих.

Отдельно нашлись **живые дыры уровня захвата администратора** — они чинятся первыми, своим деплоем (этап 0).

Целевое состояние: better-auth владеет идентичностью (сессии, пароли, сброс, 2FA), приложение владеет авторизацией (роли и права) и скоупированием данных. `User._id` не меняется — на него завязана 31 коллекция и денормализованные снапшоты профиля в `Ticket`, `Work`, `Company`, `Preferences`.

## Принятые решения

| | Выбор |
|---|---|
| Пароли | Существующие bcrypt-хеши работают дальше. Ни писем, ни сбросов. Один разлогин при переезде допустим. |
| Транспорт | httpOnly-cookie как цель, плагин `bearer()` на переходный период. Обе дороги ведут в одну серверную сессию. |
| Роли | Справочник в БД, админ создаёт свои. Права вычисляются из роли на каждом запросе + персональные исключения. |
| `organization` | Не включаем, `Company` остаётся моделью приложения. Совместимость с SaaS закладываем. |
| Сверх паритета | Список сессий и «выйти везде», TOTP, вход по ссылке из письма — **только клиентам**. Никаких OAuth/SSO. |

## Что показали данные (копия прода, проверено запросом)

- **694 пользователя, у всех есть `password` и `isActive`.** Миграция аккаунтов пройдёт по всем.
- **Все адреса уже в нижнем регистре, коллизий после `toLowerCase` — ноль.** Отсутствие `lowercase: true` в схеме опасно теоретически; чинить надо, разгребать данные — нет. Но проверку перед прод-миграцией всё равно гоняем.
- **Хеши: 412 × `$2b$`, 282 × `$2a$`** — оба варианта bcrypt, `bcryptjs.compare` ест оба.
- **6 сервисных учёток** — им сессии не выдаются никогда.
- **18 уникальных наборов прав на 694 человека**, распределение крайне неровное: 656 клиентов с пустым набором, 13 с `canSeeAllCompanyTickets`, 6 сервисных, 5 клиентов-руководителей, 4 админа, и 10 сотрудников с уникальными наборами по одному человеку.

**97% укладываются в четыре роли.** Хвост — ~15 сотрудников, ровно для них нужны персональные исключения. Это подтверждает выбранную модель: маленький каталог + точечные отклонения.

## Две находки, определяющие форму работ

**Фронт почти не надо трогать.** Все 309 вызовов имеют форму `` `${import.meta.env.VITE_API_ADDRESS}/api/...` ``. Пустая строка в переменной превращает их в относительные `/api/...` — same-origin, а `fetch` по умолчанию шлёт `credentials: "same-origin"`, то есть **cookie едет сама**. `credentials: 'include'` в проекте не встречается ни разу и не нужен. Значит:
- прод: фронт и API уже за одним nginx — работает сразу;
- дев: добавляем vite-прокси `/api` и `/uploads` на `http://backend:8080` (фронт в деве живёт в контейнере с volume-монтированием, поэтому цель — имя сервиса, не localhost);
- 299 заголовков `Authorization` остаются висеть безвредно и снимаются в уборке.

Единый `api()`-клиент всё равно пишем — но ради **одной** обработки 401 вместо трёх несогласованных, а не ради кук. Это снимает срочность с миграции 160 файлов.

**`user.password` не удаляем до самого конца.** Это единственный настоящий путь отката.

## Архитектура

```
better-auth (идентичность)          приложение (авторизация)
├ authSessions   ← отзыв, TTL       ├ Role: каталог, админ правит в UI
├ authAccounts   ← bcrypt-хеш       ├ user.roleId + permissionOverrides
├ authVerifications                 └ effectivePermissions(user, role)
└ authTwoFactors ← этап 6
        │                                   │
        └──────► req.auth ◄─────────────────┘
                    │  собирается ОДИН раз на запрос
        ┌───────────┴────────────┐
   permissions.js          reportScope / reportApprovalScope /
   (33 гейта)              knowledgeNoteVisibility — не трогаем
```

`users` — существующая коллекция, `_id` не меняется. better-auth не трогает права, скоупирование и бизнес-логику.

### Риск 1: ESM-пакет в CommonJS-бэкенде

better-auth 1.6.25 — ESM-only, документация прямо пишет «CommonJS не поддерживается». Бэкенд на `require` + `module-alias`. Решение — **ESM-остров**: один файл `backend/auth/instance.mjs` со статическими импортами и CJS-мост `backend/auth/bootstrap.js`, который подгружает его через `await import()`. Ставка на `require(esm)` в Node 23 не окупается: сломается о top-level await в графе зависимостей, и узнаем об этом в проде.

В `instance.mjs` **не работает `module-alias`** — он патчит только CJS-резолвер. Только относительные пути; всё нужное из приложения (конфиг, хуки) передаётся параметрами из моста.

Ловушка pnpm: если better-auth объявит `mongodb` в peer-зависимостях, поставится вторая копия драйвера и объекты из mongoose могут не пройти `instanceof` внутри адаптера. Закрепить `mongodb` точной версией в `backend/package.json` и проверить, что в `node_modules/.pnpm` она одна.

### Риск 2: порядок в `app.js`

`toNodeHandler` читает **сырое тело** — если `express.json()` (сейчас `backend/app.js:67`) отработает раньше, запросы к `/api/auth/*` будут висеть до таймаута без внятной ошибки. Хендлер регистрируется до него, а собирается позже: `mongoose.connect()` стоит на строке 145, `app.listen` внутри `.then()`. Обе задачи решает тонкая обёртка, которая ждёт мемоизированный инстанс, плюс `await initAuth()` внутри `.then()` перед `listen`.

Express 5 требует именованный splat: `app.all("/api/auth/*splat", authRequestHandler)`.

Проверка обязательна, ошибка тихая:
```
curl -s -o /dev/null -w '%{http_code} %{time_total}\n' -X POST \
  http://localhost:8080/api/auth/sign-in/email \
  -H 'Content-Type: application/json' -d '{"email":"x@y.z","password":"nope"}'
# 401 за <1s — порядок верный. 30+ секунд — тело съедено express.json().
```

### Риск 3: better-auth пишет мимо Mongoose

Адаптер работает нативным драйвером — `required` и `default` схемы не применяются. Созданный им пользователь приедет без `isActive` (required, без default), `firstName`, `company`, всех 28 прав: `user.save()` упадёт позже и в другом месте, а `User.find({ isActive: true })` его не увидит.

Два рубежа: `emailAndPassword.disableSignUp: true` (пользователей создаём мы, через Mongoose, как сейчас — better-auth только выдаёт сессию) плюс `databaseHooks.user.create.before`, дозаполняющий обязательные поля, если кто-то всё же пройдёт мимо. Туда же — `databaseHooks.session.create.before`, отказывающий служебным, отключённым и сотрудникам отключённых компаний: сегодня эту проверку делает только наш `login`, и на любом новом способе входа она бы потерялась.

**Индексы адаптер не создаёт.** `authSessions.token` читается на каждом запросе — без уникального индекса это COLLSCAN по растущей коллекции. TTL-индексы на `expiresAt` — единственная уборка протухших сессий, своего крона у better-auth нет. Отдельный идемпотентный `backend/scripts/initAuthCollections.js`.

Коллекции называем `authSessions` / `authAccounts` / `authVerifications` / `authTwoFactors` — по имени видно владельца, и `authAccounts` не спутать со счетами клиентов. Mongoose-моделей для них не заводим: владелец один.

## Этапы

Сквозной рычаг отката для этапов 2-3 — переменная `AUTH_MODE` (`legacy` | `better-auth`). Контроллер входа и сборка `req.auth` держат обе ветки ровно один релиз. Откат = правка `.env.prod` + `docker compose restart backend`, около двадцати секунд, без пересборки образов и без `deploy-prod.sh` (который сегодня умеет только «пересобрать всё»).

### Этап 0 — хотфикс живых дыр

Отдельный маленький план, отдельный деплой. **Блокирует всё остальное** — и не только из-за безопасности: этап 4 переписывает `permissions.js`, и если чинить IDOR там же, регрессия «клиент перестал видеть заявки» станет неотличима от бага ролей.

1. **`notifications` утекает из `GET /api/users/:id`.** `backend/controllers/user.js:425` вырезает `-password -resetToken -resetTokenExpiration`, но не `notifications` — а `backend/controllers/auth.js:279-286` кладёт туда **сырой** токен восстановления, и `controllers/user.js:1045` кладёт туда же `jwt.sign(пароль)`, то есть base64 пароля. Любой сотрудник → восстановление на почту админа → чтение токена → захват. Перевести ответ на **белый** список полей.
2. **Смена чужого пароля.** `backend/routes/internal/user.js:101` — только `isAuth`; `controllers/user.js:1031` берёт id из URL, не сверяет со своим, не требует текущий пароль. Добавить `canManageUsers`, разделить «свой» и «чужой», для своего требовать текущий пароль.
3. **IDOR на все 13 271 заявку.** `backend/middleware/permissions.js:86-93` — ветка отказа требует наличия `canAdministrateTickets`, поэтому у клиента отказ не срабатывает никогда. Переписать условие вручную, автозаменой не трогать.
4. **`updateMyAccount`** берёт `id` из тела запроса — брать из сессии.
5. **`backend/middleware/isTelegramBot.js`** — нет `return` перед `next(err)`, следом безусловный `next()`: контроллер выполняется даже после 401. Ручки `/api/tg/auth` (включает бота любому userId), `/api/tg/set-work-status`, `/api/tg/tickets/all-opened` фактически без авторизации. Плюс токен уезжает в query string, то есть в `nginx access.log` — перенести в заголовок (бот наш, обе стороны меняются одним деплоем).

*Откат:* обычный revert, изменения точечные.

### Этап 1 — данные (деплоится, снаружи невидим)

`checkEmailCollisions.js` (только чтение; сегодня чисто, но гонять перед прод-миграцией обязательно) → `normalizeUserEmails.js --apply` (отказывается работать при коллизиях) → `email: { lowercase: true, trim: true }` в схеме → новые поля `models/user.js`: `name` (зеркало `firstName`+`lastName` для better-auth, бизнес-логика его не читает), `emailVerified`, `roleId`, `permissionOverrides`, `twoFactorEnabled` → бэкфилл `name` и `emailVerified: true` всем 694.

*Откат:* `mongodump` коллекции `users` — **шаг скрипта, а не пожелание** — и `mongorestore --drop`.
*Проверка:* адресов с заглавными 0; число пользователей не изменилось; пустых `name` 0.

### Этап 2 — better-auth в сборке, но не в бою (снаружи невидим)

Зависимости, `auth/instance.mjs`, `auth/bootstrap.js`, `auth/config.js`, `auth/hooks.js`, монтирование до `express.json()`, `initAuthCollections.js`, `migrateAuthAccounts.js`. `AUTH_MODE=legacy` — вход по-прежнему по JWT.

Пароли: `password.hash/verify` на `bcryptjs` cost 12, `minPasswordLength: 6` (как сейчас), `maxPasswordLength: 72` — новое и правильное: bcrypt молча режет на 72 **байтах**, то есть русский пароль длиннее 36 символов сегодня усекается без предупреждения.

**Документ `authAccounts` пишем через адаптер better-auth, а не руками.** Форма записи (тип `userId` — строка или ObjectId, генерация `_id`, имена полей) — его внутреннее дело; ошибка на один тип даёт «неверная почта или пароль» на всех 694 сразу, и понять это можно будет только в проде. Скрипт идемпотентен, пропускает не-bcrypt хеши, `--apply` для записи.

*Откат:* закомментировать монтирование, пересобрать. `authAccounts` остаётся и безвреден.
*Проверка:* тип `_id` в `users` везде `objectId` (better-auth по умолчанию генерирует не-ObjectId строки — нужен `advanced.database.generateId`, иначе такой пользователь станет невидим для `User.findById`); число credential-аккаунтов равно числу пользователей с паролем; живой вход через `curl` даёт 200 + `Set-Cookie` + `set-auth-token`; глазами посмотреть на `findOne()` — какого типа `userId`.

### Этап 3 — переезд идентичности ⚠ здесь выбрасывает 694 пользователя

Бэкенд: `attachSession` (мягкий, наполняет `req.auth`, никогда не 401) + `requireAuth` (жёсткий, точная замена `isAuth`, статус 401 сохраняем дословно — фронт завязан на `INLINE_STATUSES`). `getAuthData` превращается в **шим** — читалку готового `req.auth` в прежней форме, чтобы 134 вызова не переписывать разом. `permissions.js` переписывается сразу целиком: 20+ почти одинаковых функций схлопываются в фабрику `requirePermission(keys, message)`, возвращающую массив мидлварей — Express 5 принимает массив там же, где одну, поэтому **сигнатура на 52 маршрутах не меняется**. Заодно уходит второй `User.findById` после `getAuthData` и лечится 500-вместо-401 у анонима.

Новое: `GET /api/me` (профиль + эффективные права + модули + prefs одним запросом — вместо `customSession`, который конфликтует с требованием мгновенного применения роли), `POST /api/logout`, `services/authSessions.js` с отзывом по пользователю, CORS-allowlist вместо `*`, `app.set("trust proxy", <число>)`.

Фронт: `VITE_API_ADDRESS=""` в `.env.dev` и в `compose.prod.yml`, vite-прокси, `lib/api.ts` с единой обработкой 401, `storeSession` читает `set-auth-token`, чинёный `authDataLoader` (сейчас не проверяет `.ok` и рисует «залогиненную» оболочку на отклонённый токен), `Error.jsx` вызывает `clearSession()` перед редиректом.

**Что должно быть готово до момента разлогина:**
1. Репетиция целиком на дев-копии прода (`./sync-dev-db.sh` → все скрипты → живой вход настоящим пользователем).
2. Проверено, что вход работает **у обоих админов** их настоящими паролями.
3. `BETTER_AUTH_SECRET` записан и в `.env.prod`, и в менеджер паролей.
4. `TRUST_PROXY_HOPS` **замерен** по числу адресов в `X-Forwarded-For` реального запроса, а не угадан. Число, не `true`: `express-rate-limit@7` при `true` валит стартап. Занижение — все запросы с одного IP (сегодня именно так), завышение — клиент подделывает IP и обходит лимит попыток входа.
5. **Проверено на деве: новый фронт + `AUTH_MODE=legacy`.** Иначе откат окажется невозможен именно тогда, когда понадобится.
6. Окно выбрано, люди предупреждены. Реально затронуто ~18 сотрудников и активная часть клиентов: из 98 заведённых за год учёток 76 не входили ни разу.

*Откат:* `AUTH_MODE=legacy` + рестарт бэкенда.

### Этап 4 — роли (поведение не меняется, пока роли не назначены)

`utils/permissions.js` — **единственный** список ключей (модель, тип и фронтовый каталог начинают строиться из него; попутно чинится расхождение в `types/user.ts`). `models/role.js`: код, название, вид staff/client, `isSystem`, `isAdmin`, набор прав, порядок. На `User` — `roleId` и `permissionOverrides` как **разрежённый объект-тристейт** (ключ есть — перебивает роль, ключа нет — решает роль). Две карты «добавить»/«отобрать» отвергнуты: допускают невозможное состояние и хуже рисуются.

`effectivePermissions(user, role)`: база — права роли, а **без роли — старое `user.permissions`**. Эта развилка и делает выкатку безопасной: пока роль никому не назначена, ответ совпадает с доролевым побайтово.

`isEndUser` остаётся полем (он в бизнес-логике и в снапшотах), источником становится `role.kind`. `isAdmin` тоже остаётся зеркалом — его читают ~100 мест и меню фронта. `isServiceAccount` ортогонален ролям.

Скрипты: `proposeRoles.js` группирует 694 пользователей по подписи прав, а близкие (расстояние Хэмминга ≤ 3) предлагает как «роль + N исключений» — иначе на 18 сотрудниках точная группировка даст 12 групп по одному человеку и толку не будет. Затем `seedRoles.js` и `assignRoles.js` (`--dry-run` по умолчанию, `--apply`, `--rollback`), который считает исключения как разницу между текущими правами человека и правами роли — **эффективные права никого не меняются**.

*Приёмка:* `dumpEffectivePermissions.js` до и после `--apply`, `diff` **должен быть пуст**. Без тестов это единственная убедительная проверка.
*Откат:* `assignRoles.js --rollback` снимает `roleId` и исключения, права мгновенно возвращаются к нетронутому `user.permissions`. Без деплоя.

### Этап 5 — вход по ссылке, только клиентам

Идёт после ролей не случайно: гейт «клиент?» опирается на `role.kind`/`isEndUser`, который на этапе 4 получает единственный источник.

Смысл — в том, что происходит уже сейчас. Из 98 заведённых за год учёток 76 не входили ни разу: клиентская учётка рождается из письма в поддержку, человек о ней не знает, и пароль ему **генерируют и присылают письмом в открытом виде** (`controllers/user.js:654` → `middleware/notifications.js:1663`). Ссылка из письма даёт ровно тот же уровень доверия, что уже даёт восстановление пароля — доступ к почте есть доступ к учётке — но снимает необходимость слать пароль.

Плагин `magicLink`. Существенные детали:

- **Письмо шлём своей машинерией**, а не напрямую из колбэка: колбэк создаёт документ `Notification`, как это делает сегодняшнее восстановление. Иначе письмо минует `backend/utils/mailGuard.js`, который вне прода принудительно уводит **любое** письмо на `a.savin@f1lab.ru` — и репетиция на копии прода разошлёт письма 694 живым клиентам.
- **Гейт на отправке**: ссылка выписывается, только если пользователь найден, `isEndUser`, активен, компания активна и это не служебная учётка. Сотрудникам ссылка недоступна — у них пароль и TOTP.
- **`disableSignUp`** обязателен: иначе ссылка на незнакомый адрес заведёт учётку.
- **Ответ всегда одинаковый** — «если такой адрес есть, письмо отправлено». Сегодняшнее восстановление отвечает честным 404 «пользователь не найден», то есть работает как проверялка чужих адресов; повторять это в новой ручке не надо. (Заодно стоит помнить, что `POST /api/signup/company-by-email` уже отдаёт `registered: true|false` — это отдельный разговор.)
- **Срок жизни 30 минут, одноразовая.** Пять минут по умолчанию для этой аудитории мало: почтовый крон ходит раз в 10 секунд, но доставка до внешнего ящика занимает минуты, а клиенты читают почту не мгновенно.
- **Свой лимитер** по адресу: без него ручка становится инструментом рассылки писем на чужой ящик.
- UI: вторичное действие «Прислать ссылку для входа» на `frontend/src/pages/Auth/Login.tsx`, видимое при `prefs.emailIsActive`, плюс страница «письмо отправлено».

Тем же этапом уходит рассылка паролей: при заведении пользователя вместо письма с паролем отправляется письмо со ссылкой установки пароля. Поле `notifications.password` перестаёт наполняться (само поле выпиливается в уборке).

*Не удался:* ссылки не приходят; вход паролем не затронут.
*Откат:* убрать плагин и кнопку.
*Проверка:* сотруднику ссылка не выписывается; отключённому клиенту не выписывается; ссылка не срабатывает второй раз; по истечении 30 минут не срабатывает; на дев-стенде письмо ушло владельцу, а не клиенту.

### Этап 6 — сессии в UI (только добавляет)

Секция «Активные сеансы» в `frontend/src/components/User/AccountSettings/Security.jsx`: браузер и ОС из `userAgent`, IP, «активна N минут назад», значок текущего устройства, «Завершить» на строке и «Выйти на всех остальных устройствах». Ручки better-auth готовы, своего кода на бэке не нужно. Разбор `userAgent` — тридцать строк вручную, без новой зависимости.

`session.cookieCache` **выключаем намеренно**: кэш держит копию сессии в самой куке, и на его срок отзыв, отключение учётки и правка роли перестают действовать мгновенно. При 694 пользователях экономия одного индексированного чтения того не стоит.

Тем же этапом — **смена своего пароля** переезжает на `POST /api/auth/change-password` с `currentPassword` и `revokeOtherSessions`. Сегодня она идёт тем же путём, что админский сброс, и текущий пароль не спрашивает вовсе.

### Этап 7 — TOTP (по умолчанию выключено)

Плагин `twoFactor`, коллекция `authTwoFactors` (секреты шифруются на `BETTER_AUTH_SECRET`), QR через `qr-code-styling` — она **уже в зависимостях фронта**. Резервные коды показываются один раз, с кнопкой скачивания и обязательным подтверждением. Админский сброс при потере устройства — своя ручка за `canManageUsers`, с аудитом и правилом «сбрасывающий сам обязан иметь 2FA». Обязательность для админов — через `Preferences` **с отсрочкой**: без неё админ, щёлкнувший переключатель, запирает снаружи в том числе себя.

**Связка со входом по ссылке.** Ссылка из письма — это отдельный путь входа, второй фактор она не спрашивает. Сегодня пересечение пусто по построению: ссылка только клиентам, TOTP только сотрудникам. Это не совпадение, а инвариант, который надо удержать: если ссылку когда-нибудь откроют сотрудникам или включат TOTP клиенту, двухфакторка обойдётся одним письмом. Записать проверку «у кого есть TOTP — тому ссылка не выписывается» прямо в гейт отправки.

*Чем ломается:* `signIn` начинает возвращать `{ twoFactorRedirect: true }` вместо сессии. Если не обработать ветку в `pages/Auth/Login.tsx`, **вход ломается всем**. Поэтому 2FA включается сначала на одной своей учётке и проверяется в приватном окне до любого объявления.
*Откат:* убрать плагин из массива — вход возвращается к одному шагу, `authTwoFactors` остаётся и подхватится при повторном включении.

### Этап 8 — уборка

Миграция экранов на `api()` пачками (метрика: `grep -rn 'Authorization' frontend/src | wc -l` от 299 к нулю), затем снять `bearer()` и перестать писать токен в localStorage; через месяц работы на `authAccounts` — `$unset users.password`; выкинуть `jsonwebtoken`, `JWT_SECRET`, `API_URL`; удалить `getAuthData.js`; хешировать `company.apiKeys` (в `backend/utils/apiKeyGenerator.js` уже лежит неиспользуемый `hashApiKey`, переход возможен **без ротации ключей у клиентов**); добавить `helmet` и CSP — второй линии обороны к DOMPurify, который сегодня стоит только в `frontend/src/components/Ticket/View/Sections.jsx:111`.

## Что остаётся самописным

- **Скоупирование данных** — `services/reportScope.js`, `services/reportApprovalScope.js`, `helpers/knowledgeNoteVisibility.js`, `services/workSubdivision.js`. Права открывают страницу, скоуп решает объём. Меняется только источник пользователя.
- **API-ключи компаний** — принадлежат компании, а не пользователю; плагин better-auth устроен иначе. Оставляем своё, но хешируем.
- **Токен телеграм-бота** — общий секрет между сервисами, один потребитель.
- **Ссылки согласования** (`routes/external/approval.js`) — одноразовые токены с ограниченным сроком, отдельная модель доверия.
- **Приём заявок из почты** — отправитель и есть удостоверение, осознанное решение продукта.
- **`/uploads/:name`** — остаётся публичным на этом круге, но **впервые становится закрываемым**: сегодня закрыть его нельзя в принципе (картинки грузятся через `<img src>`, а токен лежит в localStorage и в тег не подставляется), с cookie ограничение снимается. Отдельная задача — нужна явная связь «файл → заявка».

## Проверка

Автотестов в репозитории нет вообще, поэтому проверка ручная и поэтапная.

- **Статика:** `pnpm typecheck` и eslint во фронте; в бэкенде eslint сломан — там `node --check` по изменённым файлам плюс `node --check auth/instance.mjs`.
- **Дым внутри контейнера:** грузится ли ESM; собирается ли `auth` на живом соединении; порядок мидлварей по времени ответа; живой вход по cookie и по bearer.
- **Инварианты в mongosh** после каждой миграции: тип `_id`, число аккаунтов, наличие индексов `authSessions`.
- **Репетиция на копии прода** (`./sync-dev-db.sh` → все скрипты по порядку → `diff` снимков прав). Пароли в копии настоящие, но неизвестные — для проверки входа настоящим паролем попросить одного администратора войти на дев-стенде.
- **Ручной чек-лист по ролям**: шесть персон, для каждой — вход, ожидаемое меню, две открывающиеся страницы и одна закрытая (ждём 403, не 500 и не пустой экран). Плюс сквозные: отключение пользователя гасит его открытую вкладку; «выйти везде» роняет вторую сессию; смена пароля убивает остальные сессии, но не текущую; служебная учётка не входит; одиннадцатая попытка входа даёт сообщение лимитера.
- UI пользователь проверяет сам; playwright самостоятельно не запускаем.

## Что может пойти не так

| Риск | Симптом | Чем закрыт |
|---|---|---|
| `userId` в `authAccounts` записан не тем типом | у всех 694 «неверная почта или пароль» | писать через адаптер, а не руками; глазами посмотреть первый документ; живой вход на копии прода |
| ESM не грузится под Node 23-alpine | бэкенд не стартует | ESM-остров + динамический `import()`; дым-проверка на том же базовом образе до прод-деплоя |
| `express.json()` раньше better-auth | запросы висят до таймаута, без ошибки | проверка по `time_total`, комментарий в `app.js` у обеих строк |
| better-auth создал пользователя мимо Mongoose | нет `isActive`, `save()` падает позже и не там | `disableSignUp: true` + хук дозаполнения + скрипт проверки целостности |
| `trust proxy` угадан | все запросы с одного IP либо клиент подделывает IP | замер по реальному `X-Forwarded-For`; число, не `true` |
| нет индекса на `authSessions.token` | деградация на каждом запросе, растущая | `initAuthCollections.js` в том же деплое, `getIndexes()` в приёмке |
| новый фронт + откат в `legacy` | после отката никто не может войти | проверить связку на деве **до** этапа 3 |
| ветка `twoFactorRedirect` не обработана | вход ломается всем | включить 2FA сначала на своей учётке, проверить в приватном окне |
| письмо со ссылкой шлётся мимо `mailGuard` | репетиция на копии прода рассылает письма 694 живым клиентам | колбэк создаёт `Notification`, а не шлёт напрямую; проверить на дев-стенде, что письмо ушло владельцу |
| ручка ссылки без лимитера | рассылка писем на чужой ящик | отдельный лимитер по адресу; ответ всегда одинаковый, независимо от существования учётки |
| ссылка выписана сотруднику | обход обязательной двухфакторки одним письмом | гейт на отправке: только `isEndUser`, активный, без TOTP |
| смена `BETTER_AUTH_SECRET` | всех выбросило, секреты TOTP не расшифровать | это же аварийный рычаг «выйти всем»; предупреждение в `.env.prod.example`, секрет в менеджере паролей |
| два лимитера — наш и встроенный | 429 раньше ожидаемого | настроить правила better-auth зеркально `loginLimiter` либо знать про оба |
| телеграм-бот со своей mongoose 6 и копией модели | молча теряет новые поля | проверить, пишет ли бот в `users` напрямую; если да — править до этапа 1 |
| деплой всё-или-ничего | простой на каждом этапе | `deploy-prod.sh` пересобирает все четыре образа; рычаг `AUTH_MODE` даёт откат без него |
