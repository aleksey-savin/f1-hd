# Переезд авторизации на better-auth

## Контекст

Авторизация написана вручную и держится на JWT: `bcryptjs` cost 12, токен HS256 на 14 дней, серверных сессий нет. Отсюда три класса проблем.

**Токен нельзя отозвать.** Нет refresh, нет ротации, нет хранилища сессий, нет ручки выхода — выход это `localStorage.removeItem` на клиенте, а токен живёт свои 14 дней. Единственный рубильник — `isActive: false`, который `backend/middleware/isAuth.js` перепроверяет на каждом запросе ценой лишнего `findById`. Смена пароля, снятие прав и снятие `isAdmin` живые токены не гасят.

**Примитив идентичности дырявый.** `backend/middleware/getAuthData.js` — не middleware, а хелпер, вызываемый из контроллеров **134 раза**. Внутри `jwt.decode` вместо `jwt.verify`: подпись не проверяется, `exp` игнорируется, а `JWT_SECRET` вторым аргументом молча выбрасывается, потому что у `decode` там опции, а не ключ. Спасает только то, что `isAuth` успевает отработать раньше — но на трёх монтированиях (`backend/routes/index.js:83-99`) гейты прав стоят **до** `isAuth`, и аноним получает там 500 вместо 401.

**Права размазаны.** 28 плоских булевых флагов на пользователе, 33 функции в `backend/middleware/permissions.js` вида «а есть ли галочка», плюс инлайн-проверки в контроллерах. Ролей нет: при заведении каждого человека приходится вспоминать, кому что можно. Список ключей прав существует в трёх копиях (`models/user.js`, `types/user.ts`, `frontend/.../permissions-catalog.js`) и уже разошёлся: в типе есть три несуществующих права и нет двух реально работающих.

Отдельно нашлись **живые дыры уровня захвата администратора** — они чинятся первыми, своим деплоем (этап 0).

Целевое состояние: better-auth владеет идентичностью (сессии, пароли, сброс, 2FA), приложение владеет авторизацией (роли и права) и скоупированием данных. `User._id` не меняется — на него завязана 31 коллекция и денормализованные снапшоты профиля в `Ticket`, `Work`, `Company`, `Preferences`.

## Принятые решения

| | Выбор |
|---|---|
| Пароли | Существующие bcrypt-хеши работают дальше. Ни писем, ни сбросов. Один разлогин при переезде допустим. |
| Транспорт | httpOnly-cookie как цель, плагин `bearer()` на переходный период. Обе дороги ведут в одну серверную сессию. |
| Роли | Целиком из коробки, ничего своего. Плагин `organization` с `dynamicAccessControl`: роли создаются из интерфейса и лежат в `organizationRole`. |
| Плагин `organization` | **Одна организация = вся установка.** Роли выходят глобальными, `member` — «пользователь и его роли». `Company` остаётся обычной моделью приложения и плагина не касается. |
| Плагин `admin` | Тоже берём — за тем, чего в organization нет: `setUserPassword`, управление чужими сессиями, `banUser` со сроком и причиной, вход под пользователем. |
| `isActive` у пользователя | Заменяется на `banned` плагина. `company.isActive` остаётся — это свойство компании, у better-auth такого понятия нет. |
| Саморегистрация | Удаляется целиком. Первый запуск — сид при старте вместо веб-формы. |
| `organization` | Не включаем, `Company` остаётся моделью приложения. Совместимость с SaaS закладываем. |
| Сверх паритета | Список сессий и «выйти везде», TOTP, вход по ссылке из письма — **только клиентам**. Никаких OAuth/SSO. |

## Что показали данные (копия прода, проверено запросом)

Числа — снимок на момент планирования. Копия обновляется `./sync-dev-db.sh`, и счётчики плывут: за время работы над этапом 1 база доросла до 702. Перед прод-миграцией всё перемеряется на месте, для того `checkEmailCollisions.js` и запускается на проде непосредственно перед нормализацией.

- **694 пользователя, у всех есть `password` и `isActive`.** Миграция аккаунтов пройдёт по всем.
- **Все адреса уже в нижнем регистре, коллизий после `toLowerCase` — ноль.** Отсутствие `lowercase: true` в схеме опасно теоретически; чинить надо, разгребать данные — нет. Но проверку перед прод-миграцией всё равно гоняем.
- **Хеши: 412 × `$2b$`, 282 × `$2a$`** — оба варианта bcrypt, `bcryptjs.compare` ест оба.
- **6 сервисных учёток** — им сессии не выдаются никогда.
- **18 уникальных наборов прав на 694 человека**, распределение крайне неровное: 656 клиентов с пустым набором, 13 с `canSeeAllCompanyTickets`, 6 сервисных, 5 клиентов-руководителей, 4 админа, и 10 сотрудников с уникальными наборами по одному человеку.

**97% укладываются в четыре роли.** Хвост — ~15 сотрудников, ровно для них нужны персональные исключения. Это подтверждает выбранную модель: маленький каталог + точечные отклонения.

## Две находки, определяющие форму работ

**Фронт не надо трогать для самого переезда — проверено на стенде 2026-08-06.** Контроллер `/api/login` кладёт токен сеанса better-auth в то же поле `token` тела ответа, где лежал JWT. Немигрированный фронтенд сохраняет его в localStorage и шлёт как `Authorization: Bearer`, плагин `bearer` это принимает. Прогон полного клиентского флоу в режиме `better-auth` — вход, загрузчик корня (`app-version`, `users/:id`, `preferences-initial`), заявки, пользователи, статусы — весь 200 без единой правки клиента.

Следствие: миграция фронтенда на `api()`-клиент и куки перестаёт быть **условием** переезда и становится уборкой. Разлогин остаётся (старые JWT в новом режиме отбиваются), но экраны после входа работают сразу.

**А вот для перехода на куки фронт трогать почти не придётся.** Все 309 вызовов имеют форму `` `${import.meta.env.VITE_API_ADDRESS}/api/...` ``. Пустая строка в переменной превращает их в относительные `/api/...` — same-origin, а `fetch` по умолчанию шлёт `credentials: "same-origin"`, то есть **cookie едет сама**. `credentials: 'include'` в проекте не встречается ни разу и не нужен. Значит:
- прод: фронт и API уже за одним nginx — работает сразу;
- дев: добавляем vite-прокси `/api` и `/uploads` на `http://backend:8080` (фронт в деве живёт в контейнере с volume-монтированием, поэтому цель — имя сервиса, не localhost);
- 299 заголовков `Authorization` остаются висеть безвредно и снимаются в уборке.

Единый `api()`-клиент всё равно пишем — но ради **одной** обработки 401 вместо трёх несогласованных, а не ради кук. Это снимает срочность с миграции 160 файлов.

**`user.password` не удаляем до самого конца.** Это единственный настоящий путь отката.

## Архитектура

```
better-auth (идентичность)          приложение (авторизация)
├ authSessions   ← отзыв, TTL       ├ Role: каталог, админ правит в UI
├ authAccounts   ← хеш пароля       ├ user.role (коды) + permissionOverrides
├ authVerifications                 └ effectivePermissions(user, role)
└ authTwoFactors ← этап 6
        │                                   │
        └──────► req.auth ◄─────────────────┘
                    │  собирается ОДИН раз на запрос
        ┌───────────┴────────────┐
   permissions.js          reportScope / reportApprovalScope /
   (33 гейта)              knowledgeNoteVisibility — не трогаем
```

`users` — существующая коллекция, `_id` не меняется. better-auth не трогает права, скоупирование и бизнес-логику.

### Риск 1: ESM-пакет в CommonJS-бэкенде

better-auth 1.6.25 — ESM-only, документация прямо пишет «CommonJS не поддерживается». Бэкенд на `require` + `module-alias`. Решение — **ESM-остров**: один файл `backend/auth/instance.mjs` со статическими импортами и CJS-мост `backend/auth/bootstrap.js`, который подгружает его через `await import()`. Ставка на `require(esm)` в Node 23 не окупается: сломается о top-level await в графе зависимостей, и узнаем об этом в проде.

В `instance.mjs` **не работает `module-alias`** — он патчит только CJS-резолвер. Только относительные пути; всё нужное из приложения (конфиг, хуки) передаётся параметрами из моста.

Ловушка pnpm: если better-auth объявит `mongodb` в peer-зависимостях, поставится вторая копия драйвера и объекты из mongoose могут не пройти `instanceof` внутри адаптера. Закрепить `mongodb` точной версией в `backend/package.json` и проверить, что в `node_modules/.pnpm` она одна.

### Риск 2: порядок в `app.js`

`toNodeHandler` читает **сырое тело** — если `express.json()` (сейчас `backend/app.js:67`) отработает раньше, запросы к `/api/auth/*` будут висеть до таймаута без внятной ошибки. Хендлер регистрируется до него, а собирается позже: `mongoose.connect()` стоит на строке 145, `app.listen` внутри `.then()`. Обе задачи решает тонкая обёртка, которая ждёт мемоизированный инстанс, плюс `await initAuth()` внутри `.then()` перед `listen`.

Express 5 требует именованный splat: `app.all("/api/auth/*splat", authRequestHandler)`.

Проверка обязательна, ошибка тихая:
```
curl -s -o /dev/null -w '%{http_code} %{time_total}\n' -X POST \
  http://localhost:8080/api/auth/sign-in/email \
  -H 'Content-Type: application/json' -d '{"email":"x@y.z","password":"nope"}'
# 401 за <1s — порядок верный. 30+ секунд — тело съедено express.json().
```

### Риск 3: better-auth пишет мимо Mongoose

Адаптер работает нативным драйвером — `required` и `default` схемы не применяются. Созданный им пользователь приедет без `isActive` (required, без default), `firstName`, `company`, всех 28 прав: `user.save()` упадёт позже и в другом месте, а `User.find({ isActive: true })` его не увидит.

Два рубежа: `emailAndPassword.disableSignUp: true` (пользователей создаём мы, через Mongoose, как сейчас — better-auth только выдаёт сессию) плюс `databaseHooks.user.create.before`, дозаполняющий обязательные поля, если кто-то всё же пройдёт мимо. Туда же — `databaseHooks.session.create.before`, отказывающий служебным, отключённым и сотрудникам отключённых компаний: сегодня эту проверку делает только наш `login`, и на любом новом способе входа она бы потерялась.

**Индексы адаптер не создаёт.** `authSessions.token` читается на каждом запросе — без уникального индекса это COLLSCAN по растущей коллекции. TTL-индексы на `expiresAt` — единственная уборка протухших сессий, своего крона у better-auth нет. Отдельный идемпотентный `backend/scripts/initAuthCollections.js`.

Коллекции называем `authSessions` / `authAccounts` / `authVerifications` / `authTwoFactors` — по имени видно владельца, и `authAccounts` не спутать со счетами клиентов. Mongoose-моделей для них не заводим: владелец один.

## Где рождается пароль

Сегодня пароль лежит в `users.password`. У better-auth он лежит в отдельной коллекции (`authAccounts`, документ с `providerId: "credential"`) — это его устройство, и оно не настраивается. Пользователь без такого документа войти по паролю не может вообще: это не «неверный пароль», а отсутствие учётных данных.

Миграция этапа 2 переносит туда все существующие хеши. Но пароль рождается ещё в шести местах, и если оставить их писать в `users.password`, новый пользователь получит хеш там, куда better-auth не смотрит — а держать ради него старый вход значит завести вторую систему авторизации:

| Где | Что делает |
|---|---|
| `controllers/auth.js:109` | саморегистрация по домену компании |
| `controllers/auth.js:361` | восстановление по почте |
| `controllers/auth.js:395` | первый запуск |
| `controllers/user.js:629` | админ заводит пользователя |
| `controllers/user.js:1080` | смена и админский сброс пароля |

**Новые пароли хешируются штатно — scrypt better-auth, не bcrypt.** Кастомной остаётся только проверка, и ровно ради унаследованных хешей:

```js
verify: ({ hash, password }) =>
  hash.startsWith("$2")                    // 702 старых хеша: $2a$ и $2b$
    ? bcrypt.compare(password, hash)
    : verifyPassword({ hash, password }),  // штатный scrypt better-auth
```

Пять строк на всю обратную совместимость. Старый пароль остаётся bcrypt до тех пор, пока человек его не сменит; сменил — стал scrypt. Ленивую переподпись при входе не делаем: она требует записи из функции проверки и стоит больше кода, чем экономит.

**Проверять пароль можно ТОЛЬКО через `ctx.password.verify`** — и это не стилистика (обожглись 2026-08-07). В контексте лежит именно эта функция (`create-context.mjs`: `verify: options.emailAndPassword?.password?.verify || verifyPassword`), а сырой `verifyPassword` из `better-auth/crypto` — чистый scrypt: на хеше `$2b$` он не возвращает `false`, а **бросает** «Invalid password hash». Вход отвечал 500, причём ровно тем, кто пароль ни разу не менял, то есть сегодня — всем 702 живым учёткам. Автоматические проверки этого не ловили: пробные пользователи заводятся через `setUserPassword` и потому сразу scrypt. Ловушка закрыта на источнике: моста к сырым функциям нет вовсе — ни хеша, ни проверки. Пароль хешируют через `ctx.password.hash`, сверяют через `ctx.password.verify`, и обёрток бояться больше не надо (см. следующий абзац).

**Плагин `haveibeenpwned` НЕ используем — он fail-closed.** При недоступном `api.pwnedpasswords.com` он бросает 500 и пароль не принимает, а его маршруты — это `/reset-password`, то есть человек, пришедший по ссылке из письма единственной доступной ему дорогой, при простое чужого сервиса не смог бы задать пароль вовсе. Принятое правило обратное: не проверили — пропускаем и пишем в журнал. Вместо плагина — хук `hooks.before` в острове на том же списке путей (`/sign-up/email`, `/change-password`, `/reset-password`, `/admin/create-user`, `/admin/set-user-password`), зовущий ту же `services/passwordPolicy.js#checkBreached`, что и живая подсказка формы, и `setUserPassword`. Одна реализация на все три пути и один текст отказа (`breachMessage`) — иначе они разъедутся формулировкой и будут читаться как разные проверки. Побочная выгода: `ctx.password.hash` перестал быть обёрнутым, и мост к необёрнутым функциям исчез вместе с причиной своего существования.

Отсюда же правило для проверок: **тест на вход обязан заводить учётку с bcrypt-хешем напрямую**, а не через `setUserPassword` (`scratchpad/verify-legacy-bcrypt-login.js`). Пока все пробы были на scrypt, они подтверждали работу пути, которого в проде ещё почти нет.

`maxPasswordLength` не задаём — предел в 72 байта был свойством bcrypt, у scrypt его нет. `minPasswordLength` берём штатный (8 вместо нынешних 6): новые пароли станут чуть строже, существующих это не касается.

**Кто пишет пароль.** Пять мест из шести исчезают — их делает better-auth своими ручками:

| Было | Стало |
|---|---|
| `controllers/auth.js#forgotPassword` + `validateResetToken` + `resetPassword` | `requestPasswordReset` / `resetPassword` ядра |
| `controllers/user.js#changePassword`, своя смена | наш контроллер, но с обязательным текущим паролем (см. ниже) |
| `controllers/user.js#changePassword`, админский сброс чужого | `setUserPassword` плагина `admin` |
| `controllers/user.js#add` — админ заводит пользователя | `setUserPassword` плагина: сессия админа в запросе есть |
| `controllers/auth.js#signup` — саморегистрация | удаляется вместе с флоу |
| `controllers/auth.js#firstLaunch` | сид при старте — единственное место без сессии |

Вместе с ними уходит вся механика `resetToken` + sha256 + `notifications.resetToken`, то есть источник дыры из этапа 0 исчезает не заплаткой, а вместе с кодом.

Своего кода остаётся **одна функция на один вызов**: `backend/services/authPassword.js#setUserPassword(userId, пароль)` для сида, где сессии ещё нет и ручки плагина недоступны. Штатный хеш better-auth плюс запись в `authAccounts` через адаптер — тем же вызовом, что и `migrateAuthAccounts.js`.

**Админ по-прежнему может всё:** завести пользователя, задать ему пароль, сбросить чужой. Разница только в том, что это делают проверенные ручки плагина, а не наш контроллер. В интерфейсе сброса галочку «отправить пароль письмом» заменяет кнопка **«Отправить ссылку на смену»** — она дёргает штатное восстановление на этого пользователя. Хранение пароля в открытом виде (`notifications.password`) исчезает вместе с ней.

**Почему создание пользователя остаётся за нами.** Наш `User` — это не почта с паролем: компания по домену, 28 прав, `isEndUser`, `notify`, `workSchedules` и `isActive` (`required` без `default`). better-auth пишет нативным драйвером мимо валидации Mongoose (Риск 3).

**Письма better-auth шлёт сам, но нашим транспортом.** `sendResetPassword` и `sendVerificationEmail` настраиваются и работают — иначе ручки сброса были бы мёртвыми. Колбэк обязан идти через существующий почтовый слой: SMTP лежит в `Preferences` шифртекстом, а `backend/utils/mailGuard.js` вне прода уводит **любое** письмо на владельца. Мимо него репетиция на копии прода разослала бы письма 702 живым клиентам. Это не «кастом ради кастома», а единственная возможная реализация отправителя: своего SMTP-клиента у better-auth нет.

**Двойной записи в `users.password` не будет.** Раз пароли ставит better-auth своими ручками, наш код плейнтекста не видит и продублировать его не может. Откат от этого не ломается: `users.password` замораживается на момент переключения, и после отката у всех работает пароль, который был тогда. Пострадает только тот, кто сменил пароль внутри окна отката — у него снова заработает прежний, а не новый; выход — обычное восстановление по почте. Поле удаляется на этапе 8.

## Предусловие: MongoDB на проде

**Прод работает на MongoDB 5, дев — на 8.2.2.** Разрыв случайный: в обоих compose образ указан как `image: mongo` **без тега**, то есть `latest`; дев тянул его недавно, прод — давно.

Это мина, и она не про better-auth. MongoDB не открывает файлы данных, созданные более чем на мажор младше. Любой `docker compose pull` на проде, отсутствие образа в кеше или переезд на новый хост притащат 8.x на данные 5.0, и сервер не поднимется. 5.0 к тому же EOL с октября 2024.

Порядок:

1. **Закрепить тег** в `compose.prod.yml` и `compose.dev.yml` под фактические версии. Одна строка, снимает риск немедленно, к миграции отношения не имеет — можно делать прямо сейчас.
2. **Апгрейд по одному мажору**: 5 → 6 → 7 → 8, на каждом шаге поднимая `setFeatureCompatibilityVersion` перед переходом к следующему. Через мажор не прыгнуть.

**Mongoose 9 убрал колбэк-стиль middleware.** Хуки вида `schema.pre("save", function (next) { …; next(); })` падают с «TypeError: next is not a function», то есть сохранение документа проваливается целиком. Прочее из миграции mongoose 9, что стоит проверить отдельно: массивный синтаксис update-конвейеров блокируется без `updatePipeline: true`; `isValidObjectId()` больше не принимает числа; `doValidate()` вернул промис вместо колбэка; опция `background` у индексов удалена; UUID возвращаются объектами `bson.UUID`, а не строками. **`advanced.database.generateId` НЕ переопределять** (проверено на стенде 2026-08-06). Документация говорит, что ядро генерирует не-ObjectId строки, и соблазн подсунуть свой генератор велик — но mongodb-адаптер делает это сам и сам же конвертирует id между строкой и ObjectId. Собственный генератор эту конвертацию отключает, и получается тихая поломка: вход **проходит**, cookie и bearer выдаются, а `get-session` отвечает 200 с пустым пользователем, потому что связь `session.userId → users._id` ищется строкой по полю ObjectId. Заметить это можно только живым входом, статические проверки его пропускают.

*Проверка:* тип `_id` в `users` везде `objectId`; в `authAccounts` `_id` и `userId` — тоже `objectId`; число credential-аккаунтов равно числу пользователей с паролем; живой вход даёт 200 + `Set-Cookie` + `set-auth-token`, **и `get-session` возвращает того самого пользователя** по обоим транспортам.

### Этап 4 — роли (поведение не меняется, пока роли не назначены)

**Начат 2026-08-07, каркас готов и принят диффом. Что уточнилось на месте:**

- **Права разрешаются ОДИН РАЗ за запрос**, в `attachSession`, а не гейтом. Штатный `hasPermission` плагина при каждом вызове читает из базы все роли организации (`has-permission.mjs`), а проверок на запрос бывает несколько. Решение при этом принимает всё равно функция better-auth: остров экспортирует `authorizeFor(statements)` — это `role(statements).authorize` из `better-auth/plugins/access`, — а `req.auth.can({ ticket: ["delete"] })` её и зовёт. Своей логики разрешения прав в приложении нет.
- **Гейты переписывать по маршрутам не пришлось.** Этап 3 схлопнул двадцать восемь почти одинаковых функций в фабрику `requirePermission`, поэтому словарь сменился в одном файле, а сигнатуры на 52 маршрутах остались прежними. Оценка «87 мест» относилась к дофабричному состоянию.
- **`{ "permissions.canX": true }` в запросах к базе больше не работает** — право может приходить ролью, а роль лежит не в документе пользователя. Восемь таких запросов (списки исполнителей, модераторы базы знаний, получатели уведомлений, согласующие) переведены на `services/permissions.js#permissionFilter(key)`: он собирает условие из трёх частей — «есть подходящая роль» (через `member`), «есть собственный флаг», «администратор». Это место легко проглядеть: запрос не падает, он молча возвращает неполный список.
- **`connector: "OR"` задаётся ВНУТРИ ресурса** (`{ ticket: { actions: [...], connector: "OR" } }`), а не рядом с ним: список действий по умолчанию складывается по И (`access.mjs#normalizeActionRequest`). Рядом с ресурсом строка `"OR"` роняет запрос как «Invalid access control request».
- **Отрицания в `ac` нет** — подтверждено по исходникам: `authorize` проверяет вхождение действия в список, роли складываются по ИЛИ, динамические statements мерджатся со статическими объединением множеств. Вычитание прав невозможно ничем, и решение «точные роли вместо исключений» — единственно доступное.
- **Собственные `user.permissions` остаются вторым источником** и складываются с ролями. Это и делает выкатку безопасной: пока роль никому не назначена, эффективные права совпадают с доролевыми побайтово (проверено `dumpEffectivePermissions.js` — diff по 702 учёткам пуст). Источник уйдёт, когда все получат роли.
- **`permissionOverrides` не заводился вовсе** — решение отменить его пришло раньше, чем этап 1 дошёл до реализации. Удалять нечего.
- Попутно найдено и починено: `controllers/user.js#delete` при несуществующем id **не отвечал вовсе** (всё тело в `if (user)` без `else`) — соединение висело до таймаута клиента.

**Ключ роли и её название — разные вещи (решено 2026-08-09).** Членство хранит роль ИМЕНЕМ: `member.role` — строка, а не ссылка. Штатный `update-role` плагина переименовывает только строку в `organizationRole` и членство не трогает, поэтому переименование роли из интерфейса оставило бы всех её носителей без прав — молча, без единой ошибки. Плюс плагин приводит имена к нижнему регистру (`normalizeRoleName = role.toLowerCase()`), и «Ведущий инженер» превратился бы в «ведущий инженер», разойдясь с тем, что пишет `assignRoles.js`.

Поэтому у роли два поля: `role` — неизменяемый ключ латиницей (`engineer-lead`), по нему живут назначения и его никто не видит, и `title` — название для людей, которое правится свободно. Оба поддержаны плагином штатно, через `schema.organizationRole.additionalFields`. Альтернатива «переименовывать с переписыванием всех членств» отвергнута: транзакций у нас нет (standalone MongoDB), и обрыв посреди операции оставил бы часть людей со ссылкой на несуществующую роль, то есть без прав.

**Кеш ролей протухает по сроку, а не только по вызову** (обожглись там же). `invalidateRoles()` из наших ручек даёт обещанное «роль работает сразу», но правка мимо приложения — миграция, `assignRoles.js`, руки в mongosh — до него не достучится, и кеш держал бы устаревший каталог до перезапуска процесса. Роль, заведённая скриптом при живом бэкенде, не действовала. Срок — 30 секунд; роли меняются раз в месяц, читаются на каждый запрос.

**Автозамена `permissions.canX` → `can({...})` оставляет за собой два класса ошибок, и линт ловит только один.**

Первый — синтаксический: `authedUser.permissions.canManageUsers` превращается в `authedUser.can({...})`, потому что регулярка съедает только хвост. Такой вызов падает в рантайме («can is not a function») и линтом НЕ ловится: это обращение к свойству, а не к неизвестной переменной. Искать надо явно: `grep -rn "[A-Za-z_$)\]]\.can("` — всё, кроме `req.auth.can`, подозрительно.

Второй — смысловой и опаснее: там, где `permissions` были ЧУЖИЕ, замена молча подставляет права текущего человека. Нашлось два таких места, оба сломались бы тихо:
- список инициаторов в форме заявки фильтровался по правам каждого кандидата (`user.permissions.canPerformTickets`) — с ролями этого флага в документе нет, и фильтр выбросил бы половину списка. Заменено на пересечение с `formData.responsibles`, который сервер уже посчитал через `permissionFilter`;
- загрузчик карточки компании читал СВОИ права из `/api/users/:id`, а тот отдаёт сырые флаги документа, а не эффективные. Переведён на `/api/me`; заодно ушёл лишний запрос — карточку пользователя тянули ровно ради одной галочки.

**Проверка по утечкам fail-open ломает наивный тест.** При недоступном `api.pwnedpasswords.com` слабый пароль ПРИНИМАЕТСЯ — это решение, а не сбой (см. выше). Тест, который безусловно требует отказа на `12345678`, поднимает ложную тревогу на каждом моргании сети: за полчаса наблюдений таких пропусков было три. Проверка сначала спрашивает сервис напрямую и требует отказа только при живом сервисе.

**Весь ролевой механизм — из коробки, своего кода ноль.** Плагин `organization` с `dynamicAccessControl: { enabled: true }`:

- `createAccessControl(statement)` объявляет **словарь** — какие вообще бывают ресурсы и действия. Это свойство кода, и иначе быть не может: набор возможностей системы определяется системой.
- **Роли создаются во время работы**, готовыми ручками `create-role` / `update-role` / `delete-role` / `listRoles`, и лежат в коллекции `organizationRole` (`organizationId`, `role`, `permission`). Правка исходников и деплой для новой роли не нужны.
- Роли человека — в `member.role`, несколько поддерживаются нативно (`role: ["admin", "sale"]`).
- `maximumRolesPerOrganization` — предохранитель от разрастания.

Своей коллекции `Role`, своего CRUD, своего кэша и своего разрешения прав **не пишем**.

**Одна организация = вся установка.** `organizationId` во всех строках ролей и членства — одна и та же константа, роли выходят глобальными. `Company` плагина не касается вовсе и остаётся обычной моделью приложения: у неё `emailDomains` для разбора почты, `apiKeys`, тарифы, подразделения — ничего из этого организацией не является. Коллекция `invitation` остаётся пустой: саморегистрацию мы удалили, учётки заводит ИТ-отдел.

**Два поля роли — не зеркало, а разные вопросы.** `member.role` отвечает «что человеку можно в хелпдеске», `user.role` (поле плагина `admin`) — «может ли он звать админские операции над учётками». Второе фактически один бит и выставляется из первого.

Имя `role` свободно: прежний текстовый ярлык оказался мусором (376 записей «Клиент», дублирующих `isEndUser`, 325 пустых и одна осмысленная — `i.chernov@f1lab.ru`, где `position` говорит то же точнее) и удаляется из `models/user.js` и из снапшотов `company.js` ×3, `ticket.js` ×2, `routineTask.js`. Старые значения в документах остаются инертными; физически убрать — один `$unset`, не скрипт.

**28 булевых прав переписываются в `ac`-выражения** вида `{ ticket: ["administrate", "edit", "delete"] }`. Объём измерен: **87 мест на бэкенде и 76 файлов фронта**, 36 уникальных ключей. Работа механическая, но это самая объёмная часть этапа, и `utils/permissions.js` со стражем из этапа 1 становится картой соответствия «старый ключ → ресурс и действие».

**Вычитание прав не нужно.** Оно требовалось, пока роль стоила дорого. Роль создаётся из интерфейса за минуту, поэтому вместо «инженер минус удаление заявок» заводится отдельная точная роль. У 18 сотрудников 18 уникальных наборов — это обернётся шестью-восемью точными ролями вместо четырёх приблизительных плюс исключения. Поле `permissionOverrides`, заведённое на этапе 1, **удаляется**.

**Миграция:** одна строка в `organization`, по строке в `member` на каждого пользователя, роли из существующих наборов прав. `proposeRoles.js` (только чтение) группирует людей по подписи прав и печатает готовый список ролей для заведения; `assignRoles.js` создаёт роли ручками плагина и проставляет `member.role` так, чтобы **эффективные права никого не изменились**.

**Область действия права ролью не задаётся.** «Согласующий, но только для этих компаний» уже выражено там, где ему место: `services/reportApprovalScope.js:142` проверяет само право, а `:147` берёт область из `company.servicePlans[].approver`. То же у `reportScope.js` — `clientsSideResponsibles` и `subdivision.manager`. Добавить компанию в роль значило бы завести второе место для того же и гарантированно его рассинхронизировать.

`isEndUser` остаётся полем (он в бизнес-логике и в снапшотах). `isAdmin` остаётся зеркалом — его читают ~100 мест и меню фронта, а плагину достаточно строки `admin` в `user.role`. `isServiceAccount` ортогонален ролям.

*Приёмка:* `dumpEffectivePermissions.js` до и после `--apply`, `diff` **должен быть пуст**. Без тестов это единственная убедительная проверка.

### Этап 5 — вход по ссылке, только клиентам

**Сделано 2026-08-09. Что вышло иначе, чем задумывалось.**

**Одна дверь вместо двух.** План говорил добавить на экран входа второе почтовое действие рядом с «Получить пароль». На экране это читалось бы как одно и то же: два письма, оба со ссылкой, а выбрать верное человек всё равно не может — он не знает, клиент он или сотрудник, и знать не должен. Поэтому путь один — «Прислать письмо», а что уйдёт, решает сервер: клиенту без второго фактора ссылку для входа, всем остальным ссылку на смену пароля. Ответ при этом одинаковый на всё — успех, незнакомый адрес, отказ, — иначе ручка без авторизации стала бы проверялкой чужих адресов.

**Проверка прикладных правил переехала в хук создания сеанса.** Пока способ входа был один, «не служебная, компания активна» жило в контроллере `/api/login`. Со вторым способом эта проверка там бы и осталась, а сеанс по ссылке выписывался бы мимо неё. Теперь она в `databaseHooks.session.create.before` и ловит ЛЮБОЙ способ, включая будущие. Отключённую учётку туда не добавляли: это делает своим таким же хуком плагин `admin`, а хуки складываются в массив, не заменяя друг друга (`context/helpers.mjs`) — проверено по исходникам, потому что перезапись молча сняла бы проверку бана.

**Гейт — в нашей ручке, а не в плагине.** `signInMagicLink` выписывает ссылку по ЛЮБОМУ адресу и никого не проверяет: ни существования пользователя, ни его вида. Без своего гейта ссылка ушла бы и сотруднику, и это стало бы обходом второго фактора одним письмом.

**Токен хранится хешем** (`storeToken: "hashed"`): он лежит в той же коллекции, что и токены восстановления, и утечка дампа не должна давать вход. Проверено — по значению из письма в базе не находится.

**Лимитер по АДРЕСУ, а не по IP.** Иначе ручка становится инструментом рассылки на чужой ящик: адрес чужой, IP свой, и общий лимитер ограничивает отправителя, а достаётся получателю. Три письма в час на адрес; ответ у лимитера тот же, что у успеха.

**Грабли проверки:** тест сравнивал число писем с нулём, а в дев-базе лежат письма прошлых прогонов — сравнивать надо дельту, иначе проверяется чистота базы, а не поведение ручки.

**Заведение человека без пароля (тот же этап, 2026-08-09).**

Пароль в форме создания перестал быть полем и стал одной из двух дорог — тем же сегментом и с тем же правилом «почта выключена → вкладка гаснет», что в диалоге пароля. По умолчанию приглашение: на этой дороге пароль не покидает голову владельца, и умолчание ведёт к лучшему исходу, а не к привычному. При приглашении учётка заводится ВОВСЕ БЕЗ ПАРОЛЯ — несозданный пароль нельзя ни угадать, ни утечь; `users.password` перестал быть `required`.

**Приглашение — третий текст письма, и выбирается он СОСТОЯНИЕМ, а не флагом.** Приглашение и восстановление уходят разными ручками (`signInMagicLink` и `requestPasswordReset`), и пометить вызов можно только у первой: у второй метаданных нет. Флаг «сейчас приглашаем» в модуле был бы гонкой, отметка времени — гаданием. Состояние отвечает точно: у кого ещё нет пароля и ни одного входа — тому доступ открывают впервые, и «Восстановление доступа» он прочтёт как чужое письмо или как фишинг.

**Ссылка в приглашении живёт 48 часов вместо 30 минут.** Обычную человек только что запросил сам; приглашение приходит без спроса, его откроют вечером или после выходных. Плагин берёт срок только из своих опций и на вызов его не переопределить — строку проверки продлеваем после выписки (`services/invitation.js#extendMagicLink`).

**Сбой письма не откатывает учётку:** приглашение можно повторить, а повторное заведение упрётся в занятый адрес.

В карточке появилась строка «ни разу · приглашён N дней назад»: «никогда» не отвечало на вопрос, который там возникает, — дошло ли приглашение. Из 98 заведённых за год учёток 76 не входили ни разу, и узнать об этом было неоткуда.

Идёт после ролей не случайно: гейт «клиент?» опирается на `isEndUser`, который к этому моменту уже согласован с ролями.

Смысл — в том, что происходит уже сейчас. Из 98 заведённых за год учёток 76 не входили ни разу: клиентская учётка рождается из письма в поддержку, человек о ней не знает, и пароль ему **генерируют и присылают письмом в открытом виде** (`controllers/user.js:654` → `middleware/notifications.js:1663`). Ссылка из письма даёт ровно тот же уровень доверия, что уже даёт восстановление пароля — доступ к почте есть доступ к учётке — но снимает необходимость слать пароль.

Плагин `magicLink`. Существенные детали:

- **Письмо уходит тем же отправителем, что и сброс пароля** (подключён на этапе 2): через существующий почтовый слой и `backend/utils/mailGuard.js`, который вне прода принудительно уводит **любое** письмо на владельца. Мимо него репетиция на копии прода разослала бы письма 702 живым клиентам.
- **Гейт на отправке**: ссылка выписывается, только если пользователь найден, `isEndUser`, активен, компания активна и это не служебная учётка. Сотрудникам ссылка недоступна — у них пароль и TOTP.
- **`disableSignUp`** обязателен: иначе ссылка на незнакомый адрес заведёт учётку.
- **Ответ всегда одинаковый** — «если такой адрес есть, письмо отправлено». Так же ведёт себя и восстановление better-auth, переехавшее на этапе 3; сегодняшнее отвечало честным 404 «пользователь не найден», то есть работало как проверялка чужих адресов. ### Этап 7 — TOTP (по умолчанию выключено)

Плагин `twoFactor`, коллекция `authTwoFactors` (секреты шифруются на `BETTER_AUTH_SECRET`), QR через `qr-code-styling` — она **уже в зависимостях фронта**. Резервные коды показываются один раз, с кнопкой скачивания и обязательным подтверждением. Админский сброс при потере устройства — своя ручка за `canManageUsers`, с аудитом и правилом «сбрасывающий сам обязан иметь 2FA». Обязательность для админов — через `Preferences` **с отсрочкой**: без неё админ, щёлкнувший переключатель, запирает снаружи в том числе себя.

**Связка со входом по ссылке.** Ссылка из письма — это отдельный путь входа, второй фактор она не спрашивает. Сегодня пересечение пусто по построению: ссылка только клиентам, TOTP только сотрудникам. Это не совпадение, а инвариант, который надо удержать: если ссылку когда-нибудь откроют сотрудникам или включат TOTP клиенту, двухфакторка обойдётся одним письмом. Записать проверку «у кого есть TOTP — тому ссылка не выписывается» прямо в гейт отправки.

*Чем ломается:* `signIn` начинает возвращать `{ twoFactorRedirect: true }` вместо сессии. Если не обработать ветку в `pages/Auth/Login.tsx`, **вход ломается всем**. Поэтому 2FA включается сначала на одной своей учётке и проверяется в приватном окне до любого объявления.
*Откат:* убрать плагин из массива — вход возвращается к одному шагу, `authTwoFactors` остаётся и подхватится при повторном включении.

3. ~~**Переезд экранов на `api()`**~~ — **заголовков не осталось (2026-08-10).** Было 300 в 160 файлах.

   Цель оказалась не в переводе на `api()`, а именно в СНЯТИИ ЗАГОЛОВКОВ: сеанс едет cookie, потому что фронт и API на одном origin и в деве, и в проде. Сторы переведены на `api()` полностью (ради единой обработки 401), остальные вызовы остались обычными `fetch` — просто без заголовка. Переписывать полтораста файлов ради красоты было бы дороже и рискованнее: у каждого своя ветка ошибки, и вслепую их менять нельзя.

   Проверено на живом стенде: одна cookie открывает весь набор ручек оболочки и основных экранов, без cookie — по-прежнему 401.

   **ПОЧЕМУ ПЕРЕЕЗД ОБЯЗАН БЫТЬ ПОЛНЫМ ДО СНЯТИЯ `bearer()`** (измерено, а не выведено). Сначала проверили обратное допущение: cookie сеанса достаточно сама по себе — и в деве (`VITE_API_ADDRESS=''` плюс vite-прокси), и в проде (общий nginx) запросы same-origin, поэтому браузер шлёт её на все 300 ручных `fetch`. Казалось, что снять плагин можно раньше переезда.

   Но `Authorization` с НЕВЕРНЫМ значением ПЕРЕБИВАЕТ валидную cookie и даёт 401:

   | Запрос | Ответ |
   |---|---|
   | cookie, без заголовка | 200 |
   | cookie + `Bearer marker` | **401** |
   | cookie + `Bearer ` (пусто) | 200 |

   То есть в день снятия плагина каждый непереведённый экран начнёт получать 401 — не «перестанет пользоваться токеном», а сломается. Пока плагин включён, смешанное состояние безопасно: переведённые файлы шлют и cookie, и живой токен, непереведённые — живой токен. Опасен ровно момент переключения, и он требует нуля оставшихся заголовков.

   Побочная польза перевода: сторы списков не проверяли `response.ok` вовсе — на любой ошибке список молча оставался пустым, а `isLoading` не сбрасывался. `api()` бросает, и обработка появляется вместе с переездом.
4. **`bearer()` ОСТАЁТСЯ — решено 2026-08-10, после попытки его снять.**

   Всё остальное к снятию готово: заголовков в исходниках ноль, одна cookie открывает весь набор ручек (проверено). Упирается ровно во вход под пользователем: ссылка открывается в ЧИСТОМ браузере, где cookie взяться неоткуда, а ручка обмена отдаёт токен сеанса телом.

   Выписать cookie самим нельзя: **сеанс опознаётся только по ПОДПИСАННОЙ cookie** — проверено, `hd.session_token` без подписи даёт 401.    Остаточный риск от плагина невелик: токен в localStorage работает только как bearer к тому же origin и умирает вместе с сеансом. Правильное закрытие — не снятие плагина, а собственная ручка выдачи подписанной cookie, если `better-auth` когда-нибудь откроет для этого публичный вызов.

## Перенос на прод

Из дева в прод **не переезжает ничего из базы** — ни роли, ни организация, ни `authAccounts`. Переезжает код и один файл данных: `backend/scripts/roles.catalogue.json`. Всё остальное создаётся на месте скриптами из прод-данных.

**Роли раздаются ПО ПОДПИСИ ПРАВ, а не по id.** `assignRoles.js` смотрит, какой набор прав у человека фактически, и ищет роль, которая этот набор поглощает (`matches` в каталоге). Имена и id значения не имеют — это и делает перенос безопасным: на проде свои учётки и данные, ушедшие вперёд от копии. Незнакомая подпись **останавливает скрипт** и печатает человека поимённо; молча приписать чужую роль он не может.

```
# 1. Разведка — только чтение, можно прогнать заранее
node scripts/checkEmailCollisions.js
node scripts/assignRoles.js               # незнакомых наборов быть не должно

# 2. Окно. Останавливаем ПРИЛОЖЕНИЕ, mongo оставляем: скриптам нужна база.
#    `deploy-prod.sh` делает `down`, а он уносит и mongo — здесь именно `stop`.
docker compose -f compose.prod.yml stop backend frontend telegram-bot

# 3. Миграции, порядок значим
node scripts/normalizeUserEmails.js --apply
node scripts/backfillUserAuthFields.js --apply
node scripts/initAuthCollections.js
node scripts/migrateAuthAccounts.js --apply
node scripts/migrateUserBanned.js --apply
node scripts/migrateOrganization.js --apply
node scripts/assignRoles.js --apply

# 4. Новый код
docker compose -f compose.prod.yml up -d --build
```

**`stripOwnPermissions.js` в это окно НЕ входит — и это не забывчивость.**

Скрипт снимает личные права у всех и тем убивает единственный дешёвый откат ролей: `assignRoles.js --rollback` возвращает права из `user.permissions`, а после снятия возвращать будет неоткуда. Пока роли не отработали на проде хотя бы неделю, личные галочки — это страховка, и стоит она ничего: эффективные права считаются объединением, роли уже действуют.

Порядок при этом жёсткий и защищён в коде: `assignRoles.js` выводит роли ИЗ личных галочек, поэтому запуск после снятия видит у всех пустую подпись и раздаёт всем роль с пустым набором прав — то есть стирает раздачу целиком. На деве так и вышло: 696 членств стали «Клиент» одной командой. Теперь скрипт отказывается работать, если личных прав нет ни у кого.

Отсюда два правила:
- `stripOwnPermissions.js --apply` — отдельным заходом, после того как роли себя показали, и только вместе со снимком `dumpEffectivePermissions` до и после;
- `assignRoles.js --apply` после снятия не запускать никогда. Если каталог надо пересинхронизировать позже — правьте роли из интерфейса, для того он и сделан.

**Окно обязательно и не обходится.** `isActive` → `banned` несовместим в обе стороны: старый код после миграции не находит никого, новый до миграции — тоже. Все и так разлогиниваются один раз. Речь о минутах.

**Откат по слоям, от дешёвого к дорогому:**

| Слой | Как | Цена |
|---|---|---|
| роли | `assignRoles.js --rollback` | без деплоя: чистит `member.role`, права возвращаются из `user.permissions`. **Работает, только пока не запущен `stripOwnPermissions.js`** — он и есть точка невозврата для этого слоя |
| `banned` | `db.users_before_banned.aggregate([{ $out: "users" }])` | копия делается скриптом до первой записи |
| код | предыдущий образ | обычный деплой |
| `authAccounts`, организация | оставить | безвредны |

**До окна проверить:** `assignRoles.js` без `--apply` не находит незнакомых наборов; `TRUST_PROXY_HOPS` замерен по реальному `X-Forwarded-For`; `BETTER_AUTH_SECRET` лежит в `.env.prod` и в менеджере паролей; прод достаёт `api.pwnedpasswords.com` (не блокер — проверка fail-open, — но знать надо).

## Проверка

Автотестов в репозитории нет вообще, поэтому проверка ручная и поэтапная.

- **Статика:** `pnpm typecheck` и eslint во фронте; в бэкенде eslint сломан — там `node --check` по изменённым файлам плюс `node --check auth/instance.mjs`.
- **Дым внутри контейнера:** грузится ли ESM; собирается ли `auth` на живом соединении; порядок мидлварей по времени ответа; живой вход по cookie и по bearer.
- **Инварианты в mongosh** после каждой миграции: тип `_id`, число аккаунтов, наличие индексов `authSessions`.
- **Репетиция на копии прода** (`./sync-dev-db.sh` → все скрипты по порядку → `diff` снимков прав). Помнить, что копия крутится на MongoDB 8.2, а прод — на 5.0 (см. «Предусловие»).
- **Вход настоящим паролем проверяет Алексей**: хеши в копии настоящие, но пароли известны только ему. Моя часть — довести этап до состояния «можно проверять» и отдать точную последовательность шагов.
- **Ручной чек-лист по ролям**: шесть персон, для каждой — вход, ожидаемое меню, две открывающиеся страницы и одна закрытая (ждём 403, не 500 и не пустой экран). Плюс сквозные: отключение пользователя гасит его открытую вкладку; «выйти везде» роняет вторую сессию; смена пароля убивает остальные сессии, но не текущую; служебная учётка не входит; одиннадцатая попытка входа даёт сообщение лимитера.
- UI пользователь проверяет сам; playwright самостоятельно не запускаем.

|---|---|---|
| `userId` в `authAccounts` записан не тем типом | у всех сразу «неверная почта или пароль» | писать через адаптер, а не руками; глазами посмотреть первый документ; живой вход на копии прода |
| пароль сверяется сырым `verifyPassword` вместо `ctx.password.verify` | **500 на входе** у всех, кто не менял пароль; пробные учётки при этом входят | сырой `verifyPassword` не экспортируется вовсе; регрессия с bcrypt-хешем в `verify-legacy-bcrypt-login.js` |
| пред-авторизационный экран бросает ответ в error boundary | человека выкидывает с формы входа, введённый адрес теряется, вернуться некуда | `authFailure` в `pages/Auth/session.ts`: вход, «получить пароль» и «новый пароль» не бросают ничего, включая 500 и обрыв сети |
| ESM не грузится под Node 23-alpine | бэкенд не стартует | ESM-остров + динамический `import()`; дым-проверка на том же базовом образе до прод-деплоя |
| `express.json()` раньше better-auth | запросы висят до таймаута, без ошибки | проверка по `time_total`, комментарий в `app.js` у обеих строк |
| better-auth создал пользователя мимо Mongoose | нет `isActive`, `save()` падает позже и не там | `disableSignUp: true` + хук дозаполнения + скрипт проверки целостности |
| пароль записан мимо `authAccounts` | заведённый после переключения человек не входит: «неверная почта или пароль» при верном пароле | единственная точка записи `setUserPassword`; после этапа 3 `grep -rn 'bcrypt.hash' backend/controllers` должен быть пуст |
| пароль сменён после переключения, потом откат в `legacy` | у человека снова работает прежний пароль, а не новый | `users.password` заморожен на момент переключения — не локаут, а откат к старому; выход через восстановление по почте |
| прод тянет `mongo:latest` на данные 5.0 | сервер не поднимается вовсе | закрепить тег в обоих compose **до** любых работ; апгрейд по одному мажору с поднятием FCV |
| репетиция на деве (8.2) не отражает прод (5.0) | «на копии работало» | до этапа 3 версии свести; до тех пор перечитывать операторы агрегации и опции индексов глазами |
| `trust proxy` угадан | все запросы с одного IP либо клиент подделывает IP | замер по реальному `X-Forwarded-For`; число, не `true` |
| нет индекса на `authSessions.token` | деградация на каждом запросе, растущая | `initAuthCollections.js` в том же деплое, `getIndexes()` в приёмке |
| новый фронт + откат в `legacy` | после отката никто не может войти | проверить связку на деве **до** этапа 3 |
| ветка `twoFactorRedirect` не обработана | вход ломается всем | включить 2FA сначала на своей учётке, проверить в приватном окне |
| письмо шлётся мимо `mailGuard` | репетиция на копии прода рассылает письма живым клиентам | колбэк создаёт `Notification`, а не шлёт напрямую; проверить на дев-стенде, что письмо ушло владельцу |
| ручка ссылки без лимитера | рассылка писем на чужой ящик | отдельный лимитер по адресу; ответ всегда одинаковый, независимо от существования учётки |
| ссылка выписана сотруднику | обход обязательной двухфакторки одним письмом | гейт на отправке: только `isEndUser`, активный, без TOTP |
| смена `BETTER_AUTH_SECRET` | всех выбросило, секреты TOTP не расшифровать | это же аварийный рычаг «выйти всем»; предупреждение в `.env.prod.example`, секрет в менеджере паролей |
| два лимитера — наш и встроенный | 429 раньше ожидаемого | настроить правила better-auth зеркально `loginLimiter` либо знать про оба |
| телеграм-бот со своей mongoose 6 и копией модели | молча теряет новые поля | проверить, пишет ли бот в `users` напрямую; если да — править до этапа 1 |
| деплой всё-или-ничего | простой на каждом этапе | `deploy-prod.sh` пересобирает все четыре образа; рычаг `AUTH_MODE` даёт откат без него |
