# MCP-инвентарь: агент заполняет характеристики моделей

Продолжение `docs/superpowers/specs/2026-10-16-mcp-inventory-design.md`. Фазы 1–4 уже сделаны: чтение, предложения, страница предложения, правка справочников и слияние. Операции, их проверку, утверждение и применение описывает `docs/inventory-changes.md`, здесь они не повторяются.

**Статус:** одобрено владельцем 29.10 («ок»); план — `docs/superpowers/plans/2026-10-29-mcp-inventory-model-specs.md`. Пометка «(моё)» означает решение исполнителя, которое владелец может оспорить. Остальное сказал сам владелец.

## Зачем

Владелец заводит технику по моделям, например мониторы. Он хочет, чтобы характеристики моделей заполнялись без него. Агент сам находит спецификации, решает, каких атрибутов не хватает типу, расширяет набор атрибутов типа и вносит значения в нужные модели. Человек только утверждает.

Слова владельца (29.10):
- «характеристики моделей пусть берёт с официального сайта, везде есть спецификации. Если не может найти — пусть не выдумывает»;
- запуск — «по просьбе, и само после занесения новой модели»;
- «сам» значит, что агент сам заглядывает в HD по расписанию. Вебхук из HD в агента отклонён: расписание проще, а час задержки для справочника ничего не стоит.

Остальное владелец принял одним «всё ок» после пересказа (29.10). Это относится к пунктам, помеченным «(моё)» в разделах «Сценарии» и «Правила агента».

Что уже есть с фаз 2 и 4:
- операция `catalog` (формат сида, только добавление): создаёт атрибут и привязывает его к типу, а существующие записи находит по имени или коду;
- `updateAttribute.addOptions`, `updateConfiguration.setValues`, `updateModel`, `updateVendor`.

Отдельных операций `createAttribute` и `linkAttribute` нет. Новых для этой фичи тоже не заводим (моё): атрибуты типа агент добавляет операцией `catalog`.

Новыми здесь оказываются:
- сценарий целиком и инструкции агенту;
- источник значений (ссылка на сайт производителя), который хранится и проверяется;
- отметка «агент модель уже смотрел»;
- находка «новые модели без проверки характеристик»;
- утверждение от имени того, кто завёл модель.

## Цели

1. По просьбе в Telegram («разберись с мониторами», «заполни модель X») агент присылает предложение. В нём атрибуты, которых не хватает типу, и значения по моделям.
2. Сам: агент по расписанию находит новые модели, которые ещё никто не проверял, и присылает такое же предложение. Его утверждает тот, кто завёл модель.
3. У каждой модели в предложении есть ссылка на страницу спецификации на официальном сайте. После утверждения ссылка хранится в карточке модели.
4. Агент не возвращается по кругу к модели, которую уже смотрел: ни когда ничего не нашёл, ни когда предложение отклонили или оно протухло. Повторно — только по прямой просьбе человека.

## Не цели

- HD не ходит в интернет и сам не сверяет значения со страницей. Ищет и читает агент.
- Ссылка на источник хранится одна на модель, не на каждое значение. (моё)
- Фото моделей с сайта производителя не берём.
- Вебхук из HD в агента не делаем (решение владельца).
- Старые модели автоматически не обходим, только по просьбе. (моё: иначе первый проход завалит людей предложениями, и большинство старых моделей заводили без `createdBy`.)
- Тип значения у атрибута (`valueType`) не меняем, это осталось не целью ещё с фазы 4.

## Антицели (провал, даже если всё работает)

- Значение, которого нет на странице производителя: догадка, «типичное для класса», значение с магазина или агрегатора.
- Тихая перезапись того, что внёс человек.
- Расползание дублей: новый атрибут «Диагональ экрана», когда в каталоге уже есть «Диагональ».
- Спам утверждающему: предложение на каждую модель каждый час.
- Агент от имени заведшего модель меняет что-то кроме этой модели и её типа.

## Сценарии

### По просьбе

1. Человек пишет агенту: «разберись с мониторами».
2. Агент смотрит модели типа (`search_device_models`), атрибуты типа и общий каталог атрибутов.
3. По каждой модели ищет страницу спецификации на сайте производителя.
4. Присылает одно предложение (`propose_inventory_change`) от имени просившего, как сейчас. Если моделей много, предложений несколько: пакет вмещает не больше 40 операций (`MAX_OPERATIONS`). Модели одного типа идут в одном пакете вместе с атрибутами типа. (моё)
5. Если какую-то модель агент не нашёл, он говорит об этом в ответе человеку и ставит отметку «не нашёл» (см. «Отметка проверки»).

На прямую просьбу агент берётся и за модели, которые уже смотрел (отметка ему это показывает), и за старые модели.

### Само

1. Расписание живёт в OpenClaw (cron агента), HD его не хранит. Частота на стороне агента, ориентир — раз в час. В `docs/mcp.md` даём готовую формулировку задачи для cron.
2. Агент вызывает `inventory_findings kind=modelsWithoutSpecs`.
3. По каждой модели из ответа делает то же, что по просьбе. Предложение идёт от имени заведшего модель: новый аргумент `forModelCreator` (см. «Утверждающий»).
4. Если утвердить некому, агент ставит отметку «пропущено» с причиной и к модели больше не возвращается.

## Модель данных

- **`Vendor.website`** — строка, домен сайта производителя без схемы и пути, например `dell.com`. Если сайтов несколько (`hp.com`, `hpe.com`), список через запятую. (моё) Правится в форме вендора и операцией `updateVendor.website`. Нужен, чтобы проверять, что ссылка ведёт на официальный сайт.
- **`DeviceModel.specUrl`** — строка, адрес страницы спецификации (`https://…`). Правится в форме модели и операцией `updateModel.specUrl`.
- **Новая коллекция `ModelSpecCheck`**, одна запись на модель (unique `modelId`):
  - `modelId`;
  - `outcome`: `proposed | complete | notFound | skipped`. `complete` значит, что всё уже заполнено и совпадает с сайтом, предлагать нечего;
  - `url?` — что агент нашёл;
  - `note?` — причина для `notFound` и `skipped`, не длиннее 300 символов;
  - `changeId?` — предложение, в котором агент прислал характеристики;
  - `keyId`, `keyName`, `at`.

  Повторная проверка перезаписывает запись. Отдельная коллекция нужна, а поле на модели не годится (моё): запись отметки сдвинула бы `updatedAt` модели и ложно сработала бы проверка дрейфа в ожидающем предложении, где эта модель есть.

## Источник: только официальный сайт

- При предложении HD проверяет у каждого `updateModel.specUrl`:
  - схема `https`;
  - хост равен одному из доменов `Vendor.website` вендора этой модели или его поддомену (`www.dell.com`, `support.hp.com`).

  Если не совпало, это ошибка операции: «ссылка не на сайт производителя (dell.com)».
- Если у вендора нет `website`, агент добавляет в тот же пакет `updateVendor { website }` раньше `updateModel`. Проверка смотрит на домен, который станет после пакета. Утверждающий видит домен отдельной строкой: «Сайт вендора «Dell»: dell.com». Это место, где человек ловит подмену официального сайта магазином. (моё)
- Значения по ссылке HD не проверяет (см. «Не цели»). Честность значений держится на инструкциях агенту и на глазах утверждающего.

## Отметка проверки

- **Новый инструмент** `record_model_spec_check({ model, outcome: "complete" | "notFound" | "skipped", note, url? })` в scope `inventoryChanges`. Это единственная прямая запись агента в этой фиче. Пишется только служебная отметка, инвентарь не меняется. (моё: без неё агент крутился бы по кругу на ненайденных моделях, а предложение «ничего не менять» утверждать бессмысленно.)
- Отметку `proposed` агент сам не ставит. Её пишет `propose_inventory_change` при создании предложения. Отметка ставится каждой модели, которую пакет трогает: `updateModel` этой модели или `updateConfiguration` её конфигурации. В отметку идут `changeId` и `specUrl` модели — из пакета, а если в пакете его нет, то тот, что уже сохранён. Иначе модель, у которой человек сам вписал ссылку, а значения оставил пустыми, всплывала бы каждый час. (моё)
- Отклонённое, протухшее или отозванное предложение отметку не снимает: модель больше не всплывает (цель 4).
- Отметку видно агенту:
  - в `search_device_models` строкой у модели: `spec check: notFound 29.10 — <note>` или `spec check: proposed 29.10 · <url>`;
  - в находке.

  Людям в портале она не показывается. (моё: это служебное состояние агента; когда понадобится, станет строкой в карточке модели.)

## Находка `modelsWithoutSpecs`

Новый вид `inventory_findings`, в группе каталога. Отбирает живые модели, у которых:
- `createdAt` не старше `days` (по умолчанию 30);
- нет записи `ModelSpecCheck`.

Строка находки содержит:
- модель, тип, вендор;
- `website` вендора или `(vendor has no website)`;
- сколько атрибутов типа пусты в конфигурациях модели;
- можно ли утвердить от имени заведшего: `approver: model creator` или `approver: none (<причина>)`. Причины: заведший не указан; заблокирован; это не сотрудник; нет права «Справочники инвентаря: управлять».

Имени и контактов заведшего в строке нет: агенту они не нужны (правило «No staff contacts»).

Окно `days` в 30 дней (моё) ограничивает и первый проход после выкатки: старые модели не всплывут.

## Утверждающий: `forModelCreator`

- У `propose_inventory_change` появляется необязательный `forModelCreator: <modelId>`, взаимоисключающий с `requester`.
- Автор запроса — `createdBy` этой модели. Он должен быть:
  - сотрудником (не клиентом и не служебной учёткой);
  - не заблокирован;
  - с правами на все операции пакета, как сейчас.

  Telegram не обязателен. Без него предложение приходит в колокольчик и ждёт на странице `/inventory/changes/:id`, так уже работают уведомления фазы 2.
- **Рамка пакета.** В режиме `forModelCreator` пакет может трогать только:
  - эту модель и её конфигурации;
  - её вендора: только `updateVendor.website`, и только если сайт у вендора ещё пустой. На этот домен опирается проверка ссылок у всех моделей вендора, поэтому заменить уже заданный домен можно только предложением по просьбе человека или в портале. (моё)
  - атрибуты её типа: операция `catalog`, в которой есть только этот тип (существующий, без правки флагов, сборки и слотов) и его атрибуты. Атрибуты можно добавлять и привязывать к существующим группам. Новые типы и группы нельзя. Плюс `updateAttribute.addOptions` у атрибутов этого типа.

  Другие операции и чужие модели дают ошибку пакета. (моё: антицель 5.) В одном пакете может быть только одна модель. Чтобы собрать несколько новых моделей одного создателя в один пакет, нужен список `forModelCreator`, но это усложнение отложено. (моё)
- **Уведомление.** В режиме `forModelCreator` Telegram уважает выключатели категории уведомлений: человек ничего не просил, поэтому обход `force` фазы 2 здесь не действует. Колокольчик приходит всегда. Текст объясняет, откуда предложение: «Агент нашёл характеристики модели «X», которую вы завели». (моё)
- Лимиты фазы 2 действуют как есть: не больше 5 открытых предложений на автора и 40 в сутки на ключ. Упёрся в лимит — агент ждёт следующего прогона, отметку не ставит.

## Правила агента (инструкции в `server.js` и `docs/mcp.md`)

- Источник — только официальный сайт производителя: страница продукта или спецификации, PDF-даташит с того же домена. Магазины, агрегаторы, обзоры и Википедия не годятся.
- Не нашёл страницу или не уверен, что это та самая модель (региональный суффикс, ревизия), — `notFound` с причиной, без значений.
- Значение берётся только если оно прямо написано на странице. Перевод единиц разрешён: агент приводит значение к `unit` атрибута. Вывод одних значений из других не разрешён.
- Сначала существующие атрибуты:
  1. ищет по смыслу в общем каталоге (`get_inventory_catalog section=attributes`);
  2. если атрибут уже есть, привязывает его к типу операцией `catalog` по его коду;
  3. только если ничего похожего нет, создаёт новый той же операцией `catalog`.

  Скрытые атрибуты не трогает.
- Атрибуты типа выбирает такие, по которым технику различают и выбирают. Для монитора: диагональ, разрешение, матрица, частота, входы. Служебные мелочи вроде веса упаковки не берёт. (моё) Группу атрибута ставит по существующим группам типа.
- У атрибутов-списков значение подбирается к существующему варианту. Новый вариант добавляется через `updateAttribute.addOptions`, только если подходящего нет.
- Заполняет только пустые значения. Если значение, которое внёс человек, расходится с сайтом, отдаёт его в `setValues`: на странице предложения оно видно как «было → станет». В `reason` пакета агент упоминает каждое такое расхождение. Совпадающие значения не трогает.
- У модели с несколькими конфигурациями заполняет только значения, общие для всех её конфигураций (одинаковый `setValues` в каждой). Различающиеся оставляет и пишет об этом в `reason`. (моё)
- Всё уже заполнено и совпадает с сайтом — отметка `complete`, предложения нет.
- Повторно смотрит модель с отметкой только по прямой просьбе человека.

## Портал

UI делается только после макета: обе темы, десктоп и мобайл, «ок» владельца (правило ui-mockup-first). Что меняется:
- карточка модели (`pages/DeviceModel/View.jsx`): ссылка «Спецификация на сайте производителя», если `specUrl` есть;
- форма модели (`DeviceModel/FormFields.jsx`, одна на сущность): поле «Страница спецификации»;
- форма вендора: поле «Сайт»;
- страница предложения: строки `updateModel.specUrl` и `updateVendor.website` в существующей табличке «было → стало», ссылка кликабельна. Нового вида операции нет.

Проверку домена у `specUrl` в ручной форме не делаем: человеку можно. (моё)

## Остаётся исполнителю

- Точный текст строк находки, ошибок и подстрок операций, в стиле фаз 2–4: по-русски для людей, по-английски для агента.
- Место `ModelSpecCheck` в `docs/inventory-changes.md` и `docs/mcp.md`. Бюджет `tools/list` в `routes/mcp.test.js` нужно перемерить.
- Нормализация `website`: обрезать схему и путь, нижний регистр.
- Как именно проверять рамку `forModelCreator` для операции `catalog` (разбор её `params` по формату сида).

## Проверка

- Модульные тесты только затронутых файлов (`node --test …`): проверка домена, рамка `forModelCreator`, запись отметки при предложении, находка, инструмент отметки.
- Вручную на дев-базе:
  1. завести модель монитора;
  2. вызвать находку, затем предложение с `forModelCreator`;
  3. утвердить в портале;
  4. проверить значения, `specUrl` и отметку;
  5. проверить, что повторный вызов находки модель не показывает.
- Cron агента настраивает владелец в OpenClaw по формулировке из `docs/mcp.md`.
