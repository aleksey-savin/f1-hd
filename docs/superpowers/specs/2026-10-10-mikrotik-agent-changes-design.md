# Изменения конфигурации Mikrotik по запросу ИИ-агента — дизайн

Дата: 2026-10-10. Статус: согласован владельцем в переписке, ждёт проверки текста.

## Цель

Сотрудник просит ИИ-агента: «сделай конфиг WireGuard для такого-то сотрудника».
Агент изучает роутер (инструменты чтения уже есть), готовит набор изменений и
отправляет его в HD. HD спрашивает людей, снимает бэкап, применяет изменения и
отдаёт результат. Агент сам на роутер не пишет никогда: у него есть только
«предложить» и «узнать статус».

Успех: запрос из примера проходит путь от фразы в Telegram до ссылки на
готовый `.conf`, а приватный ключ не видел ни агент, ни журнал.

## Что уже решено владельцем

| Вопрос | Решение |
|---|---|
| От чьего имени запрос | Агент называет человека (ключ общий) |
| Какие команды | Любые, кроме запретных |
| Где утверждают | Кнопкой в Telegram и на портале, со вторым шагом «Вы уверены?»; письмо ведёт на портал |
| Сбой команды | Остановиться и сообщить; с safe mode — откатить всё |
| Ответственный есть | Два подтверждения: заявитель, затем ответственный; одно лицо — один запрос |
| Название права | «Утверждать запросы ИИ-агентов по устройствам Mikrotik» |
| Safe mode | Использовать, если пройдёт проверка на `F1-VLD-GW01` (первая задача плана, запись на роутер разрешена владельцем) |

## Роли и права

**Заявитель.** Агент передаёт Telegram-id человека. HD находит по нему
сотрудника: привязанный и активный Telegram, не клиент, не заблокирован. Не
нашёл — отказ агенту с объяснением. HD верит агенту на слово, поэтому названный
человек ничего не получает автоматически: каждое решение принимает человек,
который сам вошёл в HD или нажал кнопку в своём Telegram.

**Право** `mikrotik.approveChanges`:

- название: «Утверждать запросы ИИ-агентов по устройствам Mikrotik»;
- пояснение: «Запрос меняет конфигурацию устройства: после утверждения команды
  выполняются на роутере клиента.»;
- новое действие ломает «полный доступ» у существующих ролей администратора,
  поэтому нужна разовая выдача по образцу `grantUpgradeFirmware.js`.

**Ответственный.** Новое поле `responsibleId` у записи Mikrotik. Ставит тот,
у кого `mikrotik.manage`; выбрать можно только сотрудника с правом
`mikrotik.approveChanges`. Если ответственный позже потерял право или
заблокирован, запись это показывает, а его шаг утверждения недоступен.

**Кто решает:**

| Ответственный | Заявитель | Шаги |
|---|---|---|
| есть, другой человек | право не требуется | 1) заявитель подтверждает «да, это просил я»; 2) ответственный утверждает |
| есть, он же заявитель | нужно право | один шаг |
| нет | есть право | один шаг: заявитель |
| нет | права нет | запрос не принимается: агент получает объяснение |

Запрос ответственному уходит только после подтверждения заявителя. Отклонить
может любой из двоих на своём шаге; отклонение окончательно.

**Кто видит запрос:** заявитель, ответственный, все с `mikrotik.approveChanges`
или `mikrotik.manageConfigs`. Только `mikrotik.read` — видит, что запрос есть и
его статус, без списка команд.

**Ключ агента.** Новый доступ `mikrotikChanges` («Изменения Mikrotik») —
отдельный флажок. Работает только вместе с включённым модулем Mikrotik.
Нынешний «Mikrotik» остаётся чтением.

## Что присылает агент

Структуру, не текст консоли:

```json
{
  "device": "F1-VLD-GW01",
  "requester": 123456789,
  "title": "WireGuard для Ивана Петрова",
  "reason": "Попросил А. Савин в Telegram: удалённый доступ новому сотруднику",
  "commands": [
    {
      "path": "/interface wireguard peers",
      "action": "add",
      "params": {
        "interface": "wireguard1",
        "allowed-address": "10.0.55.20/32",
        "public-key": "{{wireguard.public-key}}",
        "comment": "i_petrov"
      }
    }
  ],
  "wireguardClient": {
    "interface": "wireguard1",
    "address": "10.0.55.20/32",
    "allowedIps": ["10.0.20.0/24"],
    "dns": ["10.0.20.1"]
  }
}
```

- `action`: `add`, `set`, `remove`, `enable`, `disable`.
- `where` — для всего, кроме `add`: точное равенство по полям строки
  (`{"name": "peer7"}`). Запросов с подзапросами и регулярками нет.
- До 30 команд в запросе (safe mode помнит около 100 действий).
- `title` и `reason` — текст агента; в интерфейсе подписан «со слов агента» и
  проходит через `maskText`.

### Проверка при приёме

Всё, что ниже, — отказ агенту с причиной, запрос не создаётся.

**Запретные разделы** (по началу пути): `/user`, `/system`, `/file`, `/tool`,
`/import`, `/export`, `/certificate`, `/ip service`, `/ip ssh`, `/ppp secret`,
`/ip hotspot user`, `/user-manager`, `/container`, `/snmp community`,
`/radius`, `/password`, `/console`, `/port`, `/special-login`, `/tr069-client`,
`/ip socks`, `/ip proxy`, `/ip cloud`, `/disk`, `/ip ipsec key`, `/ip tftp`,
`/ip smb`, `/app`, `/partitions`, `/zerotier`. Сокращения имён меню и полей
(`/sys`, `/ip ser`, `lease-s`) приравниваются к полным.

**Запретные поля** в любом разделе: поля скриптов (`isScriptField` из
`configRedact.js`: `source`, `on-event`, `on-up`, `on-down`, любое `on-…`).

**Секреты.** В поле-секрет (`isSecretField`) нельзя передать значение — только
подстановку. Иначе секрет прошёл бы через агента. Подстановки первой версии:

- `{{wireguard.public-key}}` — HD создаёт пару X25519, в команду идёт публичный
  ключ;
- `{{wireguard.preshared-key}}` — HD создаёт ключ, он идёт и в команду, и в
  конфиг клиента.

**Форма значений.** Имя поля — `[a-z0-9][a-z0-9.-]*`. В значении запрещены
управляющие символы и перевод строки, длина до 500. Экранирование для консоли
делает HD (`"`, `\`, `$`, `?`); агент экранирования не пишет.

**Сверка с роутером.** HD читает раздел по API. Для `set`/`remove`/`enable`/
`disable` условие `where` должно найти ровно одну строку; найденная строка
(вычищенная `redactRow`) сохраняется как «было». Не нашлось или нашлось
несколько — отказ. Для `add` с уникальным именем — отказ, если такое уже есть.

**Пределы.** Не больше 5 незавершённых запросов на устройство и 20 предложений
в час на ключ.

### Пометка риска

Не запрет, а предупреждение в запросе и в сообщениях. Команда помечается
«может оборвать связь с устройством», если трогает `/ip address`, `/ip route`,
`/ip firewall filter` или `raw` с `chain=input`, `/ip firewall nat`,
`/interface` (`disable`, `remove`, `set`), `/interface bridge`, `/interface
vlan`, `/routing`, `/ip dhcp-client`, `/interface list`, а также `/ipv6 address`,
`/ipv6 route` и `/ipv6 firewall filter|raw` с `chain=input`. Запрос с такой
командой получает риск «высокий», остальные — «обычный».

### Что видит человек

HD собирает из структуры привычную строку RouterOS:

```
/interface wireguard peers add interface=wireguard1 allowed-address=10.0.55.20/32 public-key=<создаст HD> comment=i_petrov
/ip firewall address-list set [find where list=vpn-users address=10.0.55.19] disabled=yes
```

Для изменений рядом — «было → станет» по каждому полю.

## Ход запроса

```
предложен → ждёт заявителя → ждёт ответственного → в очереди → применяется → применён
                 │                    │                              ├→ откачен (сбой команды или потеря связи)
                 └→ отклонён ←────────┘                              └→ не применён (изменилась конфигурация, нет бэкапа)
           истёк (24 часа без решения)
```

1. **Предложение.** `propose_mikrotik_change` → проверки → запись → агент
   получает номер, статус и ссылку на страницу запроса.
2. **Уведомление текущему шагу** — Telegram, колокольчик, почта: устройство и
   компания, кто просит, зачем, команды, риск.
3. **Решение.** «Утвердить» → «Вы уверены? N команд на устройстве X» → «Да,
   применить». «Отклонить» — с необязательным комментарием (на портале).
   - В Telegram команды показываются целиком. Не помещаются в сообщение —
     кнопок решения в Telegram нет, только «Открыть в HD»: утверждать то, что
     не видел, нельзя.
   - Письмо всегда только со ссылкой.
4. **Очередь.** Один применяемый запрос на устройство; во время обновления
   прошивки применение ждёт.
5. **Перед применением**: повторная сверка — строки «было» не изменились;
   учётная запись HD на роутере имеет политику `write`; создаются ключи для
   подстановок. Изменилось — «не применён», всем участникам причина.
6. **Бэкап** — `createArtifact(record, { trigger: "pre-change" })`. Не снялся —
   «не применён».
7. **Применение** — см. ниже.
8. **Итог** заявителю и всем решавшим — в те же три канала. Агент узнаёт через
   `get_mikrotik_change`.

**Статус «Требует проверки»** (добавлен при реализации): HD не знает или не
может поручиться, что именно осталось на роутере — выход из safe mode не
подтвердился и повторное чтение показало часть команд; роутер перестал
отвечать и проверить нечем; применение оборвалось вместе с процессом; в
запасном режиме без отката команда не прошла. Запрос показывает, что увидела
проверка по каждой команде, и ссылку на бэкап. Повторно такой запрос не
применяется никогда.

Запрос без решения гаснет через 24 часа. Заявитель может отозвать свой запрос,
пока он не в очереди.

## Применение

Исполнитель скрыт за одним интерфейсом
`applyCommands(record, commands) → { results[], rolledBack, reachable }`.
Реализаций две, выбирает проверка из первой задачи плана.

**A. Safe mode держит SSH, команды идут по API (целевая).** Решение принято
после ревью правил приёма (10.10): консоль RouterOS принимает сокращения имён
меню и полей (`/sys scr`, `lease-s`, `private-k`) и требует экранирования —
вводить в неё текст, выведенный из запроса агента, нельзя. Поэтому в консоль
не вводится ничего, кроме Ctrl+X:

1. Интерактивная SSH-сессия, Ctrl+X — вход в safe mode; HD убеждается по
   приглашению, что режим взят. Не взят (его держит другой администратор) —
   «не применён».
2. Команды идут отдельной API-сессией, по одной. API требует точных имён,
   ничего не разбирает как текст и на ошибку отвечает `!trap`. Для `set`,
   `remove`, `enable`, `disable` HD сам находит строку по `where` и передаёт
   её `.id`.
3. Сбой команды → SSH-сессия закрывается без выхода из режима → роутер сам
   откатывает всё сделанное → статус «откачен».
4. Все команды прошли → HD ещё одним соединением проверяет, что роутер
   отвечает. Не отвечает — SSH-сессия рвётся, роутер откатывает.
5. Отвечает → Ctrl+X, выход из режима, изменения остаются.

Основание — документация MikroTik: safe mode отменяет изменения, сделанные и из
других сессий. Это проверяет первая задача плана. Побочный эффект: пока HD
держит режим (секунды), правки другого администратора тоже откатятся, если
сессия HD оборвётся.

**B. API без отката (запасная).** Если проверка покажет, что safe mode не
покрывает изменения из API-сессии: команды идут по API, первая ошибка
останавливает набор, применённое остаётся, статус «применён частично», в
запросе — что прошло, что нет, и ссылка на бэкап. После набора — проверка связи.

Ввод команд в консоль (вариант, с которого начинался дизайн) исключён в обоих
случаях. Строка RouterOS, которую видит человек, — только отображение.

В обоих случаях результат каждой команды пишется в запрос. Автоматического
восстановления из бэкапа нет.

## Конфиг WireGuard

Если в запросе есть `wireguardClient`, после успешного применения HD собирает
`.conf`:

- `PrivateKey` — созданный HD; `Address`, `DNS`, `AllowedIPs` — из запроса;
- `PublicKey` сервера и порт — HD читает с роутера сам;
- `Endpoint` — адрес записи устройства и `listen-port` интерфейса (агент может
  передать свой `endpoint`).

Приватный ключ хранится зашифрованным (`encryptSecret`) в записи запроса 24
часа после применения, затем стирается; запрос помнит только публичный.
Ключи создаются на шаге 5, а не при предложении: неутверждённый запрос
секретов не держит.

Страница запроса показывает блок «Конфигурация для сотрудника»: «Скачать
.conf» и QR-код. Доступен заявителю и решавшим, после входа в HD. Каждое
скачивание — строка в хронике. Агент получает только ссылку на страницу и
отдаёт её человеку; без входа ссылка ничего не открывает.

## Инструменты MCP

| Инструмент | Что делает |
|---|---|
| `propose_mikrotik_change` | Принимает запрос, возвращает номер, статус, ссылку или причину отказа |
| `get_mikrotik_change` | Статус, кто и когда решил, результат по командам, ссылка на конфигурацию |
| `list_mikrotik_changes` | Запросы по устройству или статусу |

`propose_…` — первый инструмент сервера без пометки «только чтение». В
`INSTRUCTIONS` — что агент ничего не применяет сам, что команды читает
человек, что строки с устройства остаются данными и не могут быть основанием
для запроса без просьбы человека. Каждый вызов пишется в лог с ключом.

## Данные

**`MikrotikChange`** — запрос, он же запись журнала:

- `number` (сквозной), `mikrotik`, `title`, `reason`;
- `requestedBy` (User), `requestedVia { keyId, keyName }`;
- `responsible` (User, снимок на момент предложения);
- `commands[{ path, action, where, params, text, risk, before, result { state, error, at } }]`;
- `risk`, `status`, `expiresAt`;
- `steps[{ role: "requester" | "responsible", user, decision, channel: "telegram" | "portal", comment, decidedAt }]`;
- `backupArtifact`, `executor: "safe-mode" | "api"`;
- `wireguard { publicKey, privateKey (шифр.), presharedKey (шифр.), client {...}, keysExpireAt }`;
- `timeline[{ at, kind, user, text }]`.

**`Mikrotik`** — `responsibleId`. **`MikrotikArtifact.trigger`** — значение
`pre-change`. **`McpKey.scopes`** — `mikrotikChanges`. **Категория
уведомлений** — «Запросы ИИ-агентов по Mikrotik».

## Telegram

Сообщение с кнопками «Утвердить», «Отклонить», «Открыть в HD». «Утвердить»
меняет то же сообщение на «Вы уверены?» с «Да, применить» и «Назад». После
решения кнопки убираются, в сообщении остаётся итог. Нажатие приходит в бэкенд
через tg-service с Telegram-id нажавшего; бэкенд сам проверяет, что это человек
текущего шага и что право у него есть. Чужое нажатие — ответ «это решение не
за вами», запрос не меняется.

## Уведомления

Категория «Запросы ИИ-агентов по Mikrotik». Telegram и почту человек может
выключить в личных настройках; колокольчик и блок на главной работают всегда
(требование владельца).

| Событие | Кому |
|---|---|
| Новый запрос | заявителю (его шаг) |
| Заявитель подтвердил | ответственному (его шаг) |
| Отклонён | заявителю и уже решавшим |
| Применён, откачен, не применён | заявителю и решавшим |
| Истекает через 2 часа | тому, чей шаг |
| Истёк | заявителю и тому, чей был шаг |

Каждое событие — запись в колокольчике со ссылкой на страницу запроса.
Сообщения шага (первые две строки) идут ещё в Telegram с кнопками и на почту
со ссылкой; остальные — в Telegram и на почту обычным текстом.

**Главная.** Блок «Запросы ИИ-агентов ждут вашего решения» со счётчиком —
первым в левой колонке, над заявками. Показывает только запросы, где текущий
шаг за смотрящим: название, устройство и компания, кто просит, число команд,
пометка риска, сколько осталось до истечения. Строка ведёт на страницу запроса.
Нет таких запросов — блока нет. Обновляется через существующий `/api/pulse`
(новая тема), без своего интервала.

## Интерфейс

Проходит через макет (обе темы, десктоп и телефон):

- блок на главной и записи колокольчика;

- раздел «Изменения» на странице записи Mikrotik;
- страница запроса: кто, зачем, команды с «было → станет», риск, шаги
  утверждения, хроника, результат по командам, бэкап, конфигурация;
- диалог «Вы уверены?»;
- поле «Ответственный» в форме записи;
- флажок «Изменения Mikrotik» у ключа агента;
- сообщение в Telegram (три состояния).

## Вне первой версии

- Восстановление из бэкапа и откат вручную.
- Скрипты, планировщик, перезагрузка, пользователи роутера.
- Один запрос на несколько устройств.
- Подстановки, кроме ключей WireGuard (пароли Wi-Fi, PPP).
- IPv6 в сверке риска.

## Риски

- **Агента можно уговорить текстом с устройства** (комментарий в конфиге).
  Защита — человек видит точные команды; запрос без названного человека не
  принимается.
- **Подмена заявителя агентом.** Меняет только то, кому придёт запрос;
  применить без человека с правом (или без ответственного) нельзя.
- **Потеря роутера.** Safe mode; при запасном варианте — только пометка риска
  и бэкап.
- **Разбор вывода консоли** в safe mode менее надёжен, чем API; покрывается
  проверкой на живом роутере и тестами на записанных ответах.
- **Изменение конфигурации между предложением и применением** — повторная
  сверка на шаге 5.

## Проверка

- Модульные тесты: проверки приёма (запретный список, секреты, форма),
  сборка строк и экранирование, правила шагов, разбор ответов консоли.
- Проверка safe mode на `F1-VLD-GW01`: вход, безобидное изменение, обрыв —
  откат; то же с нормальным выходом — изменение осталось; затем уборка.
- Сквозной прогон на проде на `F1-VLD-GW01`: пир WireGuard от предложения до
  скачанного конфига, отклонение, истечение, сбой команды.


## Отличия реализации от этого документа

Дополнено после реализации (10.10). Текст выше не менялся; действует код, описание — в `docs/mikrotik-changes.md`.

- Права учётной записи проверяются в воркере перед бэкапом по группе записи (`/user`, `/user group`): нужны политики `api`, `read`, `write`, `ssh`; не хватает — «Не применён» с названием политики. Группа не читается (нужна политика `policy`) — вердикта нет, применение идёт дальше.
- Подстановки допускаются только вместе с `wireguardClient`, только в `add` на `/interface wireguard peers` для интерфейса клиента и только в одной команде запроса.
- Риск firewall: для действий кроме `add` команда «высокая», пока `where.chain` не доказывает, что цепочка не `input`; значения `chain`, начинающиеся с `!`, тоже считаются `input`; после сверки риск пересчитывается по настоящей строке.
- Повторная сверка перед применением не сравнивает бегущие поля (счётчики, время, состояние связи, выданные клиентам значения); набор этих полей задан по разделам, неизвестный раздел сверяется почти точно; у записей `/ip firewall address-list` `timeout` может только уменьшиться.
- Для `set` повторная сверка сначала сравнивает точно те поля, которые команда меняет, затем всю остальную строку без бегущих полей раздела; для `remove`/`enable`/`disable` — всю строку без бегущих полей.
- Итог применения решает повторное чтение роутера, а не слова исполнителя; отправленная команда с таймаутом или обрывом не считается невыполненной (только отказ роутера `!trap`).
- Статус «Требует проверки» ставится и при перехвате safe mode другим администратором, при неподтверждённом выходе с неполной картиной, при частичном применении в режиме `api`, при прерванном применении (застрявший `applying` старше 10 минут).
- Ожидание применения (устройство обновляется, занято, не отвечает) ограничено 30 минутами, затем «Не применён»; в спеке предела не было.
- Резервная копия при возврате запроса в очередь используется повторно не дольше 10 минут и только если на устройстве не завершился другой запрос.
- Ключи WireGuard шифруются сразу после создания (до изменения роутера); не удалось зашифровать — «Не применён». В запись они попадают только при статусе «Применён».
- Повторные скачивания конфигурации разрешены, пока живы ключи (24 часа после применения); показ QR записывается в хронику не чаще раза в 10 минут на человека.
- Safe mode: в консоль пишутся только Ctrl+X и буква `d`; keepalive SSH-соединения держателя выключен по умолчанию (`MIKROTIK_CHANGE_KEEPALIVE=1` включает); проверка safe mode на живом роутере ещё не выполнена.
- Исполнитель выбирается переменной `MIKROTIK_CHANGE_EXECUTOR` (`safe-mode` по умолчанию, `api` — запасной).
- Пределы (5 незавершённых на устройство, 20 в час на ключ) проверяются под блокировкой в памяти одного процесса; в час считаются созданные запросы, отказанные предложения не считаются.
- В Telegram «Отклонить» действует сразу, без второго шага и без комментария; при решении на портале кнопки в уже отправленных сообщениях Telegram не убираются — при следующем нажатии бот заменяет сообщение причиной.
- Поля `telegram[]` в модели запроса нет: кнопки в уже отправленных сообщениях не снимаются.
- Добавлено уведомление об отзыве запроса заявителем: получает тот, чей шаг ждал (если это не сам заявитель).
- Итоговое уведомление «Требует проверки» имеет заголовок «Запрос № N требует проверки», суть и строку «Что известно».
- Обещание отката роутером в тексте «Вы уверены?» и в предупреждении о риске показывается только в режиме `safe-mode`; в режиме `api` текст говорит, что отката нет. Неизвестное значение `MIKROTIK_CHANGE_EXECUTOR` считается `safe-mode` (одна запись об ошибке в журнале).
- Сотрудник без прав на Mikrotik, не причастный к запросу, получает «не найден»; при `mikrotik.read` без причастности и без `approveChanges`/`manageConfigs` виден урезанный вид (номер, название, статус, дата, устройство).
- Утверждение действует 30 минут: запрос, у которого последнее утверждающее решение старше 30 минут, не применяется («Не применён»).
- Кнопки решения в Telegram есть, только если каждая команда показана целиком (строка команды до 600 знаков, значения «было» до 120, всё сообщение до 3500); иначе только ссылка, утвердить можно на портале.
- Повторная сверка перед применением проверяет, что под тем же `where` лежит та же строка (`.id`); для `set` сверяется и вся остальная строка, не только меняемые поля.
- Запрещённые разделы дополнены: `/ip tftp`, `/ip smb`, `/app`, `/partitions`, `/zerotier`; имя поля — не длиннее 64 знаков.
- Команды `set`/`enable`/`disable`, которые ничего не меняют, отклоняются при приёме.
- Первому по очереди сообщение о новом запросе отправляет сам вызов `propose_mikrotik_change`; письмо уходит в HTML (текст экранирован).
