# Инвентарь: группы характеристик, собираемые ПК, сборки-шаблоны

## Context

Владелец заводит каталог техники и хочет описывать её так же полно, как карточка
товара DNS («Характеристики»: группы «Процессор», «Оперативная память»… и в конце
«Конфигурация» — список деталей со ссылками). Повод — 19.10 он добавлял атрибуты
«Системному блоку» по одному и спросил, описывать ли ПК атрибутами или
комплектующими.

Решения владельца (19.10):
- **Заполнить можно всё** (полнота уровня DNS), но у ПК своей сборки
  характеристики **тянутся из комплектующих**.
- **Своя сборка — контейнер для комплектующих.** Схема касается **только
  устройств с меткой «Своя сборка»** (ветка мастера «Заводская / Своя сборка») и
  только «Системного блока»: у типа список обязательных комплектующих; на типе
  выбирается, какие характеристики комплектующих выводить в строке списка /
  шапке карточки устройства и сборки; остальные характеристики тоже собираются
  из деталей.
- **Заводские устройства** (ноутбуки, моноблоки, маршрутизаторы, коммутаторы,
  МФУ) описываются атрибутами — «такой ерундой не занимаемся». **Брендовый
  системный блок** (Dell, HP…) — обычная модель «Системного блока» с атрибутами:
  разобрать его на комплектующие нельзя и не нужно.
- **Сборка — шаблон**, из неё создаются устройства.
- **Каждая деталь — отдельная запись с серийником**: при своей сборке гарантия
  идёт на каждую комплектующую отдельно.
- Нужна **сущность группы** и **сид, который раскатывается при деплое**. Типы для
  сида: системный блок, моноблоки, ноутбуки, маршрутизаторы, коммутаторы, МФУ.
  Дальнейшие сиды владелец будет заказывать точечно.
- Порядок работ — три проекта подряд (ниже); каждый: макет → «ок» → код.

Что есть сейчас (проверено 19.10):
- Значения атрибутов живут **только** в `DeviceConfiguration.values`
  (`[{attributeId, value: String}]`), конфигурация принадлежит модели. У
  `ClientDevice` своих значений нет; «своя сборка» (`deviceTypeId` без модели)
  характеристик не имеет вовсе.
- Форма конфигурации (`components/DeviceConfiguration/Form.jsx`) строит поля по
  связкам типа в их порядке; `multiselect` рисуется простым полем ввода;
  `required` — только звёздочка, сервер ничего не проверяет. `extendable` нигде
  не работает.
- Показ: карточка модели — сетка карточек конфигураций (`DeviceModel/View.jsx`,
  `buildRows`, `formatAttrValue`); карточка устройства — блок «Характеристики»
  (`ClientDevice/View.jsx:566`), значения сырые (populate без `valueType/options`).
- Детали: `parentDeviceId` + `quantity`; «Состав сборки» на карточке
  (`ClientDevice/View.jsx:668`), добавление — `NewComponentDialog` /
  `AttachComponentDialog`, без конфигурации. В мастере создания деталей нет
  (убраны в a79b96c).
- Прод 19.10: 31 устройство, **0 заполненных значений** во всех конфигурациях
  (одна пустая конфигурация у МФУ) — переносить нечего. В каталоге атрибутов
  есть почти-дубли («Тип памяти» / «Тип оперативной памяти», «Максимальный объем
  памяти» / «Максимальный объём памяти», «Слотов памяти» / «Количество слотов для
  оперативной памяти»).
- `DeviceType.configurationIds` мёртв; `deviceType.add/update` игнорируют
  `attributes[]`, `InlineCreateDialog` шлёт их зря.
- Связано: дизайн MCP-инвентаря (`2026-10-16-mcp-inventory-design.md`, не
  реализован) опирается на «характеристики деталей только из моделей» — с этим
  дизайном совместимо; его план надо будет сверить с группами и сборками.

## Цели

1. Группы характеристик и вид «как DNS» везде, где показываются значения.
2. Сид каталога (группы, типы, атрибуты, связки, слоты) с журналом, который
   раскатывается деплоем — и на существующей базе, и на чистой установке.
3. Собираемые типы: слоты комплектующих, ключевые характеристики, сборки-шаблоны,
   характеристики сборки и устройства, собранные из деталей.
4. Создание ПК из сборки: каждая деталь — запись с серийником, покупкой и
   гарантией.

## Не цели

- Фильтр по значению (▽ у DNS) и подсказки (i) у атрибутов — позже.
- «Расширяемый список» (`extendable`) — остаётся как есть, не реализуется.
- Собственные характеристики у устройства «Своя сборка»: всё берётся из
  деталей (ОС — поле устройства `operatingSystem`). Атрибуты типа описывают
  только его брендовые модели.
- Автоматическая чистка дублей каталога на проде — только список для владельца.
- Вложенные сборки (деталь, у которой свои детали).

## Анти-цели (провал, даже если работает)

- Сид, который при повторном деплое воскрешает переименованное или удалённое
  владельцем, или перезаписывает его правки.
- Брендовый ПК, который заставляют описывать комплектующими, или своя сборка,
  которую заставляют описывать атрибутами.
- Вторая форма атрибута или детали (правило одной FormFields на сущность).
- Характеристики ПК, которые надо вводить руками, когда детали известны.
- Деталь без собственной записи (нельзя отследить гарантию).

## Проект 1. Группы и вид характеристик

### Данные

- **`AttributeGroup`** (новая, глобальный каталог): `name` (уникально без учёта
  регистра), `order` (глобальный канонический порядок групп), аудит.
  Порядок общий для всех типов: «Процессор» всегда выше «Оперативной памяти».
- **`DeviceTypeAttribute.groupId`** → `AttributeGroup`, необязательный. Группа
  задаётся **на связке**: один атрибут может стоять в разных группах у разных
  типов («Wi-Fi» — «Сеть» у ПК, «Беспроводная сеть» у маршрутизатора). Без группы
  — блок «Прочее» в конце.
- Порядок строк внутри группы — существующий `order` связки.

### Вид «как DNS» (общий компонент, напр. `app/SpecSheet`)

- Группа — жирный заголовок; под ним строки в **две колонки, сверху вниз
  сначала левая** (как у DNS); на телефоне одна колонка.
- Строка: серая подпись (переносится), пунктирная направляющая, значение.
- Форматирование значения по `valueType`: Да/Нет; подпись опции для
  select/multiselect; число + единица.
- Пустые значения не показываются; пустая группа не показывается.
- Где: каждая конфигурация на карточке модели; блок «Характеристики» карточки
  устройства (заводского). Бэкенд отдаёт в populate `valueType`/`options` и
  группы связок.

### Редактирование

- Карточка типа: атрибуты сгруппированы по группам; перетаскивание и
  «Выше/Ниже» — внутри группы.
- «Изменить» связки: поле «Группа» (выбор из каталога + создание новой).
- Шторка «Добавить атрибуты»: «Группа для отмеченных» — одна на пачку.
- Форма конфигурации: поля разбиты по тем же группам; `multiselect` получает
  мультивыбор (сейчас простое поле).
- Управление группами (переименовать, порядок, удалить неиспользуемую) — по
  макету; минимум — небольшой список в разделе каталога.

### Сид и деплой

- **`scripts/seed.js`** — раннер сидов с журналом `seeds` (по образцу
  `migrate.js`): упорядоченный список `{ id, script }`, каждый сид применяется
  **один раз** и записывается. В отличие от миграций, на **чистой** базе сиды
  тоже прогоняются (новой установке нужен каталог).
- `deploy.sh`: шаг сидов после миграций, при каждом деплое (ждать нечего — шаг
  ничего не делает). Команда `./deploy.sh seed status|up|mark <id>`; на деве —
  `docker compose run --rm backend node scripts/seed.js up`.
- **Правила сида:** только добавляет. Существующее подхватывает по `code` или
  `name` без учёта регистра (атрибуты — с учётом устаревшего индекса `name_1`),
  типы и группы — по `name`. Чужие поля не перезаписывает, кроме пустых
  (`groupId` у связки без группы). Ничего не удаляет.
- Первый сид `2026-10-19-inventoryCatalog`: группы, типы комплектующих и
  заводские типы с атрибутами и группами, слоты и ключевые характеристики
  «Системного блока» (данные проекта 2 — сид идёт после его кода; см. «Порядок»).
  Содержимое — приложение A.
- `initializeInventoryData.js` заменяется сидом (константа
  `MIKROTIK_VENDOR_NAME` переезжает в `seedMikrotikModels.js`). Документы
  `deployment.md`, `mikrotik-management.md`, `inventory.md` обновляются.

## Проект 2. Собираемые типы и сборки

### Данные

- **`DeviceType.assembly`**: `{ enabled, slots: [{ typeId, required, multiple,
  order }], keySpecs: [{ typeId, source: "model" | "attribute", attributeId?,
  aggregate: "first" | "sum" | "list", order }] }`. Действует **только на
  устройства «Своя сборка»** этого типа; модели типа (брендовые ПК) остаются
  заводскими и описываются атрибутами типа, как все.
  - Слот = тип комплектующей (один слот на тип). `multiple` — деталей этого
    типа может быть несколько (память, накопители).
  - Ключевая характеристика — из детали слота: название модели (`model`) или
    значение атрибута; `sum` — сумма по деталям с учётом количества (2 × 8 ГБ =
    16 ГБ), `list` — различные значения через запятую, `first` — первое.
  - В слоты можно ставить только типы-комплектующие (`isComponent`).
  - Атрибуты типа остаются (они для брендовых моделей); карточка типа
    показывает и атрибуты, и отдельную секцию «Своя сборка» — слоты и ключевые
    характеристики.
- **Сборка — отдельная сущность `DeviceBuild`**, не модель: модели — только
  заводские. Поля: `name`, `deviceTypeId` (тип с включённой сборкой), `parts:
  [{ typeId, deviceModelId, configurationId?, quantity }]`, `notes`, мягкое
  удаление, аудит. Список сборок — секция «Сборки» на карточке типа (и выбор в
  мастере устройства); в списке моделей сборок нет.
- Характеристики детали = конфигурация её модели. `configurationId` нужен,
  когда у модели детали их несколько; у модели с одной конфигурацией
  подставляется она.

### Характеристики сборки (общий сервис, напр. `services/assemblySpecs.js`)

Вход — список деталей (`{typeId, model, configuration, quantity}`), выход:
- `keySpecs` — по `assembly.keySpecs` типа;
- `groups` — строки всех деталей в группах проекта 1, в глобальном порядке
  групп; внутри группы — по порядку слотов, затем по порядку связок. Одинаковые
  детали слота схлопываются («2 ×»); разные — отдельными блоками («Накопитель 1»,
  «Накопитель 2»);
- `parts` — группа «Конфигурация»: слот → деталь со ссылкой.

Один и тот же сервис считает характеристики сборки (из `parts`) и устройства (из
фактических деталей, проект 3).

### Экраны (по макету)

- Карточка типа с включённой сборкой: секция «Своя сборка» — слоты (тип,
  обязательный, несколько) и ключевые характеристики; секция «Сборки» — список
  сборок с ключевыми характеристиками в строке.
- Карточка сборки: ключевые характеристики в шапке, «Характеристики» из деталей,
  «Конфигурация» — список деталей; форма сборки — выбор модели детали по каждому
  слоту + количество. Обязательные слоты обязательны.

## Проект 3. ПК из сборки

- Форма устройства: «Своя сборка» + тип с включённой сборкой → выбор сборки
  или разовая сборка без шаблона (детали по слотам вручную). «Заводская сборка»
  и «Своя сборка» прочих типов не меняются. Шаг «Комплектующие» заполнен из сборки: **одна
  строка на единицу** (2 × 8 ГБ — две строки), в каждой модель (можно сменить),
  серийник, дата покупки, гарантия до, поставщик. Детали создаются отдельными
  `ClientDevice` с `parentDeviceId` и следуют за хостом (компания, место,
  пользователь, статус — как сейчас при прикреплении).
- Устройство хранит, из какой сборки создано: новое поле `ClientDevice.buildId`
  (только у «Своей сборки»; `deviceModelId` по-прежнему только у заводских — и
  устройство по-прежнему никогда не бывает и тем и другим).
- Карточка устройства: ключевые характеристики в шапке, «Характеристики» из
  **фактических** деталей, «Конфигурация» вместо «Состава сборки» (детали со
  ссылками, серийниками, гарантией); пометка, чем устройство отличается от
  сборки (заменена/добавлена/снята деталь); предупреждение, если не хватает
  обязательного слота.
- Строка списка устройств: у своих сборок собираемого типа — ключевые
  характеристики в мете; у остальных без изменений.
- `NewComponentDialog` получает выбор конфигурации модели детали.

## Ограничения

- Mongo без replica set: многошаговые записи проверяют всё до первой записи и
  откатывают созданное по списку `_id`. Удаление — только по явному списку `_id`.
- Права: каталог (группы, типы, слоты, сборки) — `inventoryCatalog.manage`;
  устройства и детали — `device.manage`.
- UI — только через макет (обе темы, десктоп + телефон), примитивы из
  `components/app`, тексты по «Словарю действий» («Новая группа», «Новая
  сборка»).
- Код атрибута и группы в интерфейсе не показывается; коды атрибутов сида —
  стабильные латинские.
- Тесты — `node:test` на затронутые файлы (сервис характеристик, раннер сида,
  разбор слотов).

## Решения исполнителя (мои, проверить)

- Группа — на связке, порядок групп — глобальный.
- Сид с журналом и прогоном на чистой базе, отдельно от миграций.
- Сид ставит `isComponent: true` типам комплектующих, которые подхватывает по
  имени (на проде это касается «Блока питания»: сейчас он не комплектующая и
  у него одна модель). Это единственная перезапись чужого поля.
- Ключевые характеристики «Системного блока» по умолчанию: процессор (модель),
  объём памяти (сумма), тип памяти, объём накопителей (сумма) + тип, видеокарта
  (модель).
- **Совпадение с уже существующим атрибутом при сиде.** Подхватывается как есть;
  у select/multiselect дописываются недостающие варианты (только добавление). Если
  тип значения расходится с приложением A, атрибут всё равно подхватывается, а
  расхождение пишется в лог сида и в список владельцу. `sum` считает только
  числа: нечисловое значение пропускается. (На проде 19.10 из конфликтных есть
  только «Диагональ экрана» — `num, дюймов`, совместима; `initializeInventoryData`
  на проде не прогонялся.)
- **`quantity` у детали остаётся.** Детали из сборки создаются по одной записи на
  единицу (у каждой свой серийник), но деталь без серийников с `quantity > 1`
  (например, 4 одинаковых вентилятора) законна; характеристики и `sum` умножают на
  `quantity`, сравнение со сборкой считает единицы. Существующие записи не
  делятся (на проде 19.10 одна прикреплённая деталь).
- **Не-слотовые подключения** (периферия, расходники, комплектующие типов без
  слота) у собираемого устройства остаются: отдельный блок «Подключено» под
  «Конфигурацией», в характеристиках и в отличиях от сборки не участвуют.
  Прикреплять их можно, как сейчас (`attachableToTypeIds`).
- **Включение сборки — в форме типа** («Своя сборка — из комплектующих»).
  Включить можно всегда (модели типа не затрагиваются); выключить — пока у типа
  нет сборок. Слоты и ключевые характеристики правятся на карточке типа.
- **Сбой сида останавливает деплой** так же, как сбой миграции: шаг идёт после
  миграций и до старта сервисов, повторный `./deploy.sh` продолжает с
  неприменённого сида (сид идемпотентен за счёт подхвата по имени).

## Владельцу после выкатки (не в коде)

- Список почти-дублей атрибутов и старых атрибутов «Системного блока» и
  «Моноблока», которые сид не подхватил, — решить, что слить или удалить.
- «Имя компьютера», «Гарантия», «Срок эксплуатации» как атрибуты — у устройства
  для этого есть поля.

## Приложение A. Содержимое первого сида

Обозначения: тип значения — `str`, `num`, `bool`, `sel(…)`, `msel(…)`; единица
после «,». Один атрибут каталога может стоять у нескольких типов (Сокет, Тип
памяти, Стандарт Wi-Fi, габариты, Цвет).
