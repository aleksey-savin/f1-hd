# Словарь прав: редизайн (2026-09-11)

## Контекст

Словарь прав (`backend/auth/access.js`) переехал на роли better-auth в августе
2026, но набор действий и их подписи достались от плоских флагов
(`canAdministrateTickets`, `canUseTimeTrackingModule`, …). Разбор словаря по
блокам с владельцем 11 сентября показал четыре системные проблемы:

1. **Подписи не говорят, что дают.** «Категории заявок», «Регламентные
   задания», «Отчёт по работам» — существительные без глагола: видеть? менять?
   Группа «Шаблоны заявок» держит четыре разные сущности и названа по одной из
   них.
2. **У прав есть скрытые значения.** `report.employees` открывает отчёт и
   заодно оклады в карточке человека, деньги в работах и конвейер
   согласования. `ticket.administrate` обрабатывает новые заявки и заодно
   расширяет пять чужих списков. `report.works` — отчёт, которого нет.
3. **Права не проверяются там, где обещают.** `knowledge.manage` не стоит ни
   на одном маршруте; `supplier.read` мёртв (все маршруты требуют `manage`);
   мутации заявки не проверяют отношение к записи.
4. **Тип аккаунта и роль перемешаны.** Клиентские роли держат права, которые
   в клиентском интерфейсе не работают (`work.log`, `company.read`,
   `createForOthers`), а форма роли показывает клиентской роли пятьдесят
   строк сотрудника.

Этот документ — согласованный словарь целиком, правила, по которым он собран,
и карта переезда. Реализация — отдельным планом.

## Принятые решения

- **Один словарь на оба типа аккаунта.** Отдельных «клиентских» и
  «сотруднических» прав нет. У каждого действия есть **адресат**
  (`audience`: `staff` | `client` | `both`). Форма роли показывает только
  строки адресата роли. Право адресата `staff` у клиентского аккаунта не
  действует, даже если роль его даёт: сервер отбрасывает такие действия при
  разрешении прав клиента.
- **Подпись = глагол + сущность.** «Видеть X» открывает раздел X, его список и
  карточки. «Изменять X» заводит, правит и удаляет. Особые глаголы — только
  там, где они и правда особые (брать в работу, вести, согласовывать,
  модерировать, входить под пользователем).
- **У каждой справочной сущности — пара `read` / `manage`.** Ровно два права
  на сущность; отдельных «создать / изменить / удалить» нет — ни одна роль не
  нуждалась в «создать без удалить». Заявки — не справочник, а процесс: у них
  свои глаголы.
- **Выпадающий список внутри чужой формы права не требует.** Выбор категории в
  форме заявки, вендора в форме устройства, услуги в форме компании — часть
  права на ту форму. Право «Видеть X» — про раздел X. Списки для выпадашек
  сервер отдаёт любому сотруднику (по типу аккаунта).
- **Своё — без права.** Свой график, свои отсутствия, свои шаблоны заявок,
  свои работы, свои заявки, свой профиль. Право нужно на чужое и на раздел.
- **Каждая мутация проверяет отношение к записи.** У заявок это
  `canAccessTicket` на каждом изменяющем маршруте; у работ — доступность
  заявок; у шаблонов и работ — авторство либо право «на все».
- **Скрытых значений у права нет.** Если экран показывает деньги, у него есть
  своё право на деньги. Если человек модерирует базу знаний — это право, а не
  список в настройках.
- **Настройки — одно право.** Секции настроек правами не делятся.
- **Отложено намеренно (не в этом объёме):** подтверждение и закрытие
  клиентом своей заявки (переделка процесса завершения заявки); «средний»
  скоуп для пользователей и компаний (сотрудник видит всех).

## Словарь

Идентификаторы — `ресурс.действие`; менять их из интерфейса нельзя. Колонка
«Адресат»: `staff` — только сотрудникам, `client` — только клиентам, `both` —
обоим, при этом тип аккаунта ограничивает объём (клиент никогда не видит чужую
компанию). Подсказка (`hint`) показывается под подписью в форме роли; у прав
`both` есть вторая подсказка для клиентской роли (`clientHint`).

### Заявки (`tickets`)

| Действие | Подпись | Адресат | Что даёт |
|---|---|---|---|
| `ticket.readCompanies` | Видеть заявки своих компаний | both | Сотрудник: все заявки компаний, за которые он отвечает (список ответственных в карточке компании), включая новые без исполнителя. Клиент: все заявки своей компании |
| `ticket.readAll` | Видеть все заявки | staff | Все заявки всех компаний |
| `ticket.perform` | Брать заявки в работу | staff | Принять, присоединиться, запросить помощь, изменить срок, отказаться, закрыть, вернуть в работу; отмечать пункты чек-листа; составлять и править чек-лист своей заявки, если она не из регламента; инструменты ИИ. Попадает в списки исполнителей |
| `ticket.manage` | Вести заявки | staff | Обработать новую, назначить и снять любых ответственных, изменить тему, категорию, описание, ответы анкеты, компанию и инициатора, вложения заявки, чек-лист любой заявки, включая регламентные. Получает уведомления менеджера (отказ исполнителя) |
| `ticket.delete` | Удалять заявки | staff | Удалять доступные заявки, по одной и списком |
| `ticket.createForOthers` | Заводить заявки за других | both | Сотрудник: любой инициатор любой компании и ответственные. Клиент: инициатор — коллега своей компании; компания всегда своя, ответственных клиент не указывает |
| `ticket.closeWithoutWork` | Закрывать без записи о работе | staff | Как сегодня |

Без всех прав чтения человек видит заявки, где он инициатор, автор или
ответственный. «Своя» заявка для `perform` — та, где он в ответственных.

**Что меняется в поведении:**

- Инициатор, автор и ответственный по-прежнему видят заявку без прав.
- Клиент с `createForOthers` получает в анкете поле «Инициатор» (коллеги своей
  компании, по умолчанию он сам); сервер принудительно ставит компанию
  клиента и игнорирует присланных ответственных и чужую компанию. Сегодня это
  право у клиента не работает в интерфейсе, а через API позволяет завести
  заявку на чужую компанию.
- Тема, категория, описание, компания, инициатор — только `manage`.
  Исполнитель их не правит: описание, меняющееся посреди решения, путает
  всех. Клиент свою заявку не правит вовсе.
- Вложения самой заявки — только `manage`. Исполнитель и клиент прикладывают
  файлы через комментарии (комментарии уже принимают вложения).
- Чек-лист: исполнитель составляет и правит его на своих заявках, кроме
  заявок из регламента (`ticket.routineTask`); отметки — `perform` на своих.
- Скоуп списка заявок — три яруса: свои → своих компаний → все.
- Побочные эффекты `administrate` уходят по адресам: списки пользователей и
  компаний — под `user.read` / `company.read`; категории — свободный список;
  плитки шаблонов на главной — `ticketTemplate.read` или все сотрудники;
  уведомления менеджерам — держателям `manage`.
- «Вернуть в работу» свою закрытую заявку у клиента — право инициатора по
  типу аккаунта, не право словаря (уже реализовано в `ticket-actions.js`).

## Сквозные правила

### Адресат действия

- Словарь: у действия поле `audience` (`staff` по умолчанию, `client`,
  `both`) и `clientHint` для `both`. `GROUPS` едет на клиент в `/api/me`
  как сегодня — с новыми полями.
- **Разрешение прав** (`services/permissions#effectivePermissions`): для
  аккаунта с `isEndUser` действия адресата `staff` из набора вырезаются.
  Для сотрудника вырезаются действия адресата `client`. `isFullAccess`
  считается по полному словарю до вырезания (администратор — сотрудник,
  ему вырезать нечего).
- **Форма роли**: матрица показывает только строки адресата роли; группы без
  строк не рисуются, рейл собирается из видимых групп, счётчик «N из M»
  считает видимые. Смена адресата снимает действия чужого адресата и
  показывает их в блоке «Что изменится» со знаком «−». Макет — канва
  «Форма роли»: https://claude.ai/code/artifact/dddd9e4e-aeca-4ebf-a584-2cc8a170c14c
  (четыре артборда: десктоп и мобайл в обеих темах; роль сотрудника — 16
  групп, клиентская — 9).
- **Каталог ролей**: фасет «Права» показывает подписи из словаря; блок «Права
  без своей роли» считает по адресату (право `client` без клиентской роли —
  дыра, право `staff` без роли сотрудника — дыра).
- `assertNotEscalating` не меняется: выдать можно только то, что есть у
  самого.

### Скоуп по типу аккаунта

Одна функция на ресурс, а не условие в каждом контроллере:

- `services/ticketScope.js` — `ticketListFilter(auth)` (свои / своих компаний
  / все) и `canAccessTicket(ticket, auth)` с тем же набором ярусов.
- Клиент: `company`, `user`, `device`, `work`, `servicePlan`, `knowledge`,
  `approval` — всегда ограничены его компанией поверх любого права. Это
  правило уже есть у устройств и архива работ (`scopeMatch`,
  `getFinished`); распространить на компании и пользователей.

### Проверка отношения к записи

Маршруты заявок: `update`, `process`, `delete`, `delete-multiple`,
`take-to-work(-multiple)`, `close(-multiple)`, `request-help`,
`join-responsibles`, `update-deadline`, `reject`, `add-attachments`,
`remove-attachment`, `update-checklist(-item)`, `ai-*`, `speech-to-text` —
все через `requireTicketAccess` / `assertTicketsAccessible`. Сегодня это есть
только у `back-to-work` и комментариев.

### Списки для выпадашек

Эндпоинты `GET /ticket-categories`, `GET /vendors`, `GET /service-plans`,
`GET /checklist-templates`, справочники техники — `isAuth` + `isNotClient`
(тип аккаунта), без права словаря. Страницы разделов — за `read` в `handle`
маршрута (`RouteGuard`) и в `util/sections`.

## Что видно человеку после переезда

- Первая и вторая линии видят всех пользователей и все компании и могут
  завести заявку на любую компанию (сегодня — только на «свои»).
- Клиент-администратор получает карточку своей компании, справочник коллег,
  услуги компании и сегмент «Работы» в архиве; офис-менеджер клиента — поле
  «Инициатор» в анкете.
- Исполнитель без `manage` теряет кнопку «Изменить» на заявке (сегодня её и
  так только у администратора), но получает чек-лист на своих заявках.
- Сотрудник без `schedule.read` начинает видеть свой график и свои
  отсутствия.
- Модераторы базы знаний назначаются ролью, а не списком в настройках.
- Раздел «Люди» называется «Пользователи».

### Где применяется

1. **Словарь** — `backend/auth/access.js`: новые группы, подписи, `audience`,

2. **Каталог ролей** — `backend/scripts/roles.catalogue.json` пересобирается
   по карте выше (это сид для прода, который на better-auth ещё не переехал);
   у клиентских ролей снимаются права адресата `staff`. Новая роль
   `kb-moderator` «Модератор базы знаний» (audience `staff`,
   `knowledge.read`, `knowledge.moderate`); `members` — текущий список
   модераторов из настроек дева, проверить по проду перед окном.
3. **Живые роли дева** — скрипт `backend/scripts/migrateActions.js` по образцу

## Что может пойти не так

- **`isFullAccess` и адресаты.** Полный доступ считается по всему словарю;
  если вырезание применить до сравнения, администратор перестанет узнаваться.
  Порядок: разрешить роли → проверить полноту → вырезать по типу аккаунта.
- **Сотрудник с клиентской ролью.** Роль клиента у сотрудника даёт ему
  действия `client` (например, `approval.decide`), которые сервер вырежет:
  человек увидит роль в карточке, но не её эффект. Каталог ролей показывает
  адресата роли; форма пользователя уже ставит чужие роли ниже и гасит.
- **Пересборка каталога.** `dumpRoleCatalogue.js --apply` собирает сид из
  базы дева; после `migrateActions.js --apply` на деве сид пересобирается
  оттуда, а не правится руками, кроме `members` / `matches`.
- **Прод без better-auth.** На проде роли ещё не назначены; там действует
  только сид и `assignRoles.js`. Ничего из этого документа на прод не
  выкатывается раньше миграции better-auth.
