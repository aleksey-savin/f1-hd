# UX/UI Guide

Документ описывает UI-конвенции приложения, как они сложились в коде, чтобы
новые экраны выглядели и работали единообразно. Это свод правил, а не строгая
спецификация: при расхождении с кодом прав код — ориентируйтесь на него и
обновляйте этот файл.

Четыре вещи, которые задают формат документа:

- **Гайд описывает только целевую систему** (Tailwind + shadcn/ui). Миграция с
  react-bootstrap закончена 01.08.2026 — bootstrap удалён из приложения
  целиком, и его конвенции здесь не описаны.
- **У правила ровно одна формулировка.** Если правило нужно и в другом
  разделе — там стоит ссылка «см. …», а не вторая редакция. Единственное
  исключение — «Чек-лист перед мерджем UI»: он намеренно повторяет уже
  сказанное короткими строками.
- **Гайд описывает решения, а не устройство разделов.** Правило — то, что
  применимо к следующему экрану. Как устроен конкретный компонент (эндпоинты,
  DTO, пропсы) — в JSDoc самого компонента; почему стоит хак — в комментарии
  рядом с хаком; счётчиков и списков-инвентарей не держим, если на них есть
  источник истины в коде.
- **История отделена от правил.** Хронология решений, отвергнутые варианты и
  «почему так» — в «[Журнале изменений](./ux-ui-changelog.md)», а что осталось
  доделать — в «Хвостах эндшпиля».

## Стек и базовые принципы

- **React + react-router** (data router: `loader`/`action`, `useFetcher`,
  вложенные маршруты).
- **UI-стек: Tailwind v4 + shadcn/ui** (см. раздел «Инфраструктура» ниже) — им
  построено всё приложение.
- **react-icons**, набор **Remix (`Ri*`)** — источник иконок приложения
  (подробнее — раздел «Иконки»).
- **zustand** для UI-состояния (`store/mobile-filter-offcanvas.js`,
  `store/toast-store.js` …),
  **Context** для темы (`store/theme-context.jsx`; он же ставит класс `.dark`
  на `<html>`).
- **Выпадающий список один на приложение — `app/Combobox`** (Popover + cmdk).
  Второго селекта в приложении нет (см. «Раскладка полей внутри формы»).
- Отдельные ветки **`BrowserView` / `MobileView`** (`react-device-detect`) там,
  где десктоп и мобайл расходятся по раскладке.
- Весь UI-текст — **на русском**. Семантику передаём вариантами компонентов и
  токенами (`primary`/`success`/`destructive`…), а не произвольными цветами.

## Инфраструктура целевой системы

Эталоны: **списки** — справочник «Вендоры» (`pages/Vendor/*`, пилот;
серверная выборка — «Пользователи», богатая строка — «Компании»),
**настройки** — «Мой аккаунт» (`pages/User/MyAccount.jsx`), **карточка** —
«Услуга» (`ServicePlan/View.jsx`), **мастер** — `ServicePlan/Form.jsx`.

- **Шире 1280 — только через токен контейнера.** Встроенная шкала кончается на
  `max-w-7xl`; карточке заявки этого мало (рейл 192 + хроника 384 оставляют
  секциям 656, и виджет «Окружение» в них не помещается). Заведён
  `--container-8xl: 90rem` в `@theme` — утилита `max-w-8xl` появляется сама,
  произвольных значений в разметке не пишем.
- Токены темы — `src/styles/tailwind.css` (`:root`/`.dark`; класс `.dark` на
  `<html>` ставит `ThemeProvider`). Радиус `0.5rem`, шрифт — **Inter**
  (self-hosted `@fontsource-variable/inter`, объявлен в `@layer base`).
  Канва страницы — токен `--canvas` (на узком экране светлая тема кладёт
  `--background`: под контентом во всю ширину серая подложка не видна, а
  полоса у краёв читается как сбой).
- Утилиты — **только из встроенной сетки**: произвольных значений вида
  `text-[15px]` не пишем; кегли и высоты — по ролям из «Типографики». `cn()` —
  из `@/lib/utils`.
- shadcn-компоненты — `src/components/ui/*.tsx` (генерирует CLI):
  Button/Badge/Alert расширены вариантами `success`/`warning`/`info`
  (+ `light` у Alert). Сгенерированный код руками не перекраиваем —
  расхождения с доками shadcn чинятся токенами или точечно.
- **Preflight включён** и служит единственным глобальным резетом. Из-под
  выключенного preflight остались две привычки, менять которые незачем:
  интерактивные элементы задают `appearance/border/bg/no-underline` явно, а
  правило `*,::before,::after { border-color: var(--border) }` в `@layer base`
  подменяет preflight-дефолт `currentColor` — иначе голый `border` в
  сгенерированных компонентах даёт светлые рамки меню в тёмной теме.
- **`.md-doc` ужимает картинки чужого html** (описание заявки, письмо, заметка
  базы знаний): в них приезжают жёсткие `width`/`height` из почтового клиента.
  Правило скоуплено на класс; вешать его на голый `img` нельзя — прежняя
  редакция так и делала, перебивала размеры любых картинок приложения и
  заставляла рисовать превью фоном на `div`.
- z-index: radix-оверлеи подняты до 1100 (блок `[data-slot=…]` в
  `tailwind.css`). Бар оболочки — инлайн `zIndex: 1030`, кнопка «наверх» —
  1040, рейл статусов — 1020: tw-сетка z заканчивается на 50, поэтому шкала
  оболочки задаётся стилем.
- **Скролл-лок radix**: меню (`ui/dropdown-menu`) лок не вызывают вовсе —
  переведены на `modal={false}`. Модальные оверлеи (Dialog/AlertDialog/Sheet)
  лочат законно, и «прыжки» лэйаута сняты системно в `index.css` (механика — в
  комментарии там же). **Пиксельные компенсации фиксед-элементов не
  использовать** — они не покрывают фоновую картинку и полосят.
- **Палитра статусов присутствия — per-theme токены `--ws-st-*`**
  (`styles/tailwind.css`): каталог `util/work-statuses.js` отдаёт
  `color: "var(--ws-st-…)"` — годится **только** для CSS-контекстов, копии
  каталога у бота и бэкенда остаются на hex. Классы бара статусов
  (`User/WorkStatusBar.jsx`) живут в `index.css` — только вне-сеточное.
- Страницы рендерятся **на «листе»** — плашке цвета карточки (скругление +
  тонкая граница + `p-4`, паттерн content sheet). Лист **обнимает контент, а не
  тянется на всю ширину**: `maxWidth` листа = контентная ширина страницы (её
  `max-w-*`) + паддинг, значения — в конфиге `MIGRATED_ROUTES` в Root (новый
  маршрут добавляется туда парой «путь + ширина»; имя историческое — миграция
  закончена, но список ширин нужен по-прежнему). По бокам остаётся канва — с
  фактурой или с обоями; пустых полей-«карточек» нет.
  Лист появился ради фактуры: пока канва была ровной заливкой, страницы жили
  прямо на ней и это работало, но заголовок, фильтры и чипы на клетке для
  повседневной работы утомительны. Плотному интерфейсу нужна спокойная
  подложка.
  Листа НЕТ в двух случаях: на телефоне (там канва спокойнее, а ширины на поля
  вокруг листа нет) и в **чистом виде** — личной настройке «Мой аккаунт →
  Внешний вид → Фон приложения», которая заодно выключает фактуру и обои и
  возвращает прежнюю раскладку.
  Из-за fixed-слоя обоев **любой контент канвы обязан быть `position:
  relative`** (контент-обёртка — уже в Root; `Footer` — сам `relative` и на
  десктопе тоже становится плашкой-«листом»), иначе fixed-слой рисуется поверх
  и элемент «пропадает».

**Откуда пришли — штатным `state` навигации роутера.** Ссылка в ЧУЖОЙ раздел
кладёт в переход подпись своей страницы (`<Link state>` → `useLocation().state`),
крошка на той стороне её читает. Своей истории приложение не ведёт: `state`
лежит в записи History API, поэтому переживает перезагрузку, а «назад» и
«вперёд» сами отдают то значение, что было у своей записи.

Подпись собирает `useCrumbFrom(label)` из `app/Crumbs`: адрес источника он
считает сам (`useResolvedPath(".")` — адрес своего маршрута, чтобы возврат вёл
на карточку, а не в открытую над ней шторку правки; `search` — текущий, чтобы
список вернулся с фильтрами). У `app/EntityLink` для этого проп `from`, у
голых `<Link>` — `state={fromState}`.

**Переход ВНУТРИ раздела подписи не требует**: из списка в карточку крошка и
так назовёт раздел по справочнику. Проп нужен ровно там, где раздел меняется, —
ради этого случая он и заведён.

**Справочник разделов** — `util/sections`: адрес списка, название и право на
него. Один источник для крошек и для контекстных 404 (`Error/entity-context`).
Сопоставляется **самым длинным подходящим `listTo`**, а не порядком в массиве:
у `MIGRATED_ROUTES` порядок load-bearing и требует комментариев-предупреждений,
здесь раздел, дописанный не в то место, соседний закрыть не может.

**Каталог компонентов `src/components/app/`** (двойники примитивов приложения;
эти — вместо ручной сборки и вместо легаси `src/UI/*`; подробные правила — в
тематических разделах, на которые ссылаются строки):

| Компонент | Назначение |
|---|---|
| `ListWrapper` | Каркас страницы-списка: заголовок + счётчик, поиск, сортировка, чипы (`toolbar`), кнопка создания (`addLabel`), панель списка, шторка форм (`FormOutlet`; гасится `renderOutlet={false}`), Sheet-фильтр, плашка `activeFilters`, шапка режима выбора (`selection`), пустые состояния (`emptyTitle`/`emptyHint`/`emptyAction`); серверный режим — `count`/`belowList`/`aboveList`/`hasActiveQuery`. Правила — «Анатомия списка с фильтром» |
| `FormWrapper` | Оболочка формы: `fetcher.Form`, заголовок (или свой `header` — липкая шапка), ошибки/успех, «Отмена»/«Сохранить», закрытие и навигация по успеху. Тело — FormData по умолчанию, `json` для вложенных объектов, `formData` когда в форме файлы (вернуть `null` — отменить сабмит и показать ошибки полей) — см. «Формы → нижняя шторка» |
| `FormOutlet` | Хозяин шторки форм-маршрутов — вместо `<Outlet/>` у списков, карточек и главной: открыта, пока совпадает маршрут с `handle.sheet` (константы `SHEET_MD/LG/XL`); закрытие — сперва анимация, потом переход (`useFormSheet().close`); `useSheetOpen()` — для пауз фонового обновления. См. «Формы → нижняя шторка» |
| `FormSheet` | Сама нижняя шторка (radix Sheet снизу): ширина — проп `size`, измеренная высота, на мобайле всегда почти весь экран. Формы-маршруты приносит в неё `FormOutlet`; напрямую — для форм вне маршрутов (`Team/AbsenceForm`). Шкала и поведение закрытия — см. «Формы → нижняя шторка» |
| `FormLayout` | Каркас длинной формы в шторке: именованные `FormHeader` (липкий заголовок, отдаёт свою высоту наружу; `children` — тихий контрол при заголовке) + `FormSections` (секции одним скроллом, `AnchorRail` слева — гасится пропом `rail={false}`, прокрутка к `#hash`). Default-экспорта нет — импортируем по имени. См. «Большие многошаговые формы» |
| `Field` | Поле формы: лейбл + `required`-звёздочка + контрол + `hint`. Проп `error` вытесняет `hint` (сообщение `destructive`); `aria-invalid` на контрол ставит вызывающий |
| `BrandMark` | Марка приложения: логотип арендатора (`contacts.logo`) или текстовый `Help`+`Desk`. Общая для бара оболочки и пред-авторизационных экранов. Своей картинки у приложения нет: логотип не задан — никакого знака, только слово |
| `PasswordInput` | Поле пароля с кнопкой показа; иконка сообщает состояние (скрыт — перечёркнутый глаз), а не действие. Показ можно взять под управление (`shown`/`onShownChange`), вторую кнопку кладут в `extra` с классом `adornmentButtonClass` |
| `PasswordPolicyField` | Поле нового пароля: живой вердикт (длина + число вхождений в утечки, спрашивается у сервера) и генератор с бегунком длины. Единственный способ задать пароль — см. «Пароль на экране» |
| `SwitchField` | Строка свитча: свитч + подпись + hint + скрытый input `"true"/"false"` для FormData (`name`) |
| `ListRow` | Строка списка: имя + мета, «⋯»-меню (Изменить/Удалить + `extraActions`); плитка слева только по `thumbSrc` (превью, с кольцом) или `glyph` (глиф вида, без кольца) — правило в «Анатомии списка с фильтром»; клик — правка или, с пропом `detailTo`, карточка (см. «Страница сущности»); права — `canManageEntity`. Свежесозданную строку подсвечивает сам |
| `ListGroupLabel` | Uppercase-метка группы со счётчиком (`tone="on"/"off"`) |
| `FilterChip` | Чип-фильтр с точкой-индикатором (`active`) |
| `ChipSelect` | Дропдаун-чип **одиночного выбора без поиска** — ключевой фасет с коротким набором значений; «Все …» сбрасывает (`clearable`). См. «Ключевой фасет» в анатомии списка |
| `ChipCombobox` | Дропдаун-чип с **поиском** (Popover + shadcn Command/cmdk) — фасет с длинным списком значений; `clearable={false}` — обязательный контекст без пункта сброса |
| `ChipMultiCombobox` | **Мульти**-фасет с поиском, значение — массив id (компании/пользователи в фильтре шаблонов) |
| `Combobox` | **Единственный селект приложения** — поле формы с поиском (Popover + Command), не чип. Меню в слое radix, поэтому работает и в шторке, и в диалоге. Пропы сверх очевидных: `required` (нативная валидация через скрытый спутник-input), `loading`, `name` (кладёт значение в FormData), `ariaLabel`, `clearable`. Именованный `MultiCombobox` — то же с множественным выбором: токены внутри поля, меню не закрывается, `name` даёт по скрытому полю на значение. Опции строит `toOptions(items, {value, label, hint, group, disabled})`: `group` делит список заголовками («Ведут категорию» / «Остальные»), `disabled` оставляет вариант видимым, но невыбираемым — когда его отсутствие было бы враньём |
| `DeleteItem` / `DeleteDialog` | Подтверждение удаления — см. «Диалоги» |
| `ConfirmDialog` | Подтверждение действия вне router-action (архивация заметки, уход с несохранённым): заголовок · абзац · «Отмена»/действие с вариантом |

**Правила:**

- **Каждый новый экран начинается с HTML-макета** (артефакт: десктоп + мобайл,
  обе темы), который согласовывается с Алексеем до написания кода; код
  повторяет макет пиксельно. Эталон языка — макет «Вендоров»: группы-метки
  со счётчиками, цветной статус-текст вместо заливных бейджей, бирюзовое
  главное действие (плитки-монограммы того макета сняты 07.09 — см.
  «Анатомия списка с фильтром»).
- Компоненты — только shadcn и каталог `app/*` выше; ручная сборка того, что
  уже есть в каталоге, — ошибка ревью.
- **Верификация**: `pnpm build` + `pnpm lint` (+ `pnpm typecheck`) — и передать
  Алексею на проверку в живом UI (он проверяет сам и говорит, если что-то не
  так). Playwright-проходку самостоятельно не устраивать — только по явной
  просьбе (рецепт: mint JWT в `hd-backend-1`, `addInitScript` с localStorage).

## Типографика

Шкала — встроенная сетка Tailwind, своих `--text-*` токенов нет. Тело
приложения — **14px** (`text-sm`); у каждой роли один класс, у каждого кегля —
роль. Всё, что не в таблице, наследует тело.

| Роль | Класс | px |
|---|---|---|
| Заголовок страницы (`ListWrapper`, `PageShell`) | `text-3xl leading-none font-semibold tracking-tight` | 30 |
| Счётчик у заголовка страницы | `text-xl font-medium text-faint tabular-nums` | 20 |
| Hero h1 карточки сущности | `text-2xl font-semibold tracking-tight` | 24 |
| Заголовок формы (`FormWrapper`, `FormLayout`) | `text-xl font-semibold tracking-tight` | 20 |
| Заголовок диалога, шторки, пустого состояния | `text-lg font-semibold` | 18 |
| Заголовок секции h3 | `text-base font-semibold` | 16 |
| Eyebrow, подпись секции настроек, метка группы | `text-xs font-bold tracking-wider uppercase text-faint` | 12 |
| Заголовок строки любого списка | `text-base font-medium` | 16 |
| Мета строки, подсказка, вторичный текст | `text-sm text-muted-foreground` | 14 |
| Тело: карточки, хроника, панели, баннеры, описание | `text-sm` (описание заявки — `text-base leading-relaxed`) | 14 (16) |
| Числа, даты, чипы, служебные строки | `text-xs` | 12 |
| Подпись поля (`Field`, `SettingRow`, `SwitchField`, `ui/label`) | `text-sm font-semibold text-muted-foreground` | 14 |
| Контролы в ряду: Input, Textarea, Combobox, чипы, поиск, пункты меню | `text-sm`, высота `h-10` | 14 / 40 |
| Кнопка default · sm · xs · lg | `h-10` 14 · `h-9` 14 · `h-8` 12 · `h-11` 16 | |
| Icon-кнопка default · sm · xs · lg | `size-10` · `size-9` · `size-8` · `size-11` | |
| Плитка/аватар строки списка | `size-12`, глиф `size={22}` (инициалы аватара — `text-base`); hero-плитка карточки — `size-14`, глиф `size={26}` | 48 / 56 |
| KPI (`StatTile`) | `text-3xl font-bold tabular-nums` | 30 |

- **У `text-lg` и `text-xl` ровно по одной роли** (заголовок диалога; заголовок
  формы и счётчик). «Свободных» ступеней, которые берут «чтобы было чуть
  крупнее», нет — такое место просит роль из таблицы.
- **Строка списка — тело плюс одна ступень, не заголовок.** Справочная строка в
  24px читалась как стопка заголовков форм; заголовок строки — 16, мета — 14,
  одинаково у справочников, заявок, людей, техники, заметок и дерева.
- **В одном ряду контролы одной высоты и одного кегля.** Input, Combobox, чипы и
  поиск стоят `h-10 text-sm`; кнопка рядом — `h-10`. Поле в 16px при соседях в
  14 и Textarea, менявший кегль на `md`, — то, откуда берётся ощущение
  «зоопарка».
- **Вторичный текст на одну ступень ниже тела, не на две.** Мета и подсказки —
  14, служебные числа и чипы — 12; 10–11px в интерфейсе нет.
- **Произвольных `text-[Npx]` нет.** Пересчёт в токены: 10–12.5px → `text-xs`,
  13 → `text-sm` (в плотных сетках вроде плана помещения — `text-xs`), 15 →
  `text-sm`, 0.9375rem → `text-sm`.
- **Рейл статусов и блок «Команда сейчас» — строки 14/12** (`User/PresenceList`):
  боковая панель шириной 336 и плотный блок, а не список-страница.
- **Таблицы данных и графики — своя шкала**: `ui/table` и отчёты остаются
  14/12, подписи осей в SVG — px (`components/Report/*`); их не подтягивают к
  ролям выше.
- **Markdown-тела (`.md-doc`) кегль получают от обёртки**: правило в `index.css`
  лишь перебивает 13px Toast UI через `inherit`, размер задаёт утилита на
  контейнере.
- **Личный масштаб 125%** масштабирует корень (см. «Тема и цвет»); поэтому
  ритм оболочки и ширины страниц — в rem, а любой px-расчёт в JS читает корень
  из `getComputedStyle(document.documentElement).fontSize`.

## Когда что использовать (главное правило выбора контейнера)

| Ситуация | Контейнер | Референс |
|---|---|---|
| Подтверждение, короткий вопрос, мелкий диалог (1–3 поля) | **AlertDialog/Dialog** | `components/app/DeleteItem.tsx` |
| Заполнение/редактирование формы (add/update сущности) | **Нижняя шторка**: вложенный маршрут с `handle.sheet`, хозяин `app/FormOutlet` (в `app/ListWrapper` встроен) | `pages/Vendor/*` |
| Большая многошаговая форма (мастер) | Шторка `lg` (896) + степпер во всю ширину + живая сводка справа | `ServicePlan/Form.jsx` |
| Фильтры списка (общие для десктопа и мобайла) | Sheet сбоку (в `app/ListWrapper`) | `components/app/ListWrapper.tsx` |
| Предпросмотр записи списка/дерева («заглянуть», не уходя) | **Шторка: справа на десктопе, снизу на мобилке**: крошки/статус/ключевые поля + вложенная навигация; главное действие — «Открыть карточку». Справа, потому что список остаётся виден (можно щёлкать следующую строку не закрывая) и потому что нижняя шторка на десктопе занята формами; на 390 px правая вырождается в полный экран, там нижняя. **Оправдан в двух случаях: у записи есть дети, к которым и ходят** (расположение, филиал), **или за строкой лежит документ, который читают по ходу дела** (подсказка базы знаний в заявке — читают, не уходя с заявки). Для плоской записи, которая и так ведёт на карточку, предпросмотр — лишний щелчок на пути: у списка заявок его завели и отменили (см. changelog 30.07) | `components/Location/PreviewSheet.jsx`, `Ticket/View/KnowledgeSection.jsx` |
| Список/таблица как «всплывающая» панель | Шторка снизу | эталона нет — и не нужен, пока не появится задача: единственный живой пример был легаси-дашбордом и удалён вместе с ним |
| Правка **документа** (заметка, статья) | **На месте, на той же странице** | `components/KnowledgeBase/NoteView.jsx` |
| Массовые действия над выделением | `app/BulkActionBar`: плавающая панель (десктоп) + остров `app/MobileActionBar` | `components/KnowledgeBase/NoteBulkActionBar.jsx` |

Границы этих случаев разобраны в «Формы → нижняя шторка», «Диалоги → только
мелкие вещи» и «Большие многошаговые формы» — таблица только выбирает
контейнер.

## Раскладка страницы

`layout/Root.jsx` задаёт каркас:

- **Десктоп** (`BrowserView`): фиксированный **бар оболочки на tw**
  (`layout/Navbar.jsx`): панель поверхности 56px с тонкой нижней границей в
  обеих темах; бренд — лого компании из настроек или текст «Help**Desk**»;
  пункты и разделы — из конфига `layout/Navigation/menu.js` (иконки только
  `Ri*`; раздел виден, если виден хотя бы один его пункт; в баре — короткая
  подпись, полное название — в дропдауне и drawer). На **< xl** меню
  сворачивается в бургер-Sheet (`layout/NavDrawer.jsx`, общий с мобильным
  шеллом). Меню пользователя — **Popover, не DropdownMenu** (внутри инпут
  заметки статуса, radix-меню ломает его typeahead'ом). **Статус в меню —
  чипы, не список**: сетка 2×2 (в офисе, не на работе, на выезде, обед) и
  строка во всю ширину для самой длинной подписи («на удалёнке»), текст по
  центру — в узкой ячейке ничего не режется; «сбросить» — у заголовка секции, только когда
  статус задан; заметка — одно поле, сохраняется по Enter и при уходе из
  поля, кнопки нет. В меню только ручные статусы каталога: отпуск и болею
  ставят заявки, руками — из карточки человека, поэтому их нет даже у
  администратора. **Рейл статусов** (`User/WorkStatusBar`, только ≥ `lg`) —
  табло присутствия у правого края: свёрнут до колонки кругляшей, раскрытый
  **стоит в потоке и сдвигает контент**, а не накрывает его (сам он fixed,
  место резервирует оболочка — `has-ws-rail` / `has-ws-rail-open` по
  состоянию `store/work-statuses`, запоминается на устройстве). **Норма
  молчит**: «не на работе» и «не указан» свёрнуты в строку со счётчиком, в
  свёрнутом рейле — кружок «+N»; кольца и имена — у тех, кто на связи, и у
  исключений (отпуск, больничный). Сводка в шапке — от доступности («3 на
  связи · 2 на выезде», вечером — «никого на связи · смена с 09:00»), футер —
  «Обновлено сегодня в 13:40». Присутствие есть и там, где принимают решение:
  в выборе ответственных заявки у каждого точка статуса и строка «в офисе ·
  с 09:12», на связи — первыми внутри своей группы. Контент —
  контентная обёртка `maxWidth: 1920px` с отступами `px-12`. Двухпанельную
  раскладку рисует сама страница (см. «Правка на месте»); страницы живут прямо
  на канве (конфиг ширин — в «Инфраструктуре»).
- **Мобайл** (`MobileView`): нескроллящийся app-shell — см. раздел
  «Мобильная навигация».
- Тосты — sonner, снизу справа (см. «Обратная связь»).

Списочные страницы собираются `components/app/ListWrapper`: заголовок +
счётчик рядом, справа поиск / сортировка-текст-дропдаун / чипы / кнопка
создания «Новый …» с текстом. Состав и порядок этих контролов — в «Анатомии
списка с фильтром».

## Мобильная навигация (app-shell)

На мобайле (`MobileView` в `layout/Root.jsx`) весь UI — **нескроллящийся app-shell**
`.mobile-shell` (`position:fixed; height:100dvh; display:flex; flex-direction:column;
overflow:hidden`). Скроллится только средняя область `.mobile-shell__scroll` (`<main>`);
верхний бар и нижний таб-бар — её соседи по флексу, **а не `position:fixed`**. Это
структурно убирает баг iOS Safari, где фиксированные панели «всплывали» посреди экрана
при инерционном скролле. Десктоп (`BrowserView`) сохраняет прежнюю схему (`fixed-top`
`Navbar` + `paddingTop:100px`).

```text
.mobile-shell                         position:fixed, 100dvh, flex-column, overflow:hidden
├─ <NavigationBar embedded />         верхний бар: .navbar.mobile-shell__header (в потоке)
├─ <main .mobile-shell__scroll>       единственный скролл-контейнер
│    └─ <Container> <Outlet/> <Footer/> </Container>
└─ <MobileBottomNavbar />             плавающий «остров»: .mobile-tabbar (absolute)
```

**Нижний таб-бар — `layout/MobileBottomNavbar.jsx`** («плавающий остров»):

- Скруглённый бар с `backdrop-filter: blur`, парит над краем
  (`position:absolute; bottom: calc(10px + env(safe-area-inset-bottom))`).
- Вкладка = иконка (`Ri*` — см. «Иконки») + короткая подпись;
  тач-таргет ≥ 44px.
- Активная вкладка — бирюзовый акцент (`--tab-active: var(--primary)`) и
  пилюля, которая **плавно
  скользит** между вкладками через `framer-motion` `layoutId` + `LayoutGroup`
  (с уважением `useReducedMotion`). Пилюлю центрируем через `inset`, а **не**
  `transform`: framer сам управляет `transform`, иначе выделение «съезжает».
- Набор вкладок — конфиг-массив, фильтруется по правам/`isEndUser` (как в меню).
  Активность считается явно; маршруты взаимоисключающие → ровно одна активная
  вкладка (инвариант: одна пилюля на `layoutId`).
- Обязательны `aria-label` и `aria-current` на вкладках (иконки — `aria-hidden`).

**Верхний бар (мобайл)** — тот же `NavigationBar` с пропом `embedded`: статичный
флекс-ребёнок (`.mobile-shell__header`, safe-area-паддинги в `index.css`) на
tw-классах. Гамбургер + бренд + чип статуса (Popover с `WorkStatusSwitcher`).

**Команда на телефоне** — не лента в шелле, а блок «Команда сейчас» на
главной сотрудника (`Dashboard/TeamNow`, только `MobileView`): по умолчанию
закрытая плашка — живая точка, сводка от доступности, стопка аватаров; по
тапу раскрывается в то же табло, что в рейле. Лента над каждым экраном стоила
56 px ради информации, которая нужна изредка.

**Бургер-меню** — `layout/NavDrawer.jsx` (Sheet слева, общий для мобильного
шелла и узкого десктопа): шапка с аватаром и ролью, скруглённые строки
навигации из конфига `menu.js` (разделы — `Collapsible`), футер —
`app/ThemeSegment` + «Мой аккаунт» + «Выйти».

**Правила (важно):**

- **Не вешать слушатели скролла на `window`** на мобайле — он не скроллится (гейт
  `isBrowser` в `UI/BackToTop.jsx`); нужен скролл — слушать `.mobile-shell__scroll`.
- Панели навигации на мобайле — **никогда не `position:fixed`** (только флекс/absolute
  внутри shell), иначе вернётся «дрейф».
- Сброс скролла при навигации — вручную (`mobileScrollRef` + `useEffect` по
  `location.pathname` в `Root.jsx`; router `ScrollRestoration` не используется).
- Тема навигации — scoped-токены `--nav-*` / `--tab-*` / `--tabbar-*` в
  `index.css` **ссылаются на токены новой системы**
  (`var(--border)`/`var(--card)`/`var(--primary)`) — тёмные значения даёт класс
  `.dark`, отдельных переопределений в `dark-theme.css` больше нет.
- `index.html`: `viewport-fit=cover` + `theme-color`; safe-area учитывается и сверху,
  и снизу.

## Контекстный остров действий на мобилке

`app/MobileActionBar` — мобильная половина `app/BulkActionBar` (заявки:
bulk-действия; база знаний: bulk-модерация и правка заметки). Портал в
`.mobile-shell`, классы `.mobile-actionbar*` в `index.css`. Новый код берёт
`app/BulkActionBar` и получает обе поверхности сразу; напрямую остров зовут
только там, где десктопной панели нет (правка заметки).

- **На экране всегда ровно один плавающий объект.** Пока панель в DOM,
  `.mobile-shell:has(.mobile-actionbar) .mobile-tabbar { visibility: hidden }` —
  таб-бар уступает ей место, «бутерброд» из двух плашек невозможен структурно.
- **Заблокированное действие остаётся нажимаемым и объясняет причину**: на
  тач-экране hover-тултипа нет, поэтому тап на 4 секунды подменяет строку статуса
  причиной (`reason`). Причина называет объекты **по имени** (заголовок заметки,
  номер заявки), а не по внутреннему id.
- Один массив `actions[{ key, icon, label, reason, danger }]` — источник правды и
  для десктопной плавающей панели, и для мобильного острова.
- Цветом выделено ровно одно действие (обычно разрушающее, `is-danger`); смысл
  несёт подпись под иконкой. Тач-таргет ≥ 44px, `role="toolbar"`,
  `useReducedMotion`.

## Анатомия списка с фильтром

Порядок сверху вниз (каркас — `app/ListWrapper`; эталоны — списки
«Пользователи» и «Компании»):

1. Кнопка создания («Новый X») и **поиск** — в шапке `ListWrapper`.
2. **Сегментный переключатель набора данных** (`app/Segmented`) там, где
   наборы взаимоисключающие («Активные | Архив»; «Все | Мои» у компаний —
   скрывается, если не сужает). Два независимых свитча для взаимоисключающих
   наборов — ошибка: их приходится синхронизировать руками, и пользователь не
   видит, что они спорят.
3. **Ключевой фасет в строке инструментов** — дропдаун-чип: `app/ChipSelect`
   (без поиска), `app/ChipCombobox` / `app/ChipMultiCombobox` (с поиском);
   правило выбора — ниже. Счётчик в чипе считается по загруженному набору,
   поэтому на серверной выборке его не показываем — он посчитает страницу, а
   не всю выборку (см. «Список на серверной выборке»).
4. **Очереди/спецфильтры** — только тем, у кого есть права.
5. **Sheet-фильтр с полным набором условий** — прячет длинные мультиселекты и
   отдаёт вертикаль списку (правило ниже).
6. **Сортировка** — текст-дропдаун (встроена в `ListWrapper`). Счётчик — у
   заголовка страницы.
7. Список; при группировке — заголовки групп со счётчиком
   (`app/ListGroupLabel`; статусные группы — язык статус-борда, как в
   «Вендорах»: активные бирюзой, отключённые гаснут).

Правила:

- **Не рендерить заголовок секции, если её содержимое скрыто правами.** Пустой
  `<h5>Модерация</h5>` между двумя `<hr>` у обычного сотрудника — это баг.
- **Список по умолчанию показывает всё, что пользователю видно.** Не требовать
  запроса или фильтра, чтобы данные вообще появились: бэкенд уже отдал ровно
  разрешённое, а фильтр — инструмент сужения, а не открывания.
- **Группировка выключается сама, если группа осталась одна** — заголовок с
  единственной группой не несёт информации.
- **Свежесозданную и только что изменённую строку подсвечивает сам
  `app/ListRow`** — по `createdAt`/`updatedAt`, поэтому **API списка обязан их
  отдавать**: компактная проекция без отметок времени тихо гасит подсветку.
- **Плитка слева — только когда она различает строки.** Настоящая картинка
  (логотип компании, фото модели — `thumbSrc`, с кольцом по краю) или глиф
  вида в смешанном списке (`glyph`: принтер/ноутбук/роутер из `deviceIcon` у
  моделей и в реестре устройств, без кольца). У однородного справочника
  плитки нет — название и мета начинаются от отступа панели, разделители
  тоже. Буквы в плитке (монограмма названия) и одна иконка раздела на все
  строки — ошибка: они повторяют то, что уже сказано названием и заголовком
  страницы. В списке с картинками слот остаётся у всех строк, даже когда
  картинки нет (иначе названия не выстроятся в колонку): запаска — тихий глиф
  раздела, блёклый и без кольца (`Company/CompanyLogo`). Кольцо — только у
  картинки. Люди — исключение: круглый аватар с инициалами (см.
  «Строка-человек»). Макет — артефакт «Плитка строки списка».
- **Пустое состояние предлагает действие**: «Ничего не нашлось. Измените запрос
  или сбросьте фильтры», а не «Список пуст». В `ListWrapper` оба встроены:
  «Ничего не нашлось» + «Сбросить фильтры» при отфильтрованном в ноль
  (`hasActiveQuery`), «Список пуст» + кнопка создания при пустых данных.
- Мобильная страница списка собирается тем же `ListWrapper` (в мигрированном —
  поиск всегда виден, кнопка «Фильтр» → Sheet с `FilterContainer`, сортировка
  справа). Если страница рендерит `<Outlet/>` сама — передайте
  `renderOutlet={false}`, иначе маршрут смонтируется дважды.
- **Фильтр есть на каждой странице справочника**: Sheet (`filter` проп
  `ListWrapper`) с полным набором, общий для десктопа и мобайла. В строке
  инструментов живёт **только ключевой фасет** (правило ниже): повторно
  индицировать уже применённое там незачем — это работа плашки `activeFilters`.
  Примитив `app/FilterChip` — для мест **вне** `ListWrapper`.
- **Ключевой фасет сущности** (взаимоисключающие значения) выводим одним из двух
  способов — выбор фиксируем при согласовании макета, единообразно в пределах
  страницы:
  - **дропдаун-чип `app/ChipSelect` в строке инструментов** (`toolbar` проп) —
    быстрый доступ рядом с поиском; выбранное видно в самом чипе, сброс —
    пунктом «Все …». Живой пример: «Тип устройства» на странице атрибутов
    (`pages/DeviceAttribute/List.jsx`);
  - **одиночный `app/Combobox` внутри Sheet-фильтра** — когда фасет уместнее рядом
    с прочими условиями, а не отдельным чипом; первая опция «Любое/Все …»
    сбрасывает фасет. Живой пример: «Назначение» на странице типов
    (`components/DeviceType/Filter.jsx`; «Основные устройства» = тип без
    спец-флагов). Список значений фасета выносим в отдельный модуль
    (`components/DeviceType/kinds.js`), раз его читают и фильтр, и бейдж.
  В обоих случаях применённое значение дублируется **снимаемым бейджем** в
  липкой плашке (`activeFilters`).
- **Фасет со счётчиками — это ещё и сводка** (канон «сводка = переключатель»,
  см. «Экраны-конвейеры»): когда значения фасета сами по себе отвечают на
  вопрос о множестве («сколько техники готово к выдаче»), они выносятся лентой
  в `topContent` — чип на значение, число рядом, клик сужает список. Живой
  пример — лента парка на странице «Устройства»
  (`components/ClientDevice/FleetStrip.jsx`). Два условия обязательны:
  **числа считает сервер по всей выборке**, а не по загруженной странице, и
  **счётчики фасета считаются без него самого** — иначе выбранное значение
  обнуляет соседние, и лента перестаёт отвечать на свой вопрос. Значение с
  нулём в ленте не рисуется (кроме выбранного — иначе выбор исчезал бы
  из-под пальца).
- **Применённые фильтры всегда видны**: страница передаёт в `ListWrapper`
  `activeFilters=[{ key, label, onRemove }]` — липкий «остров» бейджей над
  списком (виден и при проскроленном в конец списке), каждый бейдж снимается
  крестиком, рядом «Сбросить» (сбрасывает стор и очищает поиск). Лейблы —
  человеческие («Тип: Число»), не значения полей.

### Режим выбора нескольких записей

Клик по строке ведёт на карточку — это правило всего приложения, и выделение его
не отменяет: выделение живёт **в отдельном режиме**. Каркас — `app/SelectionBar`
(слот `selection` у `ListWrapper`) + `hooks/use-list-selection`; действия —
`app/BulkActionBar`. Живой пример — список заявок.

- **Два входа, одно состояние.** Чекбокс строки (проявляется по наведению) —
  быстрый путь; кнопка-иконка «Выбрать» в строке инструментов — обнаружимость
  и та же явная модель «режима», что у долгого тапа на мобилке.
- **`Cmd/Ctrl+click` не занимаем**: браузер держит его под «открыть в новой
  вкладке», и отбирать эту привычку нельзя. По той же причине строка остаётся
  настоящей ссылкой `<a href>`, а чекбокс лежит **рядом** с ней, а не внутри
  (интерактивный элемент внутри ссылки невалиден).
- **У чекбокса нет своего жёлоба.** Он лежит поверх штатного отступа строки
  (20 px, как у любого списка) и по наведению проявляется, а **номер сдвигается
  на 24 px** в своей колонке — тема и остальные колонки стоят. Проявление с
  задержкой 200 мс: пролёт курсора по списку ничего не двигает. В режиме сдвиг
  делается один раз для всех строк и держится до выхода; на мобилке наведения
  нет — чекбокс появляется только в режиме, и сдвигается всё содержимое
  строки, как в любом режиме правки. Резервный жёлоб под чекбокс читался как
  пустой отступ в начале каждой строки, а замена номера чекбоксом прятала бы
  единственный идентификатор, который с этого списка читают.
- **В режиме клик по строке переключает выбор**, `Shift+клик` берёт диапазон от
  предыдущей тронутой строки.
- **Мастер-чекбокс трёхпозиционный**: пусто/часть → выбрать всё, всё → снять
  выделение (режим остаётся). «Выбрать все N» — вся текущая выборка, а не
  страница и не видимая часть.
- **Выход — «Отмена» или Escape**; снятие последней галочки режим не выключает.
  Escape уступает открытому диалогу: закрывая его, человек отказывается от
  действия, а не от выбора.
- **Долгий тап (450 мс) — вход на мобилке**: отменяется сдвигом больше 10 px
  (прокрутка важнее жеста), подтверждается вибрацией; строке нужен класс
  `.longpress-target` (`index.css`), иначе iOS покажет превью ссылки.
- **Одна липкая плашка на экран**: пока режим включён, липкая — шапка выбора, а
  плашка `activeFilters` прокручивается как обычная.
- **Фоновое автообновление на паузе**, пока идёт выбор: иначе список поедет
  под курсором, а выделение частично протухнет.

### Бюджет управляющих элементов

Считайте пиксели до первой строки данных. Каждый контрол в этом списке стоит
40–44 px, и все они кажутся полезными по отдельности: кнопка создания, поиск,
переключатель набора, чипы фасетов, очереди, аккордеон фильтров, сортировка.
Семь рядов — и в колонке шириной в треть экрана видно три записи из двухсот.

- **Главное действие — иконка рядом с поиском**, а не залитая кнопка во всю
  ширину. Ряд экономится целиком.
- **Редко трогаемое — в Sheet-фильтр**, а плашка `activeFilters` показывает
  всё применённое, включая набор данных и выключенные фасеты. Применённый
  фильтр не бывает невидимым.
- **Набор одинаковых кнопок-режимов — в одну кнопку-меню со счётчиком.** Четыре
  очереди модерации с заголовком секции — это ~100 px; иконка со значком `5` и
  дропдаун — 31 px, и разбирают очередь не каждый день.
- **Сортировка — ссылка-дропдаун**, а не полноразмерный селект на 40 px: её
  меняют раз в сессию.
- **Строка состояния вместо всегда видимых индикаторов**: контекст («Архив»,
  «Очередь: На проверку»), «Найдено: N», «Сбросить» — только когда есть что
  сбрасывать. В чистом состоянии эта строка почти пуста и ничего не стоит.

Правило выведено на редизайне базы знаний (`Explorer.jsx`): было ~370 px до
первой заметки, стало ~110 px.

### Когда список перестаёт помещаться на экран

Сотня строк — ещё список. Несколько сотен — уже дерево, и вертикаль кончается
раньше данных. Три правила, в этом порядке:

1. **Группы свёрнуты по умолчанию — все.** Список свёрнутых групп помещается на
   экран целиком и сам работает навигацией. Раскрываются автоматически только
   две вещи: группа открытой сейчас сущности (иначе deep-link ведёт в невидимую
   строку) и — пока идёт поиск — группы с совпадениями.
2. **Раскрытие поиском — настоящее, а не подменённый флаг.** Заголовок группы,
   который выглядит кликабельным и не реагирует на клик, — баг. Раскрывайте
   группы вызовом, а при очистке запроса сворачивайте обратно: их раскрыл поиск,
   а не человек.
3. **На узком экране дерево превращается в drill-down.** Раскрытая группа на
   мобилке не влезает, а строка «Студия · 21» влезает вся: сначала список групп
   со счётчиками, тапом — содержимое группы, тапом — сущность. Поиск и очереди
   на модерацию из drill-down выпрыгивают в плоский список: там ось группировки
   не отвечает на заданный вопрос.

Живой пример — секция «Модели устройств» на карточке вендора
(`Vendor/View.jsx`): группы-аккордеоны по типам устройств, малый каталог
(≤ 12 моделей) раскрыт сразу, крупная группа (> 8) отдаёт «Показать все N»
инлайн, поиск раскрывает группы с совпадениями, «Развернуть/Свернуть все» — в
тулбаре.

Виртуализация на этом масштабе не нужна и не решает проблему: тормозит не
браузер, а глаз. Начинайте с того, что уменьшает число строк, а не с того, что
ускоряет их отрисовку.

### Поиск переезжает на сервер вместе с данными, по которым ищет

Клиентский поиск бесплатен, только пока искать не по чему. Как только в ответе
списка появляется полный текст сущности (`plainText`, `content`, описание) —
каждый заход в раздел скачивает его целиком, ради `String.includes()` у тех
немногих, кто вообще что-то ищет.

Признак, что пора: **в списке приезжает поле, которое список не показывает.**
Тогда — `?search=` на бэкенде, поле выкидывается проекцией, а на клиенте:

- инпут обновляется мгновенно, запрос — с задержкой (300 мс);
- терм экранируется (`escapeRegex`) и ограничивается по количеству, иначе `.*`
  в поисковой строке становится сканом коллекции;
- **выбранные значения фасетов хранятся объектами, а не id.** Серверный поиск
  сужает набор, из которого собираются опции селекта; по одному id восстановить
  пилюлю выбранного значения будет уже нечем, и выбранная компания исчезнет из
  собственного фильтра, стоит начать печатать.

### Список на серверной выборке: страницы, а не «загрузить всё»

Когда список перерастает клиент (сотни записей, долгая загрузка), на сервер
уезжает **весь набор операций разом**: поиск, фасеты, сортировка и
постраничность. Половинчатый вариант не работает — клиентский поиск по
подгруженной странице ищет только по ней. Эталон — «Пользователи»
(`pages/User/List.jsx` + `controllers/user.js` `getAll`).

- **Стор держит порцию, а не весь список**: `items` (текущая страница), `total`
  (сколько нашлось всего), `page`, `pageSize`; каждое изменение фильтра,
  сортировки или страницы само делает запрос. Счётчик у заголовка — `total` с
  сервера (проп `count` у `ListWrapper`), а не длина массива.
- **Пагинация**: нумерованные страницы на десктопе, «Показать ещё» (докрутка) на
  мобайле — оба живут в `belowList` (`app/Pager`). Порция — 30 у
  «Пользователей», 50 у «Архива заявок».
- **Скоуп по правам считает БД, а не JS.** Выбрать всё и отфильтровать в памяти
  — та же «загрузка всего»: условие видимости уходит в `$match`.
- **Поиск** — `$or`-regex по полям строки; правила из раздела выше (задержка
  300 мс, экранирование и лимит терма).
- **Фоновые обновления не рвут пагинацию.** Живые статусы присутствия
  подтягиваются лёгким запросом-табло и **мержатся** в показанные строки по
  `_id`, а не перезапросом списка — иначе докрученные страницы схлопнутся.
- **Группы — только когда они не рвутся между страницами.** По умолчанию плоский
  список; группировка (например, по подразделению) включается, когда выборка
  сужена до одной компании, и тогда набор отдаётся целиком, без страниц.
- Ось, по которой нельзя отсортировать в БД, — повод **денормализовать поле**, а
  не тащить агрегат на каждый запрос (`lastActivityAt` на пользователе вместо
  join с заявками; поддерживается хуком модели при создании заявки).

### Строка-запись: жёсткие колонки

Строка справочника с несколькими колонками данных держит форму, а не плывёт по
контенту (эталон — `components/Company/Item.jsx`):

- **Все строки одной высоты.** Поле переменной длины (адрес) — в одну строку с
  усечением, полное значение — в `title`, клик открывает карту (`linkToMap`) в
  новой вкладке; усекается только **вторичное** (юрлицо), а счётчики
  («N пользователей · M услуг») закреплены в конце и не уезжают. Счётчики
  считает бэкенд (компактная проекция `usersCount`/`servicePlansCount`), а не
  длины вложенных массивов, которые списку не нужны.
- **Живой статус — «тихим форматом»**: цвет несут только точка и ключевое слово
  («открыто»), длительность приглушена («открыто · ещё 4 ч 43 мин»); негативное
  и отсутствующее («откроется через …», «график не указан») — целиком
  приглушённо, не красным. Короткую фразу отдаёт поле `detail` из
  `util/get-working-status.js`; показывает её `Company/WorkStatusText` —
  один компонент на список и шторку-справку.
- **Гнездо действий постоянной ширины** справа (ровный правый край у всех
  строк), сами действия проявляются по наведению. Гнезду нужен воздух от края
  и приглушённый, а не блёклый глиф (`w-14` с `pe-4`, `text-muted-foreground`
  у заявок): в узком гнезде вплотную к рамке «⋯» не замечали.
- **Вид записи — в мете строки, не у номера и не у темы**: у регламентной
  заявки мету открывают глиф и слово («⟳ регламент · Компания · Инициатор»).
  Вид — вторичный факт и живёт рядом с остальными вторичными фактами; глиф у
  номера читался как случайный символ, глиф у темы сдвигал заголовки
  регламентных строк относительно остальных, пилюля в мете была тяжелее самой
  меты.
- **Действие за глобальной настройкой** (такси у компаний): настройка не
  задана — действия нет нигде. Подпись нейтральная — **«Такси»**: она честна и
  когда маршрут строится, и когда оператор его не умеет («Максим»,
  «Ситимобил»); куда поедет — в тултипе и подписи мобильной строки. Ссылку
  открывает `util/taxi-operators → openTaxi`: он кладёт в маршрут текущее
  положение начальной точкой и **открывает вкладку синхронно, до запроса
  геолокации** — после асинхронного ответа её срезает блокировщик попапов;
  отказ в доступе и таймаут не блокируют, едем с одной конечной точкой.
  Глобальные префы доступны фронту через `store/prefs.js`.
- **Кнопки звонка в строке нет** — телефоны живут в мобильной шторке-справке
  (`Company/ContactSheet`) и на карточке. На карточке заявки оба канала «дороги
  к клиенту» стоят в гнёздах действий строк «Заявка»: такси — у компании, звонок
  — у инициатора.

### Строка-человек: адресная книга, а не реестр

Список людей отвечает на «кто это и как с ним связаться», поэтому отличается от
строки справочника (эталон — `components/User/Item.jsx`):

- **Круглый аватар с инициалами вместо квадратной плитки** — люди ≠ записи,
  лицо узнаётся быстрее текста, а инициалы — общепринятая замена лица (у
  записей букв в плитке нет — см. «Анатомия списка с фильтром»). Фото — фоном
  на `<span>`, не `<img>`.
- **Присутствие — кольцом на аватаре и фразой** с цветной точкой (цвета — токены
  `--ws-st-*`). Расчёт «показывать ли присутствие» лежит в одном месте
  (`User/presence.js`), а не копируется по строке / шторке / карточке.
- **Контекстный правый столбец**: у сотрудника — присутствие, у клиента —
  последняя активность. Одна колонка, разный смысл по типу записи.
- **Связаться прямо из строки** (десктоп): звонок и письмо — только для реально
  заполненных каналов. Управляющие действия остаются в «⋯» под правами.
- **На мобайле тап открывает контакт-шторку** — крупные «Позвонить/Написать»,
  копирование и «Открыть профиль», не уходя со списка; сама строка компактная,
  с шевроном.

## Страница сущности (карточка): hero → секции → действия

Детальные страницы (услуга, пользователь, расположение, шаблон, регламент)
строятся по одному шаблону. Эталон — **`components/ServicePlan/View.jsx`**
(первая мигрированная карточка, макет согласован до кода).

- **Возврат — хлебные крошки сверху, и ведут они ТУДА, ОТКУДА ПРИШЛИ**
  (`app/Crumbs`), а НЕ кнопка «К списку» в действиях (дублировала бы). Крошки —
  по умолчанию для всех view-экранов. Сама карточка ничего о себе не объявляет:
  подпись кладёт в переход ссылка, которая из неё уводит (`from` у
  `app/EntityLink`, `useCrumbFrom` у голых `<Link>`). Адрес списка руками НЕ
  пишем: раздел, его название и право на него знает справочник `util/sections`.
  **Почему не список раздела.** Ссылка со стрелкой выглядит как «назад», а
  константа в ней вела всегда в одно место, и совпадало это с ожиданием ровно
  тогда, когда человек пришёл из этого самого списка. Пришёл из заявки в
  карточку инициатора — крошка предлагала «Пользователей», раздел, которого в
  его пути не было, а без права на список — ещё и 403.
  **Что показывает крошка** (первый подошедший ответ): `state.from` перехода →
  список раздела, если он человеку открыт → название раздела приглушённым
  текстом, если права нет → ничего. Запаска отвечает там, где источника нет:
  прямая ссылка, переход из списка своего же раздела, новая вкладка.
  **Запаску можно назвать самим**: `section="archive"` у заявки из архива (в
  активном списке её уже нет), `section={false}` там, где возврат «наверх»
  вернул бы на эту же страницу (карточка отчёта у того, кому сводка и так
  редиректит сюда).
  **Настоящая иерархия** — пропом `chain` после ссылки возврата: предки
  расположения, компания над подразделением. Текущая сущность в крошках не
  повторяется, она в `h1`.
- **Hero**: плитка-глиф раздела или логотип (`size-14 rounded-2xl bg-accent`,
  глиф `size={26}`, кольцо только у картинки — та же плитка, что в строке
  списка, и одна на страницу; буквам в ней не место) · `h1` · «статус» строкой (цветной
  текст с точкой) · охват счётчиками (`tabular-nums`) · справа **одна залитая
  «Изменить»** + меню «⋯» (пока только Удалить, через `app/DeleteDialog`,
  рендерится вне radix-меню). Подписи «Действия» нет.
- **Секции** — панели на канве (`rounded-xl border border-border bg-card p-5`)
  с uppercase-eyebrow-меткой (+ счётчик): `Panel`/`Eyebrow` — из каталога
  `app/Panel` (их делят несколько карточек), локальный `Pill` — по месту.
  Однородные списки (категории, компании) — **нейтральными пилюлями** (не
  раскрашиваем); длинный однородный список — только через `app/PillPanel`: он
  сам сворачивает облако до ~3 рядов (`collapsedMaxHeight`), даёт
  градиент-затухание и «Показать все (N)»/«Свернуть» — вручную это не собираем.
- **Правка — в нижней шторке** прямо на карточке: `<FormOutlet />` вместо
  `<Outlet/>` (как в `ListWrapper`); маршрут `update` вложен в `:id` и несёт
  `handle.sheet`.
- **Скролл к началу при монтировании** (`useEffect(() => window.scrollTo(0,0),
  [])`): на десктопе Root сбрасывает только мобильный контейнер, а window-скролл
  при навигации сохраняется — без сброса hero карточки, открытой из
  проскроленного списка, уезжает под фиксированный бар. Глобально сбрасывать по
  `pathname` нельзя — сломает фон под шторками-формами (их путь тоже меняется).
- **Строка списка ведёт на карточку** (не в шторку правки): `app/ListRow` проп
  **`detailTo`** (клик → `navigate(detailTo)`, доступно всем, кто видит список;
  «⋯» с правкой/удалением остаётся под `canManage`). В Root `MIGRATED_ROUTES`
  под общим префиксом заводим ДВЕ записи, если у списка и карточки разная
  ширина: `/…/` (со слэшем, карточка `max-w-4xl` → 944) матчится в `.find`
  раньше `/…` (список `max-w-7xl` → 1328).
- **Одно поле — одно место правки.** Секции карточки **только показывают**;
  своего редактора и своего «Сохранить» у секции не бывает. Если у секции есть
  что править, в её метке стоит ярлык **«Изменить» → та же форма, открытая
  сразу на её секции** (`<Link to="update#schedule">`; форма ловит хеш — см. `app/FormLayout`). Так у пользователя один ответ на
  вопрос «где это меняется», а у нас — одна валидация и один payload.
  Эталон: секция «График работы» карточки сотрудника
  (`User/WorkScheduleSection` — чтение, `User/UserForm` — правка) и чек-лист
  карточек шаблона и регламента.
  Исключений два, и оба — про секцию, которая **и в покое меняет данные на
  месте**: **документ** (заметка базы знаний), у которого формы нет вовсе (см.
  «Правка на месте»), и **чек-лист заявки**, который отмечают прямо на карточке
  (`pages/Ticket/View.jsx`). Уводить состав такого списка в форму значит
  разорвать одно занятие между двумя поверхностями. У правки на месте
  обязателен **явный режим** — `app/SectionEditButton` (карандаш → «Готово»):
  отмечать и перестраивать разные занятия, и рука, привыкшая ставить галочки,
  промахнётся по «удалить». Заодно у прав одна точка — показывать кнопку или
  нет. «Сохранить» у режима нет: каждое изменение уходит сразу, «Готово» только
  выключает режим. Пока режим включён, фоновое автообновление секцию не трогает.
  Секция, которая грузит данные сама (как `WorkScheduleSection`), берёт проп
  `version` (`user.updatedAt`) в зависимости загрузки: после сохранения формы
  роутер ревалидирует loader, отметка меняется — секция перечитывает своё.
- **Секция оправдана предметом, а не наличием данных.** Отдельная секция —
  заявка на то, что у сущности есть самостоятельная часть, за которой приходят.
  Если данные читают попутно и приносят вместе с чем-то другим, они живут
  подвалом того блока, к которому относятся: вложения заявки — лента чипов под
  описанием (`View/AttachmentStrip`), потому что файл почти всегда приезжает
  вместе с заявкой, а новый кладут в комментарий. Признак ошибки — секция, где
  оформление стоит дороже содержания: рамка на файл и плитка 40 px ради имени,
  которое читают один раз. Проверяйте вертикалью: секция вложений занимала
  ~310 px, лента — ~50.
- **Метка секции называет содержимое, а не предмет карточки.** «Заявка» на
  карточке заявки, «Компания» на карточке компании — это ярлык вокруг всего
  экрана, а не название блока; в рейле такой пункт вообще ни на что не указывает.
  Поля самой сущности — **«Детали»**.
- **Длинной карточке — рейл-якорь.** Если секций много и они не влезают в экран,
  слева ставим липкий `app/AnchorRail` (десктоп; на мобайле секции просто идут
  подряд): ведёт по секциям и подсвечивает текущую (scrollspy на `window` —
  только `BrowserView`). Пункты собираются **только из реально отрисованных**
  секций — скрытая правами секция не должна оставлять пункт в рейле. Якорь
  вешается пропом `id` на `Eyebrow`/`PillPanel`/`SettingsSection` (у них же
  `scroll-mt` под fixed-навбар), а ширина карточки расширяется под рейл
  (`max-w-5xl` + соответствующая запись в `MIGRATED_ROUTES`). Табы для этого
  не заводим — см. следующее правило.
- **Вкладок у карточки не бывает.** Секции идут одной колонкой, навигацию даёт
  рейл. **Вторая колонка допустима ровно там, где у сущности есть живой поток**
  — переписка и события заявки (`pages/Ticket/View.jsx`): секции слева, хроника
  справа липкой колонкой со своим скроллом. Это не вкладка: оба столбца видны
  одновременно, и ни один не прячет другой. На узких экранах (< xl) колонка
  становится последней секцией. Вкладка почти всегда означает, что в карточку затащили **предмет
  соседнего раздела**: «Мониторинг» и «Конфигурации» на карточке устройства
  были копией страницы записи мониторинга, и обе ушли. Чужой предмет
  показывается **сводкой со ссылкой** («связь · доступность · прошивка ·
  последняя связь → Открыть в мониторинге»), а не вторым его экраном:
  сводка отвечает на «нужно ли туда идти», раздел — на всё остальное.
  Документ (заметка, статья) вкладок не требует тем более.
- **Пустое значение поля — общий `—`** (приглушённым цветом), а не пустая
  строка.
- **Пустое состояние внутри секции — не пустота**: крупная приглушённая иконка,
  заголовок, объясняющий абзац (`max-width: 480`) и главное действие. Если прав
  не хватает — вместо кнопки строка «Недостаточно прав — обратитесь к
  администратору».
  **Но если пустых секций на карточке бывает несколько сразу** — заглушка
  сжимается до одной строки: иконка 16 и короткая фраза («Чек-листа нет»).
  У заявки пустуют чек-лист и работы одновременно (в данных — у большинства
  заявок), и плакаты подряд отжимают вниз то, ради чего карточку открыли.
  Эталон — `Ticket/View/Sections` `EmptySection`.
  **А если содержимое ещё и необязательное — заглушки нет вовсе**: у вложений
  заявки лента просто не рисуется, потому что «Вложений нет» не сообщает ничего
  (см. правило «Секция оправдана предметом» выше). Действие при этом остаётся в
  метке.
  **Кнопки внутри заглушки нет:** действие секции живёт в её метке и когда
  секция пустая, и когда полная. Иначе «Добавить чек-лист» стоит внутри панели, а
  «Добавить работу» — над ней, и глазу не за что зацепиться. У пустой секции
  действие называет себя словом («Добавить чек-лист»), у наполненной на его месте
  может стоять карандаш.

## Действия на странице сущности

**Ровно одна залитая кнопка**, и её выбирает состояние, а не порядок в разметке.
Пример из базы знаний (`components/KnowledgeBase/NoteActions.jsx`): модератору
непроверенной заметки главное действие — «Проверить», всем остальным —
«Редактировать». Вторая кнопка — outline/ghost. Всё редкое и опасное — в
icon-only меню `⋯` (`RiMoreLine`; группы пунктов с заголовками, разрушающее —
последним и в `destructive`).

- **Подпись «Действия» запрещена.** Она ничего не сообщает: пользователь обязан
  открыть меню, чтобы узнать, что там. Icon-only «⋯» честнее и занимает меньше.
- **Чужой запрос, ожидающий решения, — инлайн-`Alert`, а не пункт меню.**
  «Пётр Петров запросил удаление 3 июля» + `Подтвердить` / `Отклонить` рядом с
  контекстом (`components/KnowledgeBase/PendingRequestAlert.jsx`). Решение,
  спрятанное в меню, принимается вслепую: не видно ни кто попросил, ни когда.
  Кнопки внутри цветного алерта наследуют его цвет (контраст по
  `currentColor`).
- Кнопка действия и её результат называются **одним словом**: «Проверить» →
  «Заметка отмечена как проверенная» → бейдж «Проверено».
- **Главное действие, которое всё равно откажут, подменяется тем, чего не
  хватает.** У заявки без указанных работ в шапке не «Закрыть заявку», а
  «Указать работы»: кнопка, ведущая в 422, — обещание, которого интерфейс не
  держит. Если помех несколько или их не исправить одним переходом (обязательные
  пункты чек-листа, незакрытая запланированная работа), главное действие
  остаётся на месте, а диалог вместо формы показывает список причин — там же, где
  человек ждал подтверждения. Условия живут **в одном модуле** с каталогом
  действий (`Ticket/ticket-actions.js` → `closeBlockers`) и повторены на бэкенде:
  проверка на клиенте прячет кнопку, но запрос можно послать и минуя её.
- **`overflow: hidden` на блоке, где живёт кнопка меню, обрежет меню.** Обычно
  его ставят, чтобы фон-градиент не вылез за скругление, — но фон и так
  клипается по `border-radius`. Если `overflow` действительно нужен, дропдаун
  должен рендериться в портал.

**Секционная правка — карандаш, а не кнопка.** У каждой секции, поля которой
правятся в форме сущности, есть второй вход в эту форму, открытую сразу на ней
(`update#якорь`; ключ секции формы = якорь — см. «Большие многошаговые формы»).
Это **навигация**, и весом кнопки за неё не платят: `app/SectionEditLink` —
icon-only карандаш в метке секции, проявляется по наведению на секцию (обёртка
`app/Section` даёт `group`), при фокусе с клавиатуры и на тач-экране виден
всегда.

Правило действует на **всех** карточках, а не только там, где такой вход уже
был: карандаш у правимой секции — норма, его отсутствие — сообщение «этот блок
здесь не правится» (Окружение, Заявки, Мониторинг). Пока обратное не сделано
везде, отступления перечислены в «Хвостах эндшпиля».

Разделение — по природе контрола, а не по «часто/редко»:

| Что это | Как выглядит |
|---|---|
| Действие со **своим именем** («Выдать», «Прикрепить», «Добавить фото», «Задать график» у пустой секции) | Текстовая outline-кнопка `xs`/`sm` в `action`, видна всегда |
| **Вход в общую форму** («поправить этот блок») | Карандаш `SectionEditLink`, по наведению |
| **Режим правки в самой секции** (только для секции, которая и в покое меняет данные на месте) | Карандаш `SectionEditButton`, по наведению; в режиме — outline `xs` «Готово» |
| Правка **вложенной строки** (конфигурация модели, атрибут типа) | «⋯»-меню самой строки — она правит свой объект, а не секцию |

**Инвариант, который проверяем на ревью: слово «Изменить» на карточке ровно
одно — залитая кнопка в hero.** Она и держит обнаружимость. Четыре одинаковых
«Изменить» вдоль правого края перестают различаться по надписи (их читают по
позиции, а не по тексту) и выстраиваются в колонку кнопок, конкурирующую с
содержимым, — ровно то, ради чего карточку открыли. Побочный выигрыш: отсутствие
карандаша становится информативным — «этот блок здесь не правится».

## Статус, который протухает, — предложение, а не бейдж

Если у состояния есть **автор, дата или срок**, бейджа мало. Пишем фразу:

```text
✓ Проверено · Иванов И. · 16.06.2026 · действует ещё 24 дн.
⚠ Не проверено · изменил Петров П. · 03.07.2026
```

Эталон — `components/KnowledgeBase/VerificationLine.jsx`. Цветом красим только
иконку и само состояние; автор и дата — приглушённым (`muted-foreground`).
Срок на исходе переключает тон на `warning`, даже если состояние «хорошее».
Бейдж (`Badge`) остаётся для компактных списков, где нет места на фразу.

**Состояние и «что с ним не так» — разные оси, и одна не вытесняет другую.**
Просроченная заявка не перестаёт быть в работе: подменять статус словом
«просрочена» — значит отвечать на второй вопрос вместо первого, и человек
перестаёт понимать, где заявка в процессе. Статус виден всегда; беду несёт
второй знак — красный срок в списке и отдельное слово рядом со статусом там, где
есть место (шапка карточки). В шапке карточки статус ещё и
звучит в полный голос: `TicketStateText strong` — там сущность одна, и приглушать
норму, как в списке, незачем.

**В списке показываем только исключения.** Нормальное состояние («проверено»)
не показывает ничего: подсвечивать норму — значит красить весь список и
потерять на этом фоне то, что действительно требует внимания. Значок-иконка
появляется у непроверенного, у истекающей проверки, у находки сканера и у
запроса, ждущего решения (`getNoteFlags` в `util/knowledgeNoteTypes.js` —
единый порядок и тон). В узкой колонке это ещё и место под заголовок.

Чтобы фраза была возможна, бэкенд обязан отдавать **имена**, а не `ObjectId`:
`populate` актора в `getOne` и в ответах мутаций (см.
`backend/controllers/knowledgeNote.js`, `ACTOR_PATHS`). В списках имена не нужны
— там достаточно иконки, и populate туда не тащим.

## Что сделал ИИ, а что человек

Ассистент не отдельный экран, а слой поверх заявки, и на этом слое два разных
вида содержимого. Их нельзя оформлять одинаково.

- **Данные, которые ИИ вписал вместо человека**, — описание, собранное из записи
  звонка, и подобранная категория. Ошибка в них не остаётся на экране: она
  уезжает в уведомление, в отчёт и в подбор заметок. Такие поля несут **метку —
  общую иконку ИИ (`RiSparkling2Line`) в конце содержимого**, без подписи: метка сообщает
  происхождение, а не требует действия, и подписанный бейдж на плотной карточке
  перетягивал внимание с самого текста. Смысл несёт подсказка по наведению, клик
  открывает замечание. Место метки — у самого содержимого: у описания это конец
  текста, а не подвал панели с файлами.
- **Предложения рядом с данными** — руководство и справка. Они не выдают себя за
  написанное человеком, и метки им не нужно: происхождение несут название секции
  («Руководство ИИ») и оговорка в подвале («Ссылки и факты собрал ИИ — человеком
  не проверено»). Метка на каждом абзаце превратила бы карточку в рябь.

**По метке — замечание, а не «палец вниз».** Из «не понравилось» правила не
составишь, поэтому форма спрашивает **причину** (не по делу / ошибка в фактах /
выдумано / устарело) **и текст** «что неверно и как правильно». Открывается она
**диалогом поверх страницы**, а не блоком на месте: раздвинуть описание, которое
человек в этот момент читает, — худшее, что можно сделать с его вниманием. Это
диалог действия, поэтому сабмит зовётся действием («Записать замечание»). Замечание сразу
идёт в хронику заявки, а в запросы к модели — только после того, как его включит
администратор («Настройки → ИИ», список правил): одна эмоциональная формулировка
иначе тихо испортит генерации всему отделу. Область правила берётся у заявки —
категория и компания; правила без области не бывает.

**Предложение не встаёт впереди фактов.** «Руководство ИИ» идёт третьей секцией
карточки заявки — после «Описания» и «Деталей», а не сразу за описанием: компания,
заявитель и ответственный это факты, за которыми заявку открывают, а руководство —
предложение. Порядок в рейле обязан совпадать с порядком секций.

### Справка по предмету живёт в описании

Справка отвечает на «что это вообще такое», руководство — на «что делать по этой
заявке». Первая переиспользуема, второе живёт ровно одну заявку, поэтому справка
раскрывается прямо в панели описания (она про его текст), **своей секции и
пункта рейла не получает** — рейл ведёт по разделам, а не по временным
состояниям.

- **Понятия разделены на два вида.** Что человек написал сам — подчёркнуто
  пунктиром в тексте описания; что ИИ добавил от себя — строкой «Ещё в теме»
  под ним. Смешать их значит потерять границу между словами заявителя и
  домыслом модели.
- **Ссылки на документацию — отдельным блоком и с именем домена**: видно, что
  это `pbs.proxmox.com`, а не случайный блог. Живость каждой ссылки проверяет
  бэкенд запросом — выдуманный адрес у модели встречается чаще выдуманного
  факта, и мёртвая ссылка в справке дороже отсутствующей.
- **Справка вытекает в базу знаний.** «Сохранить в базу знаний» заводит обычную
  заметку — неодобренную, как любая другая: модерация и есть тот человек,
  который отделяет проверенное знание от предположения. Дальше такая заметка
  приезжает в следующую заявку обычным подбором, уже без вызова модели.
- **Всё по требованию.** Разбор стоит вызова модели, справка — ещё одного;
  платить за них на каждой созданной заявке незачем. Открытие уже составленной
  справки — чтение, а не новая генерация.

## Хроника: переписка и события одной лентой

Если у сущности есть и переписка, и история изменений, они показываются **одной
лентой**, а не двумя экранами. Эталон — карточка заявки
(`components/Ticket/Chronicle.jsx`): раньше комментарии жили в правой колонке, а
события — во вкладке «Лог», и связь «взял в работу → написал» приходилось
восстанавливать по времени.

- **Служебное сворачивается, а не показывается.** У живой заявки 1506 записей
  лога, из них 1476 — «при отправке email-уведомления». В ленте только события
  предмета; доставка уведомлений и записи ИИ схлопываются в строку **под своим
  событием** («6 служебных записей · 2 с ошибкой») и раскрываются по запросу
  отдельным вызовом — тысячи строк на клиент не уезжают.
- **Ошибки доставки называются вслух.** Свёрнутая строка с ошибками — янтарная:
  иначе единственный способ узнать, что клиенту ничего не ушло, это логи
  контейнера.
- **Вид события — в каталоге, а не в тексте записи.** Собственный текст лога
  написан для лога («запросил(а) помощь, изменён список ответственных»), в ленте
  он не показывается: иконку, тон и человеческую подпись даёт каталог
  (`util/ticket-events.js` — вид → вид; `backend/services/ticketEvents.js` — вид
  по фразе). Старые записи классифицируются тем же каталогом при чтении:
  миграция полутора миллионов строк ради выводимого поля не окупается.
- **Событие о комментарии в ленту не попадает** — сам комментарий уже показан.
- **Переключатель «Переписка | Всё»**, по умолчанию — переписка: за событиями
  приходят реже, чем за перепиской.
- **Порядок — новыми вверх, поле ввода сверху.** День отбивается меткой
  («Сегодня», «27 июля»), у записи — только время.

## Даты и время на экране

Формат даты выбирается **не по вкусу строки, а по хелперу**: их набор в
`util/format-date.js` закрыт, и новый формат заводится правкой хелпера, а не
локальным `toLocaleDateString` в компоненте. Устройство и таймзоны — в
`docs/datetime-conventions.md`; здесь только то, что видит пользователь.

| Хелпер | Как выглядит | Где |
| --- | --- | --- |
| `formatDate` | `ср, 08.07.2026, 14:30` | канонический «дата и время»: комментарии, логи, таблицы, тултипы |
| `formatShortDate` | `08.07.2026` | «создан», «обновлено», строки-меты карточек |
| `formatDateTime` | `8 июля в 14:30` | компактный, без года |
| `formatWeekdayDateTime` | `ср, 8 июля в 14:30` | отчёт по услуге: день недели объясняет, почему работа в нерабочем времени |
| `formatDayMonthTime` | `08.07, 14:30` | оси и тултипы графиков, ленты |
| `formatTime` | `14:30` | лента лога: день вынесен отдельной меткой |
| `formatDayMonth` | `08.07` | там же — для записей не сегодняшнего дня |
| `formatMonthYear` / `formatMonthLabel` | `июль 2026 г.` | заголовки месячных периодов |
| `formatCalendarDate` | `08.07.2026` | даты-без-времени: покупка, гарантия, «действует с», сроки услуг |
| `formatDayKey` | `04.09.2026` | day-key `yyyy-MM-dd` без таймзоны: подписи полей-календарей, бейджи периода в архивах, произвольный период в `MonthStepper` |
| `formatAgo` | `только что` · `12 мин назад` · `3 ч назад` | протухающие статусы (см. «Статус, который протухает») |

Русский CLDR сам ставит «в» перед временем и « г.» после года. Это норма —
не обходите её ручной склейкой; если суффикс ломает узкую вёрстку, режьте его
на месте (`components/app/MonthStepper.tsx`), а не заводите ещё один формат.

**Поля-календари** показывают выбранное как `04.09.2026` (`formatDayKey`),
период — `01.09.2026 – 30.09.2026` (тире, как у произвольного периода в
`MonthStepper`; незакрытый край — «…»), пустое поле — «Выберите дату» /
«Выберите период». Подпись месяца в сетке — «сентябрь 2026», дни недели —
«пн … вс» (локаль `ru` react-day-picker).

**Относительные метки дня** — `сегодня` / `вчера`, дальше дата. Считаются в
таймзоне организации (`businessDaysAgo`), поэтому у сотрудника в другом поясе
не расходятся с тем, что видят коллеги. Живут в логе компании
(`CompanyLogs/Offcanvas`) и в адресной книге (`util/relative-time`).

**Который час у клиента** — бейдж `ClientTime` (см. каталог компонентов).
Показывается, только когда местное время заявителя **фактически** отличается
от нашего; ночь подсвечивается. В телеграме и письмах ту же подпись собирает
бэкенд — на клиенте её не переформатируют.

---

- **Время у статуса присутствия — про будущее, если оно известно.** Тому, кого
  нет («не на работе», «отпуск», «болею»), бар пишет «до 04.09 09:00» —
  ближайшее начало смены по графику (`user.nextShiftAt`, считает автоматика;
  сегодняшнее — «до 09:00»); когда исчез, не важно. Тому, кто на смене, —
  «с 09:12»: с какого момента он в этом состоянии. Свободному режиму смен нет
  — остаётся «с …».

## Правка на месте (Obsidian-режим)

Когда страница — **документ**, а не форма, правим его на месте, а не в Offcanvas.
Эталон — `components/KnowledgeBase/NoteView.jsx`.

Это **единственное** исключение из правила «одно поле — одно место правки»: у
документа формы нет вовсе, тело правится там же, где читается. Секция карточки
у сущности с формой так себя вести не может — она показывает и уводит в форму
(см. «Страница сущности»).

**Раздел документов — две панели, и рисует их сама страница.** У базы знаний
список постоянно на экране слева (`components/KnowledgeBase/Explorer.jsx`), а
документ открывается справа: заметку читают и правят вперемешку, и возвращаться
к списку крошками пришлось бы на каждый чих. Отсюда следствия, отличающие
раздел-документ от справочника:

- **раскладкой владеет страница**, а не оболочка: сайдбар `Root.jsx` — легаси и
  для мигрированных экранов не используется (`store/sidebar` доживает у заявок);
- **крошек на десктопе нет** — список никуда не уходил; крошка «‹ Раздел»
  остаётся мобильной версии, где панель одна;
- **заголовка страницы нет**: раздел назван в баре, счётчик живёт в строке
  состояния рейла — 44 px вертикали отданы обеим панелям;
- **главное действие — иконка рядом с поиском** (правило «Бюджета управляющих
  элементов»), залитая кнопка на экране остаётся у документа.

**Главное правило: между чтением и правкой не должно двигаться ничего**, кроме
того, чем управляют. Как это достигается:

- Заголовок в правке — тот же `h2`, только инпут без рамки, с теми же
  метриками.
- Строки свойств держат `min-height` под высоту контрола выбора: пилюли в
  чтении и селект в правке занимают один бокс.
- Тело — один и тот же класс контента у вьюера и редактора
  (`.toastui-editor-contents`), поэтому мера чтения задаётся один раз.

**Клавиши и триггеры:** `Ctrl/Cmd+E` — переключить режим, `Ctrl/Cmd+S` —
сохранить, `Esc` — выйти. Двойной клик по тексту открывает правку в том же месте
(гейт по правам, не в архиве; клики по ссылкам и чекбоксам task-list
игнорируются) — но точную каретку в WYSIWYG не обещаем, целимся в начало блока.

**Несохранённые изменения:** `useBlocker` (роутер данных) + `beforeunload` +
диалог подтверждения. Собственные переходы (сохранили новую сущность, отменили
создание) обходят блокировку через ref-флаг.

**Автосохранения нет, если у сохранения есть побочный эффект.** Правка заметки
сбрасывает отметку «Проверено» — о таком побочном эффекте предупреждаем **до**
сохранения, прямо в строке статуса: «Сохранение снимет отметку „Проверено“».

## Переиспользуемые доменные блоки (одна информация — один вид)

Если сущность-информация встречается у нескольких разделов (заявка, шаблон
заявки, регламентное задание), она **показывается и правится одним
компонентом**, а не переверстывается под каждый экран: пользователь не должен
потреблять одно и то же в разном виде, а мы — держать три расходящиеся со
временем копии верстки. Компонент делаем контролируемым и достаточно гибким под
все места сразу (форма данных — надмножество), а встраивание регулируем пропами
(`framed` / `showHeader` / `showProgress`), а не форком под экран.

**ИИ предлагает — состояние держит система.** Вывод модели не отращивает
собственных отметок, прогресса и статусов: он превращается в объект, который в
приложении уже есть. Шаги руководства переносятся в чек-лист заявки (там отметки
сохраняются, считается прогресс и держится запрет закрытия), вопросы уходят
черновиком в поле комментария (отправляет человек, правя текст). Проверка на
живых данных: пока у панели ИИ были свои галочки, из ~980 пунктов отметили 10 —
параллельная механика не приживается, потому что настоящая рядом.

**У производного текста — ровно одно место, у исходника — своё.** Если ИИ (или
любой пересчёт) делает из артефакта короткий вид — пересказ звонка, выжимку
письма, — этот короткий вид живёт там, где его читают по делу, и больше нигде: у
записи звонка пересказ становится описанием заявки
(`middleware/emailHandling`), а у вложения остаётся **сырая расшифровка**.
Показывать рядом и пересказ, и исходник, и «раскрыть целиком» — значит выдать
одну мысль тремя блоками; исходник же нужен ровно для того, чтобы пересказ можно
было проверить.

Готовые доменные блоки (каталог `components/app`):

- **`Checklist`** — чек-лист во всех трёх ролях одним компонентом: **run** —
  выполнение в заявке (отметки, прогресс, подпись «кто · когда», гард
  обязательных), **edit** — составление (добавление по Enter, drag/Alt+↑↓, флаг
  «обязательный», удаление с возвратом), **read** — просмотр в карточке.
  Где живёт **edit**, зависит от предмета: у шаблона и регламента чек-лист —
  определение, и он правится в форме (на карточке правки нет, туда ведёт ярлык
  секции); у заявки — рабочий список, который и так отмечают на месте, поэтому
  режимы run↔edit переключает `SectionEditButton` прямо в секции. Контролируемый
  (`onToggle` / `onChange`); форма пункта — надмножество (`description` +
  `mandatory` + отметка `checked`/`checkedBy`/`checkedAt`); заголовок отключаем
  пропом там, где секцию подписывают снаружи (полоса прогресса остаётся —
  она часть списка, а не заголовка).
- **`Environment`** (+ `EnvironmentDeviceTile` / `EnvironmentDeviceSheet`) —
  физическое окружение (семантический zoom здание → этаж → помещение → рабочее
  место) **одним виджетом на три места**: вкладка «Окружение» заявки, карточка
  пользователя, карточка компании — режим задаётся пропом, подписи
  подстраиваются под предмет («заявитель» / «пользователь»). Язык: линейка
  глубины с подсвеченным активным уровнем, сцена-«план» с картографическим
  кластером «+/−» (колесо и ↑/↓ работают), статусы техники — текст с точкой,
  личное — янтарная ★, целевое устройство — кольцо с пульсом. Карточка
  устройства — правая radix-шторка по образцу превью расположений. Метку секции
  даёт страница; вложенных больше 12 — список сворачивается («Показать все
  (N)»). Режимы, эндпоинты и механика зума — в шапке компонента.
- **`TechSection`** — секция «Техника» карточки компании и пользователя: **одни
  данные в двух представлениях**, переключатель «Список | Окружение» — в
  `action` метки секции, выбор помнится. «Список» — строки с жёсткими
  колонками: плитка-иконка с **live-точкой связи Mikrotik** (язык присутствия
  адресной книги), имя (+★ личного) · «Тип · Вендор · Инв №» · расположение ·
  учётный статус текстом с точкой · «↗» по наведению; клик по строке — общая
  `EnvironmentDeviceSheet`. **Фасеты — те же, что на странице «Устройства»,
  минус контекст карточки** (`ChipMultiCombobox`-чипы + живой поиск от 9
  устройств + снимаемые бейджи применённого). **Без запроса список ограничен
  10 строками**, дальше — «Вся техника в „Устройствах“ (N) →» с префильтром:
  карточка не подменяет собой раздел. Эндпоинты, DTO строки и порядок обхода —
  в шапке компонента.
- **`CustomFieldsEditor` / `CustomFieldsView`** — кастомные поля формы: один
  builder (тип text/select/multiselect, опции, drag, «Новое поле») и один
  read-показ (имя + тип-чип + пилюли опций) на шаблон и заявку.
- **`ScheduleEditor` / `ScheduleView`** — недельный график одной парой: строка
  дня (чекбокс · время · «24 часа») и её read-двойник (сетка 7 ячеек). Дни —
  из одного каталога `SCHEDULE_DAYS` (`[полное, ключ, короткое]`), обрезать
  полное имя по две буквы нельзя («Че», «Пя», «Су»). **Строка дня обязана
  умещаться в одну строку и в узком контейнере** (мобильная шторка — 361px):
  там имя дня короткое, поля времени делят остаток поровну, подпись свитча —
  «24ч». Используют: график сотрудника, окно обслуживания компании, услуга,
  настройки переработок.
- **Шаблон чек-листа** (`models/checklistTemplate` + `pages/ChecklistTemplate`)
  — готовый список с привязками к категориям заявок и компаниям. Правило
  подбора живёт **в одном месте** (`services/checklistTemplates`) и питает три
  поверхности: автоприменение при создании заявки, поповер «Ещё чек-листы» на
  карточке и счётчик «Взять шаблон» в редакторе. **Побеждает самый узкий**
  (категория+компания → компания → категория), заготовка без привязок в
  автоподборе не участвует, а список регламента сильнее любого шаблона. Правило
  «одна информация — один вид» тут действует и на редактор: пункты шаблона,
  заявки, шаблона заявки и регламента правит один `app/Checklist`.
- **`ScheduleBuilder`** — расписание (cron-строка) одним конструктором,
  контролируемым (`value` — cron-строка, `onChange`): режим «Простой»
  (периодичность + детали) и «Строка cron» (ручной ввод); перевод на русский,
  валидация и ближайшие запуски — `util/cron.js` (пятипольный cron, TZ
  организации — как исполняет node-cron на сервере). Сейчас им собирает
  расписание форма регламента; любое новое «по расписанию» (рассылки,
  автоотчёты) обязано брать его же, а не заводить свой ввод cron.

Сопутствующие конвенции:

- **Заготовки переносятся на бэкенде, а не копированием в UI.** Заявку по шаблону
  собирает бэкенд: он же копирует `template.checklist` → `ticket.checklist`
  (сбросив отметки, сохранив `mandatory`) и кастомные поля. Клиент шлёт выбранный
  шаблон целиком, а не пересобирает его данные, — иначе легаси-форма заявки и
  форма шаблона разъедутся по правилам заполнения. Поля моделей приёмника и
  источника обязаны совпадать по именам, иначе Mongoose (strict) молча выбросит
  копию (проверять схему-приёмник перед тем, как класть в неё чужой объект).
- **Дочерний блок показывается на карточке, а правится в форме** — правило
  «одно поле — одно место правки» действует и для доменных блоков: ярлык
  «Изменить» в метке секции ведёт в форму на её секцию (`update#checklist`),
  см. «Страница сущности».
- **Шаблон ≠ регламент, но регламент порождается из шаблона.** Шаблон — заготовка
  ручного создания заявки, регламент создаёт заявки сам по cron; «Создать
  регламент» в «⋯»-меню шаблона открывает форму регламента, предзаполненную этим
  шаблоном (`/routine-tasks/add?fromTemplate=…`, предзаполнение делает loader).

Текстовое описание (шаблон, регламент, заметка) везде правит **один редактор —
toastui из базы знаний** (`UI/MarkdownEditor` / `MarkdownViewer`), без
переключателя markdown/WYSIWYG (`hideModeSwitch`): второй редактор в приложении
не заводим, внешний вид приводим к макету обёрткой + scoped-CSS
(`.md-editor` / `.md-doc` в `index.css`; мера чтения заметки — надстройка
`.kb-doc`), а не правкой сгенерированного тулбара.

## Главная: лендинг, а не сводка

Эталон — `pages/Dashboard.jsx` (композиции `DashboardClient` / `DashboardStaff`,
блоки — `components/Dashboard/*`).

**У главной нет своего предмета — она собрана из чужих.** Поэтому это ни
список, ни карточка, ни отчёт, и правила у неё свои.

- **Композиция зависит от роли, а не набор блоков от флагов.** Клиенту страница
  отвечает «что мне сделать и что с моими заявками», сотруднику — «что на мне
  сегодня». Общий блок у них ровно один (заготовки заявок), поэтому это две
  композиции, а не одна простыня с десятком `&&`. Персональных
  переключателей блоков не заводим: их некому расставлять на сотни учёток, а
  блок и так исчезает, когда показывать нечего.
- **«Команда сейчас» — только на телефоне** (`MobileView`): на десктопе ту же
  роль играет рейл статусов, и блок был бы дублированием.
- **Пустой блок не рисуется вовсе** — ни заголовка, ни заглушки. Это прямое
  исключение из правила «пустое состояние предлагает действие»: там речь о
  секции карточки, за которой пришли, а здесь человек пришёл не за блоком.
  У клиента без техники, без открытых заявок и без ответственности остаются
  одни карточки заготовок, и это правильная страница, а не сломанная.
- **Загрузка поблочная.** Router-loader только проверяет вход, каждый блок
  ходит за своим сам — медленный (техника, переработки) не держит остальные.
  Общий запрос заводится там, где несколько блоков задают вопросы **одному
  набору**: три «заявочных» блока сотрудника делят `store/dashboard-tickets`,
  потому что «на мне», «без ответственного» и «давно без движения» — три среза,
  а не три выборки.
- **Блок отвечает на вопрос, а не показывает таблицу.** Если у среза нет
  вопроса, ради которого его открывают, ему не место на лендинге: он уводит
  внимание с того, за чем сюда приходят.
- **Метрика, у которой всегда максимум, — не метрика.** Проверяйте ось на
  живых данных до вёрстки. `deadline` заявки проставляется автоматически
  («создание + 5 часов») и стоит у всех 13 271 заявки — по нему «просрочены»
  все открытые до единой, и блок про сроки показывал бы просто список
  открытых. Честная ось — время последнего движения, и она же **сортировка, а
  не порог**: старше недели 38 заявок из 49, порог не отсекает ничего.
- **Однородный на вид поток делится по происхождению, если половина его —
  машинная.** Из 19 ничейных заявок 12 заводит мониторинг; одним списком
  секция читается как «команда не справляется», хотя людских там семь.
- **Состояние внешней системы отличает аварию от собственной поломки.** Когда
  падает опрос мониторинга, офлайн уходит весь парк разом и с одной ошибкой —
  это одна авария, а не N. Признак вырождения считает бэкенд
  (`pollLooksBroken`: одновременная группа ≥ 80% парка + общая ошибка), блок в
  этом режиме сворачивается в строку состояния. Цена ошибки разная: в первом
  случае едут к клиенту, во втором чинят у себя.
- **Ссылка «дальше» ведёт в раздел с уже проставленным фильтром**, а не в его
  пустое начало: «Все закрытые» с главной клиента открывает архив с периодом и
  инициатором (`/archive?from&to&applicants`). А если раздела человеку не
  видно, ссылки нет вовсе: обещание, которого интерфейс не держит, хуже
  отсутствия ссылки.
- **«Своё» не спрашивает права на раздел.** Блок про собственные данные
  человека гейтится модульным рубильником, но не правом, открывающим чужие:
  `canUseInventoryModule` открывает раздел «Устройства» целиком, его нет ни у
  одного из 676 клиентов и быть не должно, — а собственный стол клиент видеть
  обязан. Такому блоку заводится своя ручка вне закрытого префикса, скоуп в ней
  считает токен, параметра с id нет (`/my-workplace` →
  `location.getMyTech`). Общий компонент получает проп режима (`TechSection
  self`), а не форк.

## Страница отчёта и графики

Эталон — «Компании» (`pages/Report/Companies.tsx`, первый мигрированный
отчёт; макет согласован до кода). Правила — для всех будущих отчётов
(финансовые и т.д.).

**У отчёта та же анатомия, что у справочника: сводка по всем → карточка
одного.** Отчёт отвечает на вопрос о множестве («сколько времени по
компаниям»), но следующий вопрос всегда про один элемент этого множества —
и он не должен уводить в другой раздел или раскрываться аккордеоном в строке
списка. Строка сводки ведёт на карточку (`/report/companies/:companyId`),
карточка строится по правилам «Страницы сущности» (крошки → hero с
плиткой-логотипом → секции-панели), период переносится со сводки, а не
сбрасывается.
Третий уровень заводим только если у сущности есть собственная структура
(подразделения клиента), а не ради красоты.

**Один предмет — один отчёт.** Срез «по сотрудникам» жил в отчёте о компаниях
и дублировал отчёт «Сотрудники»: две страницы отвечали на один вопрос разными
цифрами. Если разрез повторяет предмет соседнего отчёта — он переезжает туда,
а не живёт в обоих.

**Режимы отчёта — сегмент в тулбаре, не вкладки** (`?view=`): «Сводка |
Динамика» у «Компаний», «Статистика | Переработки | Динамика» у «Сотрудников».
Режим по умолчанию отвечает на главный вопрос отчёта: у отчёта о людях это
«чем занималась команда», а не «сколько доплатить». Переключатели, влияющие на
все режимы (период, «только согласованные работы»), живут в шторке фильтра —
иначе в одном режиме они видимы, а в другом действуют незаметно.

**Каркас** — `app/PageShell`, общий для отчётов, календаря команды,
согласования работ и главной:

- Заголовок в языке `ListWrapper` (h1 + тулбар справа), но сам `ListWrapper`
  не используется — у отчёта нет поиска/сортировки/пагинации.
- Режимы отчёта — `Segmented` в тулбаре, активный несёт query
  (`?view=trends`) — канон «Архива»: у каждого режима свой zustand-стор
  (`store/reports/*`), ремоунт при переключении, параметры переживают уход со
  страницы. Гейт между режимами не нужен, пока права эндпоинтов одинаковые.
- **Период — `app/MonthStepper`, дефолт отчёта — текущий месяц** (живой
  взгляд на «сейчас»; у архива — прошлый, там текущий «ещё не история»).
  Произвольный период — в Sheet-фильтре (`Report/FilterSheet` — та же шторка,
  что у списков) одним полем `app/DateRangeField`; кнопка фильтра —
  `success`, когда
  период произвольный (`isFullMonthRange` из `util/period`). Кнопки
  «Сформировать» нет: открытие страницы сразу строит отчёт, смена любого
  параметра сама делает запрос.
- Сторы: seq-guard от гонок листания (поздний ответ старого периода не
  перетирает свежий); **ошибка не сбрасывает `data`** — устаревший отчёт
  остаётся под danger-баннером с «Повторить». Контракт UI:
  `isLoading && !data` — скелет раскладки, `isLoading && data` — приглушение
  `opacity-60`.
- Экспорт (Excel/CSV) — outline-кнопка-меню в тулбаре; `xlsx` подгружается
  динамически в момент экспорта, в чанк страницы не входит.
- Тяжёлые страницы (recharts) — **lazy-роут** (`route.lazy` в `App.jsx`,
  первый — аналитика): чанк не грузится тем, кто отчёт не открывает;
  протухший после деплоя чанк закрывает `vite:preloadError` в `main.jsx`.

**KPI-плитки** — `app/StatTile` + `StatTileDelta`: значение периода + дельта
к **предыдущему периоду той же длины** (бэкенд отдаёт `totals` и
`prev.totals`, проценты считает фронт). Подпись базы сравнения («к прошлому
периоду») обязательна.

**Графики — только shadcn chart (recharts):**

- Каждый график — `ChartContainer` + `ChartConfig`, цвета **только**
  `var(--chart-N)`/токены. Хардкод-цветов (hex/hsl-радуг) в графиках не
  бывает. `components/ui/chart.tsx` сгенерён CLI (в условных классах
  индикатора тултипа точечно доставлен пропущенный префикс `` — брак
  генератора; при перегенерации проверить).
- **Палитра `--chart-1..5`** (`styles/tailwind.css`): порядок слотов
  фиксированный — это механизм различимости при дальтонизме, не косметика;
  тёмная тема — свои затемнённые ступени тех же оттенков. Менять — только с
  прогоном валидатора dataviz-скилла против поверхностей `#fff`/`#1d2024`.
  Красного слота нет намеренно: статусные цвета (destructive/warning) не
  бывают рядовыми сериями.
- **Цвет закреплён за сущностью, не за рангом**: классы работ всегда
  Выезды = chart-1, Удалённо = chart-2, Регламент = chart-3
  (`Report/ClassLegend`); в «Динамике» слоты раздаёт базовый порядок компаний
  (по суммарному времени) — переключение метрики ничего не перекрашивает.
- **Форму выбирает задача**: одна величина — стат-плитка, не график; величина
  по категориям / состав целого — горизонтальный стек-бар
  (`Report/StackedTimeBars`); изменение во времени — линии. Двухосевых
  графиков не бывает; сумма и слагаемые на одном графике не смешиваются.
- **Серий больше пяти не рисуем**: хвост сворачивается в «Прочие» (в барах —
  серая полоса-хвост, в линиях — пунктир `--faint`); произвольный выбор
  серий — `ChipMultiCombobox`, максимум 5 (слоты палитры).
- Светлые слоты палитры на белом ниже контраста 3:1 ⇒ **подписи значений на
  графике либо таблица рядом обязательны** (у стек-баров — сумма у конца
  полосы через `LabelList`).
- **Hover обязателен**: `ChartTooltip`, контенты — **только**
  `ChartTooltipContent`/`ChartLegendContent` (div-разметка; сырые recharts
  `Legend`/`Tooltip` рисуют несброшенные ul/li — preflight выключен). Точки
  линий — только на наведении (`activeDot`), тултип сортируется по значению.
- **Высота графика — явная** (`aspect-auto` + вычисляемый `style.height`):
  aspect-контейнер от нефиксированного родителя схлопывается в ноль в
  мобильном app-shell; у горизонтальных баров высота = строки × шаг.
- Оси и сетка рецессивные (`faint`/`border-soft`), у линий — без вертикальных
  линий сетки.

**Таблицы отчёта**: shadcn `ui/table` в панели с `overflow-x-auto`
(страница никогда не скроллится горизонтально); сортировка — локальный state
таблицы (в стор не уезжает), «Итого» — в `TableFooter`; детализация —
раскрытием строки в bar-list (`Report/BarList`: одна величина — один оттенок),
а не отдельным аккордеоном.

**Карточки-метрики** (`Report/MetricCards`) — паттерн «сводка =
переключатель»: карточка показывает изменение метрики и спарклайн «Итого» и
одновременно выбирает метрику главного графика (активная — рамка `primary`).
Один элемент делает две работы — пять больших графиков легаси сжались в один.

## Экраны-конвейеры (документ идёт по стадиям)

Эталон — «Согласование работ» (`pages/Finances/Approval.tsx`, макет согласован
до кода). Отличие от отчёта: здесь не «сколько», а **где застрял документ и что
он ждёт**. Отсюда правила.

**Рейл стадий вместо стопки таблиц.** Плитки стадий со стрелками
(`Report/PipelineRail`) — метка · сумма крупно (`tabular-nums`) · «N отчётов» ·
строка часов («автоподпись через 2 дн.», «самый старый — 12 дн.»). Плитка
одновременно фильтрует список под собой — тот же канон «сводка = переключатель».
Стадии **не раскрашены**: цвет тратится на активную плитку, часы и главное
действие. Возврат документа (отклонён клиентом) — не стадия конвейера, а строка
под рейлом: это возврат в нашу работу, а не движение вперёд.

**Одна информация — один вид.** Карточка документа одна на все поверхности —
нам, клиенту в приложении и клиенту по ссылке из письма
(`Report/ReportCard`). Различаются только ДЕЙСТВИЯ, и их выбирает состояние
документа, а не поверхность: подпись ставится под одной и той же бумагой, каким
бы путём человек до неё ни дошёл. Данные для карточки тоже собирает один код на
сервере — иначе виды разъезжаются молча.

**Клиенту — список дел, а не конвейер.** Он не гоняет документы по стадиям: у
него есть «ждут вашей подписи» карточками и «подписанные» таблицей. Форму меняет
скоуп с сервера, страница остаётся одна. Фильтр периода на список дел не
распространяется — забытый месяц обязан остаться видимым.

**Вычисляемые наборы — не фильтр.** Если строка попадает в две таблицы разными
кусками (работа, начатая в рабочее время и законченная в нерабочее), фасет
поверх общего списка этого не выразит: таблиц должно быть две. И наоборот — там,
где деления нет (почасовая оплата), таблица одна, без пустого уточнения в
подписи.

**Фильтр обязан называть свой итог.** Под отфильтрованной таблицей стоит не
«Итого», а «Итого по «X»», и рядом сказано, что общий итог ниже — по документу
целиком. Иначе частичная сумма читается как отчётная.

**Маршрут подписей** (`Report/SignatureRoute`) — свёрнутый узел по умолчанию,
всегда, а не «когда веток много»: порог означал бы, что один документ выглядит
по-разному у разных клиентов. Свёрнутый отвечает на «сдвинулось ли» (полоса по
сегменту на подпись — масштабируется на любое число) и «кто держит» (имена).
Развёрнутый — дерево, где **отступ означает полномочия**: подписант верхнего
узла вправе решить за своих потомков. Состояния, которые блокируют движение
(отказ, «подписывать некому»), видны и свёрнутым — это не очередь, а остановка.

**«В очереди» — не «ждём».** Очередь идёт снизу вверх: пока черёд не наступил,
у человека нет ни письма, ни ссылки, и показывать его наравне с теми, от кого
решения ждут сейчас, значит валить вину не на того — поэтому у ожидания два
разных состояния. Как считается сама очередь — в шапке `SignatureRoute`.

**Своя роль называется по-разному по обе стороны.** «Мы» понятно только нам; в
клиентском виде первый узел маршрута — наименование компании-исполнителя, иначе
он не сообщает получателю ничего.

**Объём зрителя режет сервер, а не интерфейс.** Промежуточный подписант видит
свои работы и работы подчинённых подразделений, а из денег — только то, по чему
он решает (у нас это оплата сверх тарифа). Итог договора, ставки и тарифы ему не
отдаются вовсе, и секции с ними не рендерятся. Прятать в браузере бесполезно:
данные всё равно приехали, а персональная ссылка из письма — тем более не окно
во весь документ. Строку с нулевой суммой не показываем совсем: ноль в выписке
заставляет искать подвох там, где его нет.

**Уже решённое отмечается тихо.** Родитель видит подписанные детьми строки —
это контекст, а не предмет его решения, поэтому пометка сдержанная и живёт
только пока документ на согласовании: на закрытом подписаны все части, и
подсветка залила бы таблицу целиком.

**Деньги считает сервер.** Единственный источник — сервис расчёта
(`backend/services/servicePlanBilling.js`). Клиент не подписывает цифру,
посчитанную чьим-то браузером, а второй алгоритм на фронте гарантированно
разъедется с первым.

**Предварительную цифру считает тот же код, что и выставляемую.** «Примерно»
не даёт права на второй алгоритм: предпросмотр, который расходится со счётом,
хуже отсутствующего — по нему принимают решения и на него ссылаются в споре.
Поэтому у предпросмотра нет своей формулы, он зовёт функции биллинга
(`backend/services/workPreview.js` → `servicePlanBilling`), и на клиент цифра
приезжает готовой. Проверка расхождения — сверка ручки предпросмотра с
карточкой отчёта на одной и той же работе. **Право видеть сумму тоже решает
сервер**: без него денежного ключа в ответе нет вовсе, и интерфейс не рисует
строку — прятать в браузере то, что уже приехало, бессмысленно.

## Письмо-уведомление тоже интерфейс

Для половины согласующих письмо — единственная поверхность: в приложение они не
заходят. Правила выведены из разбора первой версии, которую приняли за спам
(`backend/services/mail/approvalEmailTemplate.js`).

- **Тема называет отправителя и действие.** «Отчёт на согласование» не сообщает
  ничего; «F1Lab · отчёт за июль 2026 — согласование работ «РА ДВ Регион»»
  отвечает на «от кого, о чём, что от меня нужно» ещё в списке входящих.
  Отправитель — наша компания, а не компания получателя: своё название в
  собственном ящике человеку ничего не говорит.
- **Тема обязана отличать письма друг от друга.** Один человек бывает
  руководителем нескольких подразделений; пачка одинаковых заголовков
  схлопывается почтовыми службами в одну переписку, и нужное письмо не найти.
- **Достоверность делают факты, а не оформление**: обращение по имени, названная
  роль, выписка «подпись → значение» (период, объём, деньги), одно действие,
  и сказано, почему письмо пришло и что будет, если не отвечать.
- **Ни одной внешней картинки.** Заблокированные изображения — первое, из-за
  чего письмо выглядит мусорным, а логотип из сети блокируется всегда. Бренд —
  типографикой и одной акцентной полосой.
- **Рамки почты, а не выбор вкуса**: таблицы вместо flex/grid, стили инлайном,
  системный шрифт (вебшрифты не грузятся). Тёмная тема — `@media`, её понимают
  не все клиенты, поэтому светлый вариант базовый и самодостаточный.
- **Служебное — только там, где работает.** Маркер «пишите ответ выше» стоит
  ровно в тех письмах, ответ на которые вернётся в систему: тема называет
  заявку (`[F1-HD-51713]`), и ответ станет комментарием — по маркеру отрезается
  цитата. В коде подтверждения, письме об отсутствии, отчёте на согласование
  отвечать некуда, и строка обещает переписку, которой не будет.

## Формы → нижняя шторка

Это центральный паттерн приложения. Форма добавления/редактирования — **вложенный
маршрут** (`add`, `update/:id`) той страницы, с которой её открывают, и
рендерится в **шторке, выезжающей снизу** (десктоп — колонка 672px по центру,
мобайл — почти весь экран).

**Механика:**

- **Открыта ли шторка, решает маршрут.** Маршрут формы несёт свою шторку в
  `handle`: `handle: SHEET_MD | SHEET_LG | SHEET_XL` из `app/FormOutlet` (с
  гейтом прав — `{ can: {…}, ...SHEET_MD }`). Пока такой маршрут совпадает с
  адресом, шторка открыта; общего флага «шторка открыта» и обработчиков на
  ссылках нет — ссылка на форму просто ведёт на её адрес, и прямая ссылка
  работает так же. **Исключение:** формы базы знаний открываются в основной
  панели — у их маршрутов `sheet` в `handle` нет.
- **Шторку рисует один хозяин — `app/FormOutlet`** вместо `<Outlet/>`: в
  `app/ListWrapper` (`renderOutlet`), на карточках и на главной. Вложенный
  маршрут без `handle.sheet` он рисует как обычный `Outlet`.
- **Форма заводится вложенным маршрутом каждой страницы, с которой её
  открывают.** Маршрут решает, что видно за шторкой: откроете со списка форму,
  которая живёт под карточкой, — за затемнением окажется карточка, страница, с
  которой человек не приходил, да ещё и лишним запросом её лоадера. Пара для
  сущности: `update/:id` в детях списка и `update` в детях карточки. У формы
  заявки хозяев больше (список, главная, карточка шаблона), и её маршруты
  собирает фабрика `routes/ticket-forms.jsx` — `ticketFormRoutes({ prefix,
  modes })`. `..` после сабмита сам ведёт к хозяину.
- **Шторка открывается по готовности — один раз и уже с формой.** Роутер
  рендерит маршрут после его лоадера, поэтому форма появляется в шторке в том
  же кадре, что и сама шторка: заглушек и доигрывания высоты «по приезде» нет.
  Чтобы ждать было нечего, справочники формы (`*/form-data`, каталоги для
  селектов) лоадер берёт из кэша `store/form-data` (`load(path)`: свежее —
  сразу, устаревшее — сразу и обновление в фоне), а страница-хозяин прогревает
  его при монтировании (`warm(path)`). **Сама сущность в кэш не попадает
  никогда** — её правят многие и часто; лоадер правки всегда запрашивает её
  заново (у заявки — `GET /api/tickets/:num?view=form`, без карточных данных).
  Переход дольше 200 мс показывает курсор ожидания и **линию ожидания на
  нижней границе бара оболочки** (`app/NavProgress`; признак
  `html[data-navigating]` ставит `layout/Root.jsx`): линия стоит на черте, под
  которой появится страница, одинаково на десктопе, в браузере телефона и в
  PWA.
- **Закрытие — сперва анимация, потом переход.** Форма не переходит сама, а
  просит хозяина: `useFormSheet().close(to?, { replace })` из `app/FormOutlet`
  (за обычные формы это делает `app/FormWrapper`). Шторка уезжает с ещё
  смонтированной формой, и только затем происходит переход. `close()` — как
  «Отмена», крестик и `Escape`: назад по истории, если форму открыли в
  приложении, иначе (прямая ссылка на форму) на адрес хозяина с `replace`;
  `close("..", { replace: true })` — успешный сабмит; `close("/tickets/42",
  { replace: true })` — карточка созданной сущности. Относительные адреса
  форма разрешает у себя (`..` — родительский маршрут). «Назад» браузером при
  открытой шторке снимает маршрут раньше анимации — шторка доигрывает уход
  пустой, на замороженной высоте.
- **Клик по свободной области экрана не закрывает шторку формы на десктопе**
  (`app/FormSheet` гасит `onInteractOutside` при `!isMobile`) — защита от
  случайной потери данных в наполовину заполненной форме. Закрыть можно
  **крестиком**, **успешным сабмитом** или **`Escape`** (все идут через
  `onOpenChange`); `Escape` закрывает ВСЕ шторки приложения одинаково — его
  не гасить. На мобайле — поведение по умолчанию (тап по затемнению
  закрывает).
- **Ширина шторки на десктопе — под контент, но не под место открытия.**
  Шкала одна (`size` в `handle.sheet` маршрута): **`md` 672** — обычная форма
  в один столбец, **`lg` 896** — мастер со сводкой справа, **`xl` 1024** —
  форма с рейлом секций (рейл 192 + колонка полей). Мобайл — всегда почти
  весь экран. **Одна и та же форма — одной ширины со списка, с карточки и с
  главной:** ширина живёт на маршруте формы, хозяин её не выбирает.
- **Скроллится внутренность шторки, а не она сама** (`FormSheet` держит
  `overflow-hidden`, скролл — на внутреннем контейнере). Иначе крестик radix
  (он `absolute`) уезжает вверх вместе с содержимым длинной формы. Этот же
  контейнер шторка отдаёт через `OverlayScrollContext` — по нему работает
  `app/AnchorRail` внутри формы: на `window` скролла там нет.
- **Высота шторки — измеренное число, а не `auto`.** Содержимое открытой формы
  меняется (раскрылась секция, появились ошибки полей, приехал ленивый
  редактор), и `FormSheet` проводит смену высоты переходом (200 мс,
  `ease-out`, с `motion-reduce`), меряя содержимое `ResizeObserver`'ом. На
  закрытии высота замораживается до размонтирования, а следующее открытие
  стартует с настоящей высоты формы. Обёртке с высотой нельзя давать
  `overflow: hidden` — она станет скролл-контейнером, и липкие шапка и ряд
  кнопок прилипнут к ней вместо прокручиваемой внутренности. Ленивые блоки
  резервируют место сами (`UI/MarkdownEditor` ставит `min-height` на высоту
  редактора), чтобы шторка не подрастала вторым движением.
- **Въезд шторки не зависит от её высоты.** Нижняя шторка растёт по
  содержимому, поэтому анимации «подняться на 100% собственной высоты» ей
  нельзя: точкой отсчёта у такой анимации служит сама высота, и смена
  содержимого посреди анимации утаскивает шторку обратно вниз. `ui/sheet`
  поднимает `side="bottom"` на фиксированные **6rem с проявлением**: 300 мс
  `ease-out` на открытие, 200 мс `ease-in` на закрытие. Проценты собственного
  размера остаются боковым шторкам — там ширина задана классом, и 100% есть
  от чего считать.

**Оболочка формы — `components/app/FormWrapper`:**

- `fetcher.Form method="post"` (router-actions), сабмит без перезагрузки.
- Заголовок формы; кнопка закрытия — крестик самой шторки.
- Ошибки/успех — `AlertMessage` (`variant="danger"`/`"success"`).
- Кнопки справа внизу: **«Отмена»** (ghost) и **«Сохранить»** (primary,
  `disabled` пока идёт сабмит); на мобайле ряд липнет к низу шторки.
- При успешном сабмите — `useFormSheet().close(successTo ?? "..", { replace:
  true })`: шторка уезжает, затем переход (см. «Механика» выше).

**Раскладка полей внутри формы:**

- Каждое поле — **`app/Field`** (лейбл + `required`-звёздочка + контрол +
  `hint`); свитчи — **`app/SwitchField`** (подпись + подсказка-эффект + скрытый
  input `"true"/"false"` для FormData). Руками эти блоки не собираем.
- **Подпись контрола всегда связана с контролом** — `<label htmlFor>` либо
  label-обёртка: клик по подписи переключает свитч/чекбокс и фокусирует поле
  (площадь клика, тач, скринридеры). Каталог делает это сам: `Field` /
  `SwitchField` — из коробки, `SettingRow` — пропом `htmlFor` (обязателен для
  строк с одним контролом). Подпись-«div» рядом с контролом без
  связи — баг; связать не с чем (иконка-кнопка, ячейка матрицы «событие ×
  канал») — тогда `aria-label`.
- **Выпадающий список — всегда `app/Combobox`** (или `MultiCombobox`), длина
  набора роли не играет. Значение уходит в `FormData` пропом `name`; у
  множественного выбора это по скрытому полю на каждое значение, чтобы
  `formData.getAll(name)` вернул список, а не склеенную строку.
- Два поля в ряд — `grid gap-3 md:grid-cols-2`; узкие экраны
  схлопываются в один столбец.
- Длинную форму делим на секции `ui/Card` с заголовком — это способ «разбить»
  форму без модалок-вкладок.
- Даты — `app/DateField`, период — `app/DateRangeField` **одним полем** (не
  пара «с / по»), дата со временем — `app/DateTimeField`; в стейте по-прежнему
  строки `yyyy-MM-dd` / `yyyy-MM-ddTHH:mm`. Время — `app/TimeInput` («ЧЧ:ММ»,
  нативный `type="time"` без браузерного индикатора). Голые нативные
  `<input type="date" | "datetime-local" | "time">` в формах не используем.

### Навигация после сабмита (куда попадает пользователь)

Правило трёх исходов — его нарушение дезориентирует («создал модель с
карточки типа — оказался на списке моделей»):

1. **Создание сущности, у которой есть карточка, → карточка созданной
   сущности**, а не список. `successTo` у `FormWrapper` принимает функцию от
   ответа action — она строит адрес из `_id` созданного объекта (значит,
   бэкенд-ответ обязан содержать созданную сущность; наши `add`-контроллеры
   уже так отвечают). Эталон — `pages/DeviceModel/Add.jsx`,
   `pages/DeviceType/Add.jsx`. У сущности без карточки (вендор, атрибут)
   исход по умолчанию — остаться на списке (`".."`).
2. **Редактирование → остаёмся там, где были.** Форма правки — вложенный
   маршрут той страницы, где её открыли: у списка — `update/:id` в его
   шторке, у карточки — `update` в шторке самой карточки (после сабмита
   `".."` возвращает на неё). Кнопка «Изменить» на карточке никогда не
   уводит на список (`components/DeviceModel/View.jsx`,
   `components/DeviceType/View.jsx`).
3. **Создание с «чужой» страницы → форма открывается вложенным маршрутом
   этой страницы.** «Новая модель» на карточке типа — это `models/add`
   на карточке типа (шторка на месте, контекст не теряется), а не переход
   на список моделей; после успеха — п.1, карточка созданной модели.

**Отступление от п.1 — когда создание было шагом чужой задачи.** «Новая услуга»
из карточки компании возвращает **на карточку компании**, а не на карточку
созданной услуги: пользователь настраивал компанию, а услуга — средство. Такое
отступление допустимо, только если создание начато ради родителя и названо
этим же словом в интерфейсе; во всех прочих случаях действует п.1.

Механика в `app/FormWrapper`: по успеху `close(successTo ?? "..",
{ replace: true })` через `useFormSheet` — сперва анимация ухода шторки,
затем переход; запись формы не остаётся в истории, поэтому браузерное
«назад» с карточки созданной сущности возвращает на страницу, где открыли
форму создания. Дополнительно карточка даёт постоянный путь вверх по иерархии:
родительская сущность в hero — ссылка (тип устройства на карточке модели),
а не просто текст.

## Диалоги → только мелкие вещи

Модальные диалоги — для **подтверждений и коротких действий**, не для форм.

Эталон — **`components/app/DeleteItem.tsx`**:

- `AlertDialog` + `RouterForm method="post"`: заголовок — название удаляемого,
  текст — **«Вы уверены? Это действие нельзя отменить.»**, скрытый `id`,
  футер — **«Отмена»** и **«Удалить»** (`destructive`, `intent="delete"`) — по
  «Словарю действий»: у диалога есть сабмит, меняющий данные, значит «Отмена».
- Из «⋯»-меню диалог открывается **состоянием** (`DeleteDialog` рендерится вне
  radix-меню — меню размонтирует содержимое при закрытии), это уже собрано в
  `app/ListRow`.
- Диалог закрывается на сабмите: строка исчезнет с редиректом экшена, и
  открытый модальный radix оставил бы залипший `pointer-events` на `<body>`.
- **Отказ в удалении объясняем на месте.** Бэкенд не всегда даёт удалить: за
  записью числится история (модели у вендора, закупки у поставщика). Тогда
  экшен возвращает `{error, message}`, а экран показывает тост `danger` с
  причиной **и выходом**: «За поставщиком числится 5 устройств — удаление
  оставит их без источника закупки. Отключите поставщика вместо удаления».
  Проглоченный 409 читается как «кнопка сломана».

Если полей становится много или появляется логика в несколько экранов — это
уже не диалог, переносите в шторку/мастер.

**Не делать:** длинные формы создания/редактирования в диалоге; вложенные
диалоги; диалог ради того, что укладывается в шторку снизу.

## Большие многошаговые формы → горизонтальный прогресс

Для мастеров (несколько логических шагов) сверху показываем **горизонтальный
индикатор прогресса**, чтобы пользователь видел, где он и сколько осталось.
**tw-эталон** — `components/ServicePlan/Form.jsx` (мастер услуги, макет
согласован до кода).

**Когда дробить форму на шаги.** Если полей много и они распадаются на
**логические этапы** (у услуги: «Основное» · «Тарификация» · «График») — это
мастер, а не одна простыня. Форму разбиваем на шаги с валидацией по шагу и
кнопками «Назад»/«Далее»/«Сохранить»; механика во всех мастерах одна — массив
`STEPS`, `stepValid(i)`, `maxReached`, `attempted` (см. `ServicePlan/Form.jsx`).
Длинную, но **одно-логическую** форму мастером не притворяем — её достаточно
разбить на секции (см. «Раскладка полей» выше).

**Создание — визард, правка — плоская.** Один и тот же набор полей в создании
проходят по шагам (визард со сводкой), а в правке дают **одной простынёй секций
без степпера**: правят обычно одно поле, гонять его по шагам — лишний путь
(`isEdit ? <секции> : <визард>`; эталон — `TicketTemplate/Form.jsx`).
Набор полей у создания и правки **совпадает**: появилась секция в правке —
появился шаг в мастере (график работы у сотрудника — пятый шаг).

**Длинной форме — рейл секций, как на карточке.** Каркас общий —
`components/app/FormLayout`: `FormHeader` (липкий заголовок формы; высоту
отдаёт наружу) + `FormSections` (секции одним скроллом и `app/AnchorRail`
слева — десктоп; на мобайле секции идут подряд, как на карточке). Ключ секции
= якорь: ярлык «Изменить» в метке секции карточки открывает форму хешем
(`update#schedule`, `update#checklist`), и она открывается уже прокрученной к
нужному месту. Шторке такой формы даём `xl`. Табы внутрь формы не
заводим — рейл держит контекст и не прячет остальные секции.
**Форма подстраивается под тип сущности.** Если от одного переключателя зависит,
применима ли половина полей, — не показывайте неприменимое серым, **убирайте шаги
целиком**. У пользователя тип аккаунта (сотрудник / клиент / служебный) решает
набор шагов: клиенту не нужны права, категории и финансы, служебному — почти
ничего. Взаимоисключающие флаги модели при этом собираются в **один сегмент**, а
обратно в флаги — при сабмите (`kindToFlags`), а не тремя свитчами в форме.

**Файлы в форме — FormData, и только она.** Вложения в JSON не положить,
поэтому форма с файлами собирает `FormData` сама (проп `formData` у
`app/FormWrapper`), а router-action пересылает тело как есть — `Content-Type`
руками не ставим, boundary собирает браузер. Тот же проп даёт форме право
отменить отправку: вернуть `null` вместо тела значит «рано» — ошибки показались
у своих полей, и заранее блокировать «Сохранить» не пришлось (заблокированная
кнопка не объясняет, чего не хватает).

**Сложное вложенное тело — JSON, а не FormData.** Пока форма плоская, полей с
`name` достаточно. Как только в теле появляются вложенные объекты и
массивы (права по модулям, матрица уведомлений, список компаний), ручная сборка
из `FormData` становится источником тихих потерь — пропущенный ключ, опечатка в
имени поля, строка `"true"` вместо boolean (всё это было в форме пользователя).
Тогда форма собирает объект сама и шлёт `fetcher.submit(payload, { method:
"post", encType: "application/json" })`, а router-action просто пересылает тело.

**Длинные наборы флагов — по модулям с «рубильником».** Группа = панель с
мастер-свитчем в шапке и счётчиком «N из M»; выключенный модуль гаснет.
Зависимое поле живёт **внутри** своего права (категории заявок — под
«Выполнение заявок»), а не отдельной вкладкой.

**Один каталог на показ и на правку.** Набор прав/способностей описывается один
раз (`User/permissions-catalog.js`) и питает и форму, и карточку. Два списка
неизбежно расходятся: у формы не было трёх прав модели, а `permissions =
permissions` сбрасывал их при каждом сохранении.

**Чужие личные настройки правим с предупреждением.** Если админ меняет из формы
то, чем обычно управляет сам пользователь (уведомления): объект уходит на сервер
**только если его действительно трогали** — иначе сохранение затрёт чужой выбор;
рядом — предупреждение «перезапишете личный выбор»; бэкенд мержит значения по
путям, а не заменяет поддокумент целиком.

**Необязательный шаг можно пропустить** — на нём рядом с «Далее» стоит
«Пропустить» (шаг чек-листа в шаблоне и регламенте: заполнять не обязаны, а
сам блок потом правится с карточки).

**Степпер — `components/app/WizardStepper.tsx`** (tw, готовый):

- Ряд кружков 32px с номером; пройденные — `RiCheckLine`. Состояния токенами:
  текущий/пройденный — `bg-primary text-white`; будущий — `bg-accent text-faint`
  + `inset-ring`; подписи — `accent-text` / `muted-foreground` / `faint`.
- Между кружками — линия-коннектор (`bg-primary` для пройденного участка,
  `bg-border` для оставшегося).
- Клик по шагу — в режиме правки (`allowJump`) или по достигнутым (`maxReached`).
- **По умолчанию тянется на всю ширину контейнера** (`flex` + дети `flex-1`). На
  форме со сводкой это обязательно: степпер идёт **во всю ширину шторки**, а не
  обрывается над левой колонкой — иначе лента шагов смотрится оторванной от
  сводки. Нужен узкий — задайте `max-w-*` через `className`.

  ```jsx
  <WizardStepper
    steps={[{ label: "Основное" }, { label: "Тарификация" }, { label: "График" }]}
    current={step}
    maxReached={maxReached}
    allowJump={isEdit}
    onStepClick={handleStepClick}
  />
  ```

**Живая сводка справа — у большой формы-мастера обязательна.** Панель
(`components/ServicePlan/Summary.jsx`) наполняется по мере прохождения шагов
(незаданное — «—», разделы раскрываются по `maxReached`) и держит контекст:
название, категории, цена, график видны сразу, не листая шаги назад. Под сводку
шторку **расширяем до `lg`** (`handle: SHEET_LG` у маршрута формы),
колонки — `flex flex-col md:flex-row` (контент `flex-1`, сводка
`md:w-72`).

**Прогресс-бар вместо степпера** — когда нужен процент выполнения/готовности,
а не дискретные шаги: тонкая полоса, над ней компактная подпись и счётчик
«N / M», вариант по состоянию (готово — `success`, в процессе — `primary`).

## Панели настроек: селектор → условный блок

Экран настроек с выбором внешнего сервиса строится по паттерну «селектор →
условный блок конфигурации» (живой пример — секция «Искусственный интеллект»
настроек системы, `components/Preferences/Ai.jsx`):

- **Мастер-переключатель** (свитч) включает раздел; пока он выключен, все поля
  ниже идут `disabled`.
- **Селект выбирает вариант** (провайдера) и раскрывает его блок настроек;
  у каждого варианта — свой набор полей: секреты — всегда input
  `type="password"`, специфичные поля добавляются точечно (например,
  «Идентификатор каталога (folder ID)» у Yandex AI Studio).
- **Динамический список «по ключу»** — когда варианты подгружаются от сервиса
  по введённому ключу: селект + кнопка обновления рядом (`RiRefreshLine`, на
  время запроса — спиннер). Плейсхолдер «— загрузите список —», уже
  сохранённое значение остаётся выбираемым (даже если его нет в свежем
  списке), ошибка загрузки — инлайн-текстом у поля.
- **Ручной ввод идентификатора — последнее средство.** Прежде чем ставить
  текстовое поле «введите название модели», проверьте, отдаёт ли сервис
  каталог: у всех поставщиков ИИ он нашёлся, и ручной ввод обернулся
  опечатками, которые видно только по ошибке провайдера. Статический список в
  коде — тоже долг: каталог у поставщика меняется без нас.
- **Вариант — это протокол, а не название продукта.** Если два сервиса
  различаются только адресом, в селекторе им место одно: «Локальная модель» —
  это и Ollama, и LM Studio, и vLLM, и llama.cpp, у которых один и тот же
  OpenAI-совместимый вход. Отдельные пункты на каждый продукт были бы
  одинаковыми формами с разными подписями, а список пришлось бы дополнять
  каждый раз, когда появится ещё один. Названия продуктов живут в подсказке
  поля адреса — там они помогают, а в селекторе только множатся.
- **Не спрашивайте дважды одно и то же.** Когда соседний блок настроен на тот
  же сервис, дайте переключатель «использовать данные основного провайдера»
  вместо второго поля для того же ключа. Переключатель показывают всегда, но
  гасят для несовместимых пар, и подсказка называет причину («Anthropic не умеет
  распознавать речь») — исчезнувший элемент заставляет искать, а погашенный
  объясняет. Общими бывают только доступы: модель у каждого канала своя.
- Это **контролируемая конфигурация**, которую сохраняют целиком одним
  объектом, — не router-action форма: селекты здесь работают от `value` +
  `onChange`, без скрытого input и без `required` формы.

### Секция внешнего сервиса обязана отвечать, работает ли она

Включённый свитч — это намерение, а не факт. Секция, которая ходит наружу
(почта, Telegram, интеграция), обязана иметь **строку состояния**
`app/HealthRow` и **действие проверки** — иначе единственный способ узнать,
что канал молчит, это логи контейнера. Эталон — секции «Сбор заявок» и
«Уведомления → почта (SMTP)».

**Каналов в секции столько, сколько ключей.** У «Искусственного интеллекта» их
два — чат-провайдер и распознавание речи, — и строк состояния тоже две, каждая
у своего блока и под своим свитчем. Одна общая строка врала бы: ключи, сервисы
и отказы у них разные.

- **Строка живёт постоянно, а не появляется после нажатия.** Её наполняют
  фоновые процессы (крон сбора почты, реальные отправки уведомлений), поэтому
  она честна и без единого клика; кнопка проверки лишь добавляет свежий факт.
  Хранилище — группа `health` рядом с настройками канала
  (`backend/services/mail/health.js`): `lastOkAt`, `lastMessageAt`,
  `lastError` + `lastErrorHint`, `lastErrorAt`, `consecutiveFailures`.
- **Фраза, а не бейдж** (см. «Статус, который протухает»): цветом красим только
  иконку и состояние, дату и детали — `muted`. Причину сбоя формулирует
  **бэкенд** (`describeMailError`: код ошибки → «что случилось» + «что
  делать»), фронт её не угадывает.
- **Проверка не блокирует сохранение**: сервер может лежать, а настройки
  записать уже нужно. Успешную проверку записываем в `health`, неуспешную —
  нет: проверяют обычно черновик, и красная строка про несохранённые поля
  врала бы о работающем канале.
- **Действие называет результат, а не механику**: у приёма — «Проверить»
  (`RiRefreshLine`), у отправки — «Отправить тестовое письмо»
  (`RiMailSendLine`), потому что успешный коннект к SMTP ещё не значит, что
  письмо примут. Адресат — текущий администратор, отдельного поля нет.
- **Включённый канал валидируется на бэкенде**: неполная конфигурация — это
  канал, который «работает» только на вид. Ответ 422 с человеческой фразой
  («Укажите сервер IMAP — без него письма не забрать») уходит в тост.

### Секреты в настройках

Пароли и API-ключи **наружу не отдаются**: форма рисует `••••••••  (задан)`, а
пустое поле при сохранении означает «не менять» (тот же канон у ключа PRO32 в
`User/UserForm.jsx`). Следствие для формы: список моделей и кнопки проверки
работают с пустым полем — бэкенд подставит сохранённый секрет сам. Контракт
ответа и хранение — в `backend/helpers/preferencesSecrets.js`.

### Поля, общие для двух каналов, — один компонент

Транспорт почты (сервер и порт, режим шифрования, учётная запись, доверие
самоподписанному сертификату) одинаков у приёма и отправки, поэтому его
рисует единственный `Preferences/MailChannelFields`, а различия приходят
пропсами. Дефолтные порты по режиму продублированы в компоненте и в транспорте
бэкенда — менять синхронно (пометка стоит в обоих файлах).

  равно уходят в FormData скрытыми полями с текущими значениями — иначе
  сохранение молча сбрасывает их (закрытый баг легаси).
- Каждая секция-форма — свой `fetcher.Form` с `intent` на action страницы;

- Тема — сегмент трёх состояний light/dark/system (`app/ThemeSegment` через

  в той же секции «Внешний вид»: применяется сразу через `ThemeContext`,

- **Фоновая картинка пользователя**: читаемость текстов канвы обеспечивает
  «лист» в `layout/Root.jsx` (см. раздел миграции), сами экраны про фон не
  знают.
- **Подтверждение внешнего события** (подключение Telegram-бота): после
  действия — revalidate-поллинг loader'а до смены статуса, с гейтом
  `useFetchers().every(f => f.state === "idle")` — ревалидация при живом
  fetcher роняет роутер («Did not find corresponding fetcher result»).
  Статус ожидания — текст с точкой `warning` и подсказкой, что сделать.

Бэкенд-контракт, на который опирается экран: `updateMyAccount` **мержит**

рецепт новой категории лежит в `backend/middleware/notifications.js`.

## Пред-авторизационные экраны

Вход, вход по коду из письма и новый пароль по ссылке из письма. Оболочки
приложения тут нет, тостов тоже (`Toaster` живёт в `Root`) — **всё, что нужно
сказать, говорится на месте**, инлайн-плашкой `AlertMessage` или сообщением у
своего поля.

- **Одна оболочка на все три** (`components/Auth/AuthShell`): слева стойка —
  марка, контакты поддержки и местное время; справа единственный «лист» с
  формой. Экран, который приходит по ссылке из письма, берёт её же: страница
  без брендирования читается как чужая.
- **Свет за листом формы — единственная добавка к общей канве.** Клетку и
  вуаль рисует канва приложения (см. «Тема и цвет → Канва — не ровная
  заливка»), а `.auth-canvas` на оболочке — только ПРИЗНАК экрана, как
  `.mobile-shell` у app-shell: по нему канва включает мягкий бирюзовый ореол
  и ставит его за листом. Больше нигде света нет — якорить его не к чему.
- **В стойке нет ни одной выдуманной строки** — только марка и то, что задано
  в настройках: логотип — `contacts.logo`, не задан — текстовая марка без
  какого-либо знака (своей картинки у приложения нет); подпись под маркой —
  `contacts.title` («Настройки → Основные»), не задана — подписи нет. Фразы
  вроде «Служба поддержки такой-то» в коде быть не может: своего названия у
  приложения нет (компанию-исполнителя везде выводят из автора документа —
  см. `services/reportCard.js`), а до входа автора тоже нет.
- **Тема переключается на месте**, без перезагрузки: как и внутри приложения,
  контекст переключает класс `.dark`. Перезагрузка стирала бы введённый адрес.
- **Режим — маршрут, а не query-параметр.** У каждого экрана свой
  `document.title`, свой экшен и своя кнопка «назад». Общие данные грузит
  layout-маршрут один раз (`shouldRevalidate: () => false`, иначе каждый
  неудачный вход перезапрашивал бы настройки).
- **Композиция ограничена по ширине и центрирована по вертикали.** Без
  ограничителя стойка уезжает к левому краю монитора, а лист — к правому, и
  между ними остаётся пустая половина экрана; без центрирования блок висит в
  верхней части. Внутри композиции колонки выровнены **по верхнему краю**:
  марка и верх листа стоят на одной линии.
- **Стойка — одна ячейка сетки, а не два блока в разных строках.** Пока лист
  пересекал обе строки, браузер размазывал его высоту по ним и отрывал марку
  от фразы под ней. Порядок на мобилке («марка → форма → контакты») задаётся
  `display: contents` + `order`, а не второй разметкой.
- **Вход обязан открыться и без настроек.** Ручка настроек отвечает 500 —
  оболочка рисует себя беднее (фолбэк), но форма на месте: иначе икота на
  настройках запирает снаружи всех разом.
- **И обязан остаться на экране при любой неудаче.** Эти формы не бросают в
  error boundary ничего — ни 500, ни обрыв сети: экран ошибки предлагает
  «вернуться» и «на главную», а человеку, который не может войти, обе дороги
  ведут сюда же, зато введённый адрес теряется. Ответ, где сервер объяснил
  причину, показываем как есть; у 500 текст свой («Сервер не смог обработать
  запрос…»), потому что «Login failed» из журнала выглядит как вина человека.
- **Путь показывается, только если он работает.** Почта выключена — нет «Войти
  по коду из письма»; почта поддержки не задана — нет «Написать в поддержку».
  Обещать неработающее хуже, чем не предлагать.
- **«Не получается войти» — это блок из названных путей, а не микроссылка.**
  Формулировки выбираются по тому, кто на экране на самом деле: большинство
  приходящих не заводили себе учётку сами и пароля не имели, поэтому им «Войти
  по коду из письма», а не «Забыли пароль?» — забывать было нечего.
- **Дорога с экрана входа одна, расходится она после кода.** Экран
  (`/auth/code`) для всех один: адрес, «Прислать код», ввод кода (код, а не
  ссылка: ссылка открывается там, где читают почту, а код — там, где входят).
  Что будет после верного кода, решает сервер по адресу: клиент просто входит
  (пароля у большинства клиентов никогда не было); сотрудник задаёт новый
  пароль и дальше входит паролем и вторым фактором — вход по коду ему не
  положен. До верного кода экран различия не знает и знать не может: ответ
  на запрос одинаков для любого адреса, поэтому он всегда говорит «код
  отправлен». Спрашивать «вы клиент или сотрудник» — вопрос про устройство
  системы, не его забота.
- **Письмо авторизации уходит сразу, и экран знает, ушло ли оно.** Человек
  стоит у экрана и ждёт, поэтому такие письма не откладываются в очередь до
  следующего тика крона: отправка синхронная, и если она не удалась, экран
  говорит «При отправке письма произошла ошибка», а не «код отправлен».
  Ограничитель попыток по-прежнему объясняет себя своим текстом.
- **Шаги живут на одном адресе**, состояние — в данных экшена: адрес → код из
  письма → код из приложения (клиент со вторым фактором) или новый пароль
  (сотрудник; форма — общий `NewPasswordForm`, тот же, что у ссылки из
  письма). Прийти на поздний шаг, минуя предыдущий, нельзя. Неверный код оставляет на шаге кода,
  «прислать ещё раз» — своя форма. Плитка итогового состояния стоит в строке
  заголовка (`AuthHeading tile`), не над ним.
- **Второй фактор — общий шаг** (`components/Auth/TwoFactorStep`): после пароля
  и после кода из письма форма одна и та же, ручка одна и та же. Своего адреса
  у шага нет.
- **Звёздочек обязательности нет.** У входа обязательны оба поля, у остальных
  экранов — единственное; пометка ничего не добавляет. `Field` без `required`,
  `required` остаётся на самом контроле.
- **Подтверждения пароля нет** — его работу делает кнопка показа
  (`app/PasswordInput`), страховка от опечатки — новое письмо с того же экрана
  входа.

## Пароль на экране

Пароль задают в четырёх местах — заведение пользователя, диалог пароля в
карточке, «Безопасность» в профиле, страница по ссылке из письма, — и правило у
всех одно: **поле `app/PasswordPolicyField`**, а не собственная сборка из
инпута и кнопки.

- **Вердикт вместо чек-листа.** Под полем одна строка, которая говорит две
  правды: хватает ли длины и сколько раз пароль встречается в известных
  утечках. Списка «заглавная · цифра · символ» нет намеренно: `Qwerty123!`
  удовлетворяет любому такому набору и встречается в утечках 184 730 раз —
  чек-лист, который его пропускает, не защищает, а учит неправильному.
- **Число вхождений называем вслух.** «Слабый пароль» — оценка, «встречается в
  утечках 78 374 раза» — факт, и он единственный, кто убеждает сменить дату
  рождения на что-то другое.
- **Спрашиваем сервер, а не гадаем на клиенте** (`POST /api/password/check`,
  k-анонимность: наружу уходят пять символов SHA1). Ввод с задержкой, ответ на
  устаревший запрос отбрасывается. Сервис не ответил — пароль принимаем и
  говорим об этом прямо: «проверить не удалось». Запирать человека из-за
  чужого сбоя нельзя.
- **Генератор — с бегунком длины** (8–24, по умолчанию 10) и алфавитом без
  похожих знаков: пароль, заданный администратором, кто-то будет читать с
  экрана или диктовать по телефону. Сгенерированный показывается сразу — его
  для того и сгенерировали.
- **Подтверждения пароля нет** нигде, включая формы внутри приложения: его
  работу делает кнопка показа.
- **Своя смена пароля спрашивает текущий**, чужой сброс — нет. Правило одно на
  всех: администратор чаще всего меняет пароль себе же из карточки, и поле
  «текущий пароль» появляется там, когда карточка своя.
- **Последствие называем в диалоге, а не в тосте после.** «Ваши сеансы на
  других устройствах завершатся. Эта вкладка останется» — до нажатия, рядом с
  кнопкой.
- **Пароль письмом не отправляется.** Вместо него — ссылка, по которой человек
  задаёт свой; в интерфейсе это вторая дорога того же диалога, а не галочка
  «отправить учётные данные». Почта выключена — дорога гаснет вместе с
  вкладкой, причина в `title` (см. «Панели настроек»: погашенный элемент
  объясняет, исчезнувший заставляет искать).

## Роли и права

Права выдаются **ролями**. Матрицы галочек в форме человека нет: она живёт в
форме роли, и это единственное место, где право включают руками.

- **Тип аккаунта и роль отвечают на разные вопросы.** Тип («Клиент /
  Сотрудник / Служебный») говорит, КТО человек: от него зависят разделы формы,
  скоуп заявок и то, каким письмом приглашать. Роль говорит, ЧТО ему можно.
  Подпись под сегментом обязана называть именно это — «от типа зависят разделы
  формы» описывает механику формы и читается как первая ступень раздачи прав.
- **Роль знает своего адресата.** У роли есть поле «Кому назначается»; в форме
  человека роли своего адресата идут первыми, чужие уходят вниз и гаснут.
  Не запрет: выбрать чужую можно, данные дрейфуют. Вывести адресата из самих
  прав нельзя — «Клиент: руководитель» даёт учёт времени и отчёты по работам.
- **Под выбором ролей — «что получается».** Человек выбирает роль, а отвечает
  за права: складывать два-три набора в уме он не должен. Против каждого права
  стоит роль, которая его дала, — это ответ на «почему у него это есть».
  Пустые разделы в список не попадают.
- **Полный доступ не расписывается.** Роль, отдающая весь словарь, показывается
  одной строкой «полный доступ ко всему порталу»: полсотни галочек не
  информативнее одной фразы. Отдельного переключателя «Администратор» нет — он
  и был ролью, только записанной вторым способом.
- **У права одно название, и живёт оно на сервере.** Словарь и подписи к нему
  объявлены рядом (`backend/auth/access.js`) и приезжают на клиент вместе с
  правами. Своего списка подписей у интерфейса нет: пока был, одно право
  звалось «Отчёты по оказанным услугам» в форме роли и «Просмотр общего
  финансового отчёта» в отказе, и человек шёл просить несуществующее.
- **Смотреть и менять — разные права в каждом разделе.** «Видеть технику» без
  «Изменять технику» — обычный, а не исключительный случай; раздел, у которого
  есть только «Управление», нельзя дать посмотреть.
- **Мастер-переключателя раздела в форме роли нет.** Он изображал рубильник
  модуля, а был обычным правом «видеть раздел» — и, будучи снятым, прятал
  соседние строки, скрывая от администратора то, что у роли ещё есть.
  Рубильники модулей живут в настройках установки.
- **Право на раздел стоит на маршруте.** `handle: { can: … }` рядом с адресом,
  проверяет `RouteGuard` в оболочке. Гейт, написанный внутри страницы, легко
  забыть — так полсотни экранов и открывались по прямой ссылке кому угодно.
- **Каталог показывает свои дыры.** Под списком ролей — блок «Права без своей
  роли»: право попадает туда, когда его не даёт ни одна роль, кроме роли с
  полным доступом, то есть выдать его отдельно нельзя. Блок пуст — его нет.
- **Отобрать право у человека поверх роли нельзя.** Нужна точная роль — она
  заводится за минуту. Личные права сверх ролей были переходным состоянием и
  сняты.
- **Носители роли — действующие учётные записи.** Счётчик в каталоге, плашка и
  имена в форме роли считают только тех, кто может ролью действовать:
  отключённые и удалённые не считаются. Отключение роль при этом не снимает —
  человека включают обратно с тем же доступом. Роль, оставшаяся только у
  отключённых, гаснет как «никому не назначена»; второго числа
  («· 1 отключён») в строке нет — в каталоге этот вопрос не задают.

## Сеансы и вход под пользователем

- **Устройство, а не строка User-Agent.** В списке сеансов «Chrome · Windows»;
  сырую строку в интерфейс не отдаём — её не узнаёт никто. Не распозналось —
  «Неизвестное устройство», а не угаданный браузер.
- **«Активна» — это время последней активности**, не срок годности сеанса.
  Человек спрашивает, когда с устройства заходили, а не когда сеанс истечёт.
- **Токен сеанса в интерфейс не попадает никогда.** Строку опознаёт `id`,
  сопоставление «id → токен» не покидает сервер.
- **«Выйти на остальных устройствах» не трогает текущую вкладку** и говорит об
  этом рядом с кнопкой: иначе действие читается как выход.
- **Отключение спрашивает причину и срок**, оба необязательны. Причина — заметка
  администратора администратору, самому человеку она не показывается. Срок
  снимает отключение сам.
- **Вход под пользователем — ссылка в другой браузер, а не подмена вкладки.**
  Своя сессия остаётся живой, поэтому «Выйти» в чужом браузере — обычный выход,
  а не «вернуться к себе»: возвращаться некуда.
- **Полоса подмены видна на каждой странице и не закрывается.** Работа под
  чужой учётной записью — состояние, о котором надо помнить постоянно.
- **Под администратором войти нельзя**, и пункт меню у него не показывается
  вовсе: погашенный он только просил бы объяснений.

## Второй фактор

- **Второй шаг входа — продолжение того же экрана**, а не отдельная страница:
  пароль уже принят. Своего адреса у шага нет намеренно — прийти на него,
  минуя пароль, нельзя.
- **Ошибка в коде не выбрасывает обратно к паролю.** Человек ввёл его верно;
  повторять весь вход из-за опечатки в шести цифрах — то, что раздражает в
  чужих порталах.
- **Резервный код — вторичное действие.** Им пользуются раз в жизни, и рядом с
  основным полем он предлагал бы выбор там, где выбора обычно нет.
- **Включение обязательно подтверждается кодом**, хотя библиотека умеет и без
  этого: человек с неверно настроенным приложением иначе запирает себя
  снаружи.
- **Резервные коды показываются один раз**, с кнопкой скачивания и галочкой «я
  сохранил». Это единственное место в портале, где мы просим подтвердить
  прочитанное, и оправдано оно тем, что второго показа не будет.
- **Выключение спрашивает пароль.** Иначе уведённая вкладка снимает второй
  фактор молча.
- **Показываем всем, не предлагаем никому.** Строка есть и у клиента:
  подсказка объясняет, что это, и не уговаривает включить.
- **Требование к администраторам включается только тем, у кого фактор уже
  есть.** Отсрочка одна не спасает: если за её срок никто не настроил
  приложение, войти не может никто, включая тех, кто мог бы требование снять.

## Секреты, которые показываются один раз

Резервные коды второго фактора и API-ключи компаний хранятся отпечатком:
прочитать выданный секрет нельзя ни из интерфейса, ни из базы. Отсюда общие
правила — они распространяются на любой новый секрет такого рода.

- **Показ один и об этом сказано до закрытия окна.** Диалог не закрывается сам
  после успеха: закрыть его раньше, чем человек скопирует, значит потерять
  секрет навсегда.
- **Галочка «я сохранил» перед «Готово».** Единственные два места в портале, где
  мы просим подтвердить прочитанное; повод один — второго показа не будет.
- **В списке — хвост, а не маска.** `hd_…4f2a` сверяется глазом с тем, что
  прописано в интеграции; ровные точки не отвечают ни на один вопрос.
- **Вместо «показать» — «когда работал».** Когда значение недоступно, это
  единственный способ отличить живой секрет от забытого. Он же делает удаление
  осмысленным: фраза в подтверждении меняется по факту использования.
- **Забытый секрет — повод для плашки.** Ключ, которым ни разу не
  воспользовались, показывается предупреждением над списком: это открытая
  дверь, за которой никто не следит.
- **«Перевыпустить» вместо «удалить и создать».** Имя — то, по чему интеграцию
  узнают, и терять его при замене значения незачем.

## Словарь действий

Одно действие — одно слово, на всех поверхностях (кнопка, заголовок формы,
вкладка браузера, пункт «⋯»-меню). Расхождения ниже — не стиль, а баг. Канон:

| Ситуация | Канон |
|---|---|
| Правка структурной записи (инвентарь, компания, пользователь, заявка, услуга) | **«Изменить»** — в ⋯-меню, hero-кнопке, заголовке формы-шторки и `document.title`. Заголовок — глаголом: «Изменить модель устройства». |
| Правка свободного текста на месте (заметка, Obsidian-режим `NoteView`) | **«Редактировать»** — намеренное исключение: правим текст, а не поля записи. |
| Создание: кнопка-триггер, заголовок формы, `document.title` | **«Новый / Новая / Новое X»** (существительное, согласование рода): «Новая модель», «Новый вендор». Одно слово на всех поверхностях создания. Асимметрия с правкой намеренна: создаём — существительным («Новая модель»), меняем — глаголом («Изменить модель»). |
| Сабмит **формы** (add/update сущности) | **«Сохранить»** (прогресс — «Сохранение…»). Глагол «Создать» как сабмит не используем. |
| Сабмит **диалога действия** (принять, закрыть, присоединиться, удалить) | **Название самого действия**: «Присоединиться», «Закрыть заявку», «Удалить». Это подтверждение операции, а не форма сущности, и результат называется тем же словом. «Сохранить» тут сбивает: человек нажимает «Присоединиться» в шапке и видит в диалоге другое слово. |
| Отмена формы/подтверждения (есть сабмит, меняющий данные) | **«Отмена»** — в т. ч. диалог удаления, модалки действий заявок, загрузка изображения. |
| Закрытие read-only / просмотра (нечего отменять) | **«Закрыть»** — просмотр вложения, оригинала письма, фото в полном размере. |
| Удаление | **«Удалить»**. «Удалить безвозвратно» — только для необратимого (минуя корзину). |
| Фильтр | **«Применить» / «Сбросить»** (без слова «фильтр» в тексте кнопки). Залитая в шторке одна — «Применить» (мобайл); «Сбросить» — outline. |
| Поле даты / периода (`DateField`, `DateRangeField`, `DateTimeField`) | Плейсхолдеры **«Выберите дату» / «Выберите период»**; крестик очистки — «Очистить» (`aria-label`). Только календарь — ввода текстом нет. |
| Возврат из карточки | крошки **«‹ Откуда пришли»** (`app/Crumbs`); списком раздела — только когда следа нет. Не кнопка «К списку». |
| Переход к связанной сущности | **«Открыть …»**: «Открыть карточку», «Открыть профиль». |
| `document.title` | Обычное предложение, **не капслоком**: «Изменить компанию», «Новая модель»; карточка — **«Просмотр X»**. |

**Действие внешнего сервиса называет сервис.** Кнопка, которая уводит в чужую
систему или создаёт там сессию, начинается с её имени: **«PRO32 Пригласить»**,
«PRO32 Подключиться», «PRO32 Разрешить подключение». Рядом стоят действия самой
сущности, и голое «Пригласить» читается как приглашение коллеги в заявку.

**Военного сленга в интерфейсе нет.** «В строю», «на передовой», «бойцы» —
отвергнуто прямо. Про доступность людей пишем нейтрально: **«работают»**,
**«доступно»**, **«отсутствуют»**, **«не на работе»**.

**Исключение — генерация, а не добавление.** Действие, которое _порождает_ объект,
а не добавляет существующий (API-ключ, пароль), может называться
**«Создать» / «Сгенерировать»**. Такие места: создание API-ключа
(`Company/View/ApiKeysSection.jsx`) и **«Создать регламент»** на шаблоне заявки
(порождает регламент, предзаполненный этим шаблоном, — см. «Доменные блоки»).

**«Добавить X» — только привязка существующего.** Единственная роль глагола
«Добавить» — привязать уже существующую сущность к родителю (выбор из каталога/
списка), а не создать новую: «Добавить атрибут» (из каталога к типу), «Добавить
услугу» (подключить компании), «Добавить устройство» (из инвентаря в мониторинг),
«Добавить ответственного». Создание же — «Новый / Новая / Новое X», и
единственное отступление — генерация выше («Создать» / «Сгенерировать»).

**Подсказка описывает систему, а не наше решение.** Текст в интерфейсе отвечает
на «что это» и «что будет, если нажать», и никогда — на «почему мы так сделали».
Обоснование живёт в комментарии к коду и в этом гайде: человеку, который заводит
роль, оно ничего не даёт и читается как оправдание.

| Было | Стало |
|---|---|
| «Перечислять права незачем — роль даёт всё, включая то, что появится позже» | «Роль «Администратор» открывает все разделы и все действия» |
| «Роль другого адресата выбрать всё равно можно — она просто уйдёт вниз списка» | «Выбрать её можно и для другого типа аккаунта» |
| «Отдельно от „изменять людей“: вести карточку и распоряжаться входом — разные уровни доверия» | «Отдельно от права „изменять людей“» |
| «По умолчанию равен выходному, чтобы расчёт не изменился молча» | «По умолчанию равен коэффициенту выходного дня» |

Слова-маркеры, после которых текст надо переписать: «незачем», «нет смысла»,
«на самом деле», «просто», «всё равно», «как раз затем», «честнее», «намеренно».
И любое место, где подсказка спорит с читателем или объясняет устройство формы
вместо того, что форма делает.

## Тема и цвет

Поддерживаются **светлая и тёмная** темы + «системная» (`store/theme-context.jsx`:
`theme` = `light | dark | system`, флаг `isDark`, сохраняется в `localStorage`).
Провайдер ставит класс **`.dark` на `<html>`** — от него живут все токены
системы.
Больше ничего переключать не нужно: смена темы применяется на месте, без
перезагрузки страницы.

**Размер текста — личная настройка, тема — настройка устройства.** Масштаб
(`user.fontScale`, 100 или 125) хранится на сервере и следует за человеком;
`localStorage` — зеркало для первой отрисовки и экранов входа, после `/api/me`
сервер побеждает. Тот же провайдер ставит `data-font-scale` на `<html>`, а
применяет его CSS (`styles/tailwind.css`): `html { font-size: 125% }` **только
на десктопе** — на телефоне ширины 390px на четверть больше не бывает.
Масштабируется корень, а не текст: система на rem, поэтому вместе с кеглем
растут отступы, высоты контролов и ширины шторок — как при зуме браузера.
Отсюда правило для оболочки: **ритм в rem, px только у долей вьюпорта
(`maxWidth` страниц) и у SVG графиков**; px-резерв под rem-размер (бар,
рейл, остров) разъезжается при масштабе. Расчёт в JS (`rootMargin`
наблюдателя, «строка» колеса) читает корневой размер из
`getComputedStyle(document.documentElement).fontSize`, а не считает его 16.

**Канва — не ровная заливка** (`.auth-canvas`-блок «Фактура канвы» в
`index.css`, на `body` и `#root`, то есть ровно там, где базовый слой красит
канву). Техническая клетка 32 px, каждая пятая линия вдвое темнее (шаг
160 px), к углам всё угасает в цвет канвы, поверх — зерно.

- **Зерно — дизеринг, а не текстура.** Вуаль ползёт по каналу единицами, и
  в 8 битах это видно кольцами (на тёмной канве особенно). Шум с нулевым
  средним в режиме `overlay` ломает ступени, цвет канвы при этом остаётся
  ровно токеном. Без него любой широкий низкоконтрастный градиент на канве
  будет пятнить — это не повод его усиливать.
- **Привязка к окну, а не к документу** (`background-attachment: fixed`):
  иначе на длинной странице вуаль растягивается на всю её высоту и пропадает,
  а клетка едет при прокрутке.
- **Порог адаптации взят у канвы, а не у раскладки.** До 768 px канва белая
  (`--background`), на белом клетка заметнее — там она мельче (24 px) и
  слабее. Раскладка при этом перестраивается на `lg` = 1024: полоса
  768–1023 — мобильный стек на серой канве, это нормально.
- **Два исключения, оба гасят фактуру целиком.** Персональные обои
  (`user.backgroundImagePath`, слой `.app-wallpaper` в `layout/Root.jsx`):
  фон задаёт пользователь. И **чистый вид** (`user.plainCanvas`, «Мой аккаунт
  → Внешний вид → Фон приложения»): человек попросил ровную канву — тогда нет
  ни фактуры, ни обоев, ни листа под контентом, то есть ровно то, как
  оболочка выглядела до фактуры. Обои при этом не стираются: их выключили, а
  не удалили.
  Первое правило висит на `:has(.app-wallpaper)` — признак и так есть в
  разметке; второе на `html[data-canvas="plain"]`, рядом с `data-font-scale`,
  потому что настройка глобальная и должна действовать в том числе до входа,
  где оболочки ещё нет. Отдельного состояния под это не заводим.
- **Свет за листом — только на входе** (`:has(.auth-canvas)`). В приложении
  его нечем якорить: за листом формы мягкий бирюзовый ореол осмыслен, за
  списком заявок — нет. Ореол ходит за листом (`calc(50% + 222px)` с `lg`),
  иначе читается как пятно, сползшее в угол.

**Палитра — токены** (`src/styles/tailwind.css`, значения для
светлой / тёмной):

| Токен | Значение | Когда |
|---|---|---|
| `primary` | бирюза `#00bc8c`, текст белый | главное действие («Сохранить», «Новый …»), одно на экран |
| `background` | `#fff` / `#1d2024` | **базовая поверхность** (шторки, диалоги, панели) — сток-семантика shadcn, НЕ канва |
| канва | `#f4f5f6` / `#16181c` | фон страницы; красится оболочкой (`#root`/`body`), не токеном |
| `card` / `popover` | как `background` | панель списка, меню, поповеры |
| `muted-foreground` / `faint` | два уровня приглушённого | мета-строки, подсказки / счётчики, плейсхолдеры, неактивное |
| `accent` | серый ховер | фон наведения строк и ghost-кнопок |
| `accent-text` | читаемая бирюза `#007a5e` / `#0bd39f` | акцентный текст: метки групп, включённые способности |
| `destructive` | `#d63c3c` / `#f05252` | удаление, ошибки, `required`-звёздочка |
| `success` / `warning` / `info` | `#00bc8c` / `#eb9c14` / `#4d94e8` | семантика статусов (варианты Badge/Alert/Button) |
| `border` / `border-soft` | тонкие границы | контуры панелей / разделители строк |

Принципы: **статус — цветной текст с точкой, а не заливной бейдж**; заливка —
только у главного действия и семантических алертов.

**Цвет — ресурс, а не украшение.** Правило, выведенное на редизайне базы знаний:
на экране цветом говорим **максимум о трёх вещах**. Однородные сущности
(категория, компания, пользователь) различаются **иконкой** и живут одинаковой
нейтральной пилюлей с `Ri*`-иконкой, иначе бейджи превращаются в светофор без
смысла.

**Цвет говорит о состоянии, а не о виде записи.** Тип заметки базы знаний
раньше красил бейдж: «Информация» была бирюзовой (цветом главного действия), а
«Бэклог» — янтарным, как и «не проверено», — два разных смысла одним цветом в
одной строке. Теперь **вид несёт иконка** (`NOTE_TYPES.icon`, нейтральная
пилюля), а цветовая ось у экрана одна — состояние: `warning` у непроверенного и
истекающего, `destructive` у ждущего решения об удалении, приглушённое у
архивного. Поле `badge` в каталоге типов осталось только для немигрированной
панели заметок на странице заявки.

## Иконки

- Только **react-icons / Remix (`Ri*`)**, размер задаём `size={...}`. Набор в
  приложении один: `lucide-react` снят, иконки в сгенерированных
  `components/ui` переведены на `Ri*` — в шапке каждого такого файла стоит
  напоминание повторить замену после перегенерации CLI.
- Закрепившиеся соответствия: `RiSaveLine` — сохранить, `RiArrowGoBackFill` —
  закрыть/назад, `RiAddFill` — добавить, `RiDeleteBinLine` — удалить,
  `RiRefreshLine` — обновить/перегенерировать, `RiCheckLine` — выполнено.
- Иконка обычно идёт перед текстом в кнопке (`<RiSaveLine /> Сохранить`).
- На узких экранах подпись прячут, оставляя иконку (так делает кнопка
  создания в `ListWrapper`).
- **Статусы присутствия в вебе — иконки каталога** (`icon` в
  `util/work-statuses.js`: бейдж аватара, заголовки групп, чипы меню). Эмодзи
  каталога остаются Telegram-табло: там иконок нет, а в вебе эмодзи рисуются
  по-разному на каждой ОС.

## Обратная связь и статусы

- **Тосты** — **sonner** (`ui/sonner`, `<Toaster/>` в `Root.jsx`, снизу
  справа): вызов — `showToast(variant, message)` из `store/toast-store.js`
  (имена вариантов — `success`/`danger`/… — маппятся на toast.success/error/…).
  `Toaster` живёт в `Root`, поэтому вне оболочки
  (пред-авторизационные экраны, публичные страницы) тостов нет — там всё
  говорится инлайн.
- **Инлайн-алерты** — `app/AlertMessage` (те же имена вариантов). Внутри
  форм ошибку/успех показывает сам `FormWrapper`.
- **Статусы в списках** — цветной текст с точкой или метка группы
  (`ListGroupLabel`); заливной бейдж — для компактных мест, карты
  «статус → вариант» собираем рядом с компонентом. **Точку не кладите первым
  флекс-элементом**: базовая линия флекс-контейнера берётся от первого элемента,
  а у пустой точки её синтезируют по нижнему краю — статус уезжает вниз
  относительно соседей по строке. Точка — `inline-block` с `align-middle` в
  обычном строчном потоке (`Ticket/ticket-state.jsx`).
- **Длительные операции** — `app/Spinner`; для опроса фонового результата —
  паттерн «спиннер + поллинг». **У статуса «в работе» обязан быть срок.**
  Фоновая работа умирает не только с ошибкой: перезапуск процесса убивает её
  молча, статус остаётся «в работе», и опрос идёт вечно — выхода из ожидания у
  человека нет вовсе. Срок ставит бэкенд (отметка старта + предел), он же
  переводит просроченное в ошибку с причиной; фронт время не считает.
  Отдельно проверьте, **не ждёт ли этого статуса кто-то ещё**: у нас уведомление
  о заявке ждало расшифровки звонка, и зависшее «распознаётся» означало не
  крутящийся спиннер, а заявку, о которой никто никогда не узнает.
- **Пустые состояния** — не пустой экран: в списках встроены в `ListWrapper`
  (см. «Анатомия списка»), в секциях карточек — см. «Страница сущности».

## Ошибки и гейты прав

Единый каркас — `components/Error/ErrorScreen.jsx`: код с котом-талисманом
вместо средней цифры (4·4, 4·3, 5·0, 5·3; состояние без HTTP-кода — кот соло),
заголовок, пояснение, действия, строка автоповтора и тихая тех-строка.
Состояния — `components/Error/{404,403,500,503,NetworkError}.jsx`, диспетчер —
`pages/Error.jsx` по `useRouteError`: 401 → редирект на `/auth`; 403; 404;
502/503/504 → «Обновляемся»; сетевой TypeError fetch («Failed to fetch») →
«Нет соединения»; всё прочее → 500.

- **Текст — «что случилось → почему могло → что делать»**: без «Упс»,
  капслока и вины пользователя. 404 называет сущность по имени и в правильном
  роде («Не нашли заявку №51713») — карта «маршрут → слово» в
  `components/Error/entity-context.js` (новый раздел = новая запись), главная
  кнопка ведёт к списку раздела, не абстрактно «На главную».
- **Маскот — только для наших страниц ошибок.** На публичных страницах для
  стороны клиента (согласование по ссылке из письма) `ErrorScreen` не годится:
  кот-талисман здесь незнакомая картинка, а после подписи финансового документа
  он ещё и выглядит несерьёзно. Итоговый экран там свой — иконка состояния,
  заголовок, строка пояснения. И успех вообще не ошибка: «Отчёт согласован»
  нельзя рисовать каркасом страницы ошибки только потому, что раскладка совпала.
- **Оболочка выживает**: errorElement стоит на уровне детей корня (App.jsx) —
  навбар и таб-бар живые, из ошибки можно уйти в любой раздел; корневой
  errorElement — фолбэк на случай падения самого authDataLoader. Root узнаёт
  об ошибке через `store/route-error.js` (флаг ставит layout-эффект
  `pages/Error.jsx`) и кладёт страницу на канву (944) без легаси-Card и
  сайдбара.
- **503 и «Нет соединения» проверяют себя сами**: `use-availability-probe`
  пингует публичный эндпоинт и по успеху перезагружает страницу (после деплоя
  это заодно подтягивает свежие ассеты). **Ревалидацией роутера ретрай не
  делаем** — после ошибки она не гарантирует перезапуск упавших загрузчиков.
- **Анимации** — в `styles/tailwind.css` рядом с `row-flash`, reduced-motion
  уважается. Кадрирование маскота — в комментарии у `ErrorScreen`.
- **Гейт прав в шторке/секции — `components/Error/InlineForbidden.jsx`**:
  плитка-замок + «нужно право „X“» (label из `User/permissions-catalog.js`).
  Полноэкранный 403-арт внутри шторок не рендерим; полностраничный гейт —
  `Error/403.jsx`.

## Чек-лист перед мерджем UI

Единственное место, где правила намеренно повторяются: строки ниже — короткие
напоминания, а не вторая редакция. Расходится строка с разделом — прав раздел.

**Формы**

- [ ] Форма открывается в **нижней шторке** через маршрут `add`/`update` и
      обёрнута в `FormWrapper`. Исключение — документ: правится на месте.
- [ ] На десктопе шторку не закрывает клик мимо (`Escape` — закрывает, его не
      гасить); ширина из шкалы `md/lg/xl` и **одинаковая со списка и с
      карточки**; скроллится внутренность шторки, а не она сама.
- [ ] Навигация после сабмита: создание → карточка созданной сущности, правка →
      остаёмся где были; redirect с `replace`; форма с «чужой» страницы —
      вложенным маршрутом этой страницы.
- [ ] Поля — `app/Field`/`app/SwitchField`; выпадающие списки — `app/Combobox`
      (значение в FormData — пропом `name`).
- [ ] Каждая подпись связана со своим контролом (клик по подписи переключает
      свитч/чекбокс, фокусирует поле): `Field`/`SwitchField`/`SettingRow
      htmlFor`/label-обёртка; подписей-«div» без связи нет.
- [ ] Диалог — только подтверждение/короткое действие.
- [ ] Мастер: степпер во всю ширину шторки, живая сводка справа; создание —
      визард, правка — плоская; наборы полей у создания и правки совпадают;
      неприменимые типу шаги убраны целиком.
- [ ] Длинная правка — `app/FormLayout` (липкий заголовок + секции с рейлом);
      ключ секции = якорь, ярлык с карточки открывает форму на ней.
- [ ] Вложенное тело (объекты, массивы, матрицы) — **JSON**, не ручной FormData.
- [ ] Чужие личные настройки уходят на сервер только при реальном изменении, с
      предупреждением; бэкенд мержит по путям.

**Списки**

- [ ] Заголовок секции, скрытой правами, не рендерится; данные видны без
      обязательного фильтра; пустое состояние предлагает действие.
- [ ] Серверная выборка: счётчик — `total` от API (`count`), пагинация в
      `belowList`, скоуп и поиск считает БД, фоновые обновления мержатся в
      строки без сброса страниц.
- [ ] Кликабельная строка не срабатывает от кликов **внутри порталов** (диалог,
      меню, шторка): React всплывает события по дереву компонентов, а не по DOM,
      поэтому обработчик строки проверяет
      `event.currentTarget.contains(event.target)` (см. `app/ListRow`). Симптом —
      «закрыл модал, а меня унесло на карточку».

**Карточка**

- [ ] Крошки сверху — через `app/Crumbs`; адрес списка руками НЕ вписан (его
      знает `util/sections`), кнопки «К списку» в действиях нет.
- [ ] Ссылка в ЧУЖОЙ раздел несёт `from`/`state` (`useCrumbFrom`) — иначе на той
      стороне человек получит список чужого раздела вместо пути назад.
- [ ] Одна залитая кнопка, выбранная состоянием; остальное — ghost/outline и
      icon-only «⋯»; подписи «Действия» нет.
- [ ] Запрос, ожидающий решения, — инлайн-`Alert` с автором и датой, не пункт
      меню.
- [ ] Статус с автором/датой/сроком — фразой, а не голым бейджем; бэкенд отдаёт
      имена (`populate`), а не `ObjectId`.
- [ ] Длинный однородный список — через `PillPanel` (сам сворачивает, «Показать
      все (N)»).
- [ ] **Ни одно поле не правится в двух местах**: секции показывают, правка —
      в форме; у секции есть вход в неё → `update#<якорь>`, но нет своего
      редактора и своего «Сохранить». Секция, грузящая данные сама, перечитывает
      их по `version` после сохранения формы. Исключение — секция, которая и в
      покое меняет данные на месте (документ, чек-лист заявки): у неё правка
      идёт своим режимом (`SectionEditButton`), а не в форме.
- [ ] Слово **«Изменить» на карточке одно** — залитая кнопка в hero. Секционный
      вход — карандаш `app/SectionEditLink` или `app/SectionEditButton` (секция
      обёрнута в `app/Section`); текстовая кнопка остаётся только у действия со
      своим именем («Выдать», «Прикрепить», «Задать график» у пустой секции).
- [ ] Правка на месте — только документ (заметка): геометрия чтения и правки
      совпадает, `Ctrl+E`/`Ctrl+S`/`Esc`, `useBlocker` + `beforeunload`,
      побочный эффект сохранения назван до сохранения.
- [ ] Информация, общая с другими разделами (чек-лист, кастомные поля,
      расписание), — одним компонентом из `components/app`; заготовки
      шаблон → заявка переносятся на бэкенде (поля моделей совпадают по именам).

**Мобайл**

- [ ] Панели — флекс/absolute-дети `.mobile-shell` (не `position:fixed`),
      скролл только у `.mobile-shell__scroll`, слушателей скролла на `window`
      нет; на экране один плавающий объект.
- [ ] Заблокированное массовое действие объясняет причину (тултип на десктопе,
      тап-подсказка на мобилке) и называет объекты по имени, не по id.

**Код, цвет и текст**

- [ ] Кегли и высоты — по ролям «Типографики»: в ряду контролы одной высоты,
  ритм оболочки в rem, px-расчёты в JS читают корневой размер.
- [ ] Утилиты только из встроенной сетки (без `-[Npx]`); компоненты — shadcn
      и каталог `app/*`, а не ручная сборка.
- [ ] Повторяемый кусок — из каталога `components/app`, не свёрстан заново
      (перед вёрсткой — свериться с таблицей каталога).
- [ ] Иконки — `Ri*`; семантика — вариантами/токенами; цветом максимум о трёх
      вещах; статус в списке — текст с точкой/меткой группы, а не светофор
      бейджей.
- [ ] Тексты действий — по «Словарю действий» («Новый X» / «Изменить» /
      «Сохранить» / «Отмена» vs «Закрыть» / «Добавить» только для привязки).
- [ ] Графики — только `ChartContainer`+`ChartConfig` с токенами `--chart-*`
      (палитра — через валидатор), контенты тултипа/легенды — shadcn'овские;
      подписи значений или таблица рядом; серий >5 нет — хвост в «Прочие»;
      высота графика явная (см. «Страница отчёта и графики»).
- [ ] Проверено в светлой и тёмной теме, на десктопе и мобайле; верификация —
      `pnpm build` + `pnpm eslint`, живой UI проверяет Алексей (см. правила
      миграции).
